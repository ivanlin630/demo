# 批 2（經濟三票）merge 順序與 baseline 計畫

> systems 立 2026-09-06。★**這份存在的理由**：批 1 的六票是**一起**進的，
> 而那讓「批後對比」只能回答「這六票合起來造成什麼」，**答不出是誰造成的**。
> ★★批 1 最後靠一格**歸因 cell** 才把功勞拆開（造出流量的是⑥拔身分閘＋⑦相位；⑤是語意訂正）——
> ★★★**那是事後補救，不是設計**。這一批不重蹈。

## ★硬規則：**三票不得一起 merge**
```
⑨貨幣創世   —— 改【創世】= 換世界
B-v0 市場厚度 —— 改【撮合/寄賣】= 換交易層
⑩拆物價 clamp —— 改【估值】= 換價格訊號
⇒ ★三者動的是【不同子系統】,而它們【都會動同一批數字】(價格/成交/庫存/coin)
⇒ ★★合著進 ⇒ 下一條 baseline 讀不出是誰造成的 ⇒ 又要再開一次歸因 cell
```

## ★★順序與理由（★可被推翻，但要說出理由）
| 序 | 票 | 為什麼排這裡 |
|---|---|---|
| 1 | ★**⑩ 拆 clamp** | **改動面最小、且是【純估值】**——它不改誰跟誰交易，只改價格數字。★★先進它，後面兩票的 baseline 就已經是「價格訊號正常」的世界 |
| 2 | **B-v0 市場厚度** | 它改的是**撮合能不能成立**；★在 ⑩ 之後量，才分得出「成交變多」是【價格對了】還是【機制通了】 |
| 3 | ★★**⑨ 貨幣創世** | ★**它換世界**（初始批＋分配形狀）⇒ **它之前的所有 baseline 都作廢** ⇒ ★★★**必須最後**，否則前兩票的對比全部要重做 |

## ★★★每一票之間要做的事（★不做就等於合著進）
```
①該票 merge 後,跑【同 seed 同床】的量測,產出一份 <ticket>.measure.json
②★而那份量測的【對照組】是【前一票 merge 後】的那一份 —— 不是批前
   ⇒ 這樣每一票的差值就是【它自己造成的】
③★★三票都進完之後,再跑一次【批前 vs 批後】的整批對比 —— 那份答的是「這一批值不值得」
   ⇒ 兩種對比都要,它們答的不是同一個問題
```
★**環境紀元**：三票的量測都在 `2026-09-06` 之後 ⇒ 同一紀元，牆鐘可比（見 `env-epochs.tsv`）。
★★**而如果中途有人改了環境，紀元表要加一行，這一批的牆鐘對比就要重新分組。**

## ★誠實限
```
★這份順序假設【三票之間沒有硬相依】—— 我沒有逐一驗證過
   (例:B-v0 的寄賣若讀價格,它就依賴 ⑩;⑨ 的初始批若被 B-v0 的 escrow 記帳)
⇒ ★★implementer 若在做的過程中發現相依,以他看到的為準,回一封改順序
⇒ ★★★而「我沒驗過」這件事要寫在這裡,不是寫在我心裡
```
