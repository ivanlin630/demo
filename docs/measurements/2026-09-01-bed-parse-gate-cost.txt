═══════════════════════════════════════════════════════════════════
★★②分佈：長尾，不是少數重量級 ⇒ 沒有便宜的針對性解
═══════════════════════════════════════════════════════════════════
```
檔數 321｜逐檔 load 總計 54.7s（★不含 dir walk 與啟動）
   3300ms  a2a_join_guard_test.gd
   2979ms  headless_test.gd
    441ms  ui_flow_test.gd
    433ms  agent_repl.gd
    ...（其餘 300+ 檔多在 150–400ms）
★前 12 名合計 10.2s ＝ 18.6%

```
★**而最貴的兩張正好是最大的兩個檔**（headless_test ~16k 行）
  ⇒ 載入時間 ∝ 檔案大小 ⇒ ★這是【編譯 321 個檔】的真實代價，不是浪費。

═══════════════════════════════════════════════════════════════════
★★★③所以取捨是【真的取捨】，不是「有沒有人去優化」
═══════════════════════════════════════════════════════════════════
```
A 接受 70s
   ★代價：runner 總時 78s；★★而 systems 的擔心（趕時間時跳過）成立與否要看人
B 依 hash 快取，只載入【變過的床】
   ★★而它【不安全】：一張床可能因為【它引用的 production class 改了】而壞，自己內容沒變
   ⇒ 要正確就得【production 一改就整份失效】
   ⇒ ★★★而 merge-gate 跑的時候幾乎【一定】有 production 改動 ⇒ 快取幾乎總是失效 ⇒ 省不到
C 只載入「changed since merge-base」的床
   ★★★同 B 的洞，而且更嚴重：它連「production 改了」都不看
D runner 並行跑（bed-parse 與其餘 5 支同時）
   ★牆鐘 78s → ~70s ⇒ ★★省 8s，而複雜度與錯誤訊息交錯的代價不小
```
★**我的建議（★判定是 systems 的）：A，並把理由寫進註冊表那一行**
  ⇒ ★★因為真正該防的不是「慢」，是【有人以為跳過它沒關係】——
     ★★★而那要靠【它擋過什麼】被記著（2026-08-27 那張 qty_tap_bed 的血證），不是靠它變快。
