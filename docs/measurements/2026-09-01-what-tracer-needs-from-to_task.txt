# 【specimen tracer 到底需要 to_task 的什麼？】—— ★只查不修
#
# ★這個問題從來沒被回答過：R² 回答的是「29 個 handler 有沒有讀 idle_employ_value」
#   ⇒ 那是【相鄰但不同】的問題（它證明「那顆快取沒用」，不證明「tracer 不需要 to_task」）。

═══════════════════════════════════════════════════════════════════
★★★答案（一句話）
═══════════════════════════════════════════════════════════════════
tracer 需要 `to_task` 的，只有【靜態 option 的 `task` 與 `target` 兩欄】，
用來算【一個 bool `nd`】，而 `nd` 的唯一消費者是 dump 字串裡的【一個 ✗ 字元】。

═══════════════════════════════════════════════════════════════════
★①逐條追（file:line）
═══════════════════════════════════════════════════════════════════
specimen_tracer.gd:99-100（★唯一的呼叫點）
```
var td: Dictionary = DecisionOptions.to_task(state, team, opt)
var _task = td.get("task", TeamData.TASK_IDLE)
var _tgt: Vector2i = td.get("target", Vector2i(-1, -1))
nd = (_task == TASK_IDLE) or (_tgt == (-1,-1) and _task != TASK_FLEE)
```
⇒ ★取的欄位只有兩個：`task` / `target`；★★而它們只被合成一個 bool。

`nd` 往下游走到哪：
```
specimen_tracer.gd:110  _cd["nd"] = nd            ← 存進候選字典
specimen_tracer.gd:388  "✗" if c.get("nd", false) ← ★唯一的消費者
```
⇒ ★★★全域 grep：**沒有任何 production／床／判決檔讀 `candidates[].nd`**。
   它是給 QA 人眼看的一個標記（「util 最高但當下不可派」）。

★②而【動態 candidate 早就不呼叫了】（2026-08-26 假陽性修）
```
specimen_tracer.gd:96-102
  var _ctt0 = e["cand"]["to_task"]            ← candidate 自帶
  if not _ctt0.is_empty(): nd = (target == (-1,-1))    ← ★零呼叫
  else:                    nd = ...to_task(...)        ← ★★只剩這條會呼
```
⇒ ★所以「tracer 呼 to_task」現在**只發生在靜態 option**那一條 else 分支。
⇒ ★★同一支函式裡另外兩處用 `to_task` 的（`_cd["要做的事"]`、means-end 標記）
   **全部讀 candidate 自帶的 dict，零呼叫**。

═══════════════════════════════════════════════════════════════════
★★★③關鍵事實：production 自己【一個迴圈之後】算的是同一件事
═══════════════════════════════════════════════════════════════════
```
tracer（rank 內）：
  specimen_tracer.gd:99   DecisionOptions.to_task(state, team, opt)

production（dispatch 迴圈）：
  faction_ai_system.gd:2804
    var td = (e["cand"]["to_task"]) if e.has("cand") else DecisionOptions.to_task(state, team, opt)
  faction_ai_system.gd:2822-2823
    if tgt == (-1,-1) and td["task"] != TASK_FLEE: continue   # 不可派 → 試次佳
```
★**兩邊是【同一個表達式】、算【同一個判斷】、對【同一批候選】**——
★★差別只有：tracer 在 `rank_scored` 內（:53）算，production 在 dispatch 迴圈算，**晚一個迴圈**。
⇒ ★★★**所以 tracer 不需要自己呼：它需要的東西，production 待會就會算出來。**

═══════════════════════════════════════════════════════════════════
★★A 案成立，而形狀具體
═══════════════════════════════════════════════════════════════════
```
把 `nd` 從【capture 時自己算】改成【dispatch 時由 production 順手戳記】
⇒ 零額外呼叫 ⇒ ★零額外 gather ⇒ ★★不需要任何黑名單（沒有寫入要抑制）
```
★**這也解掉了那三次失敗的根**：前三次都在問「要抑制哪些寫入」，
★★而正確的問題是「為什麼要走那條會寫的路」——**答案是不必走。**

## ★★★代價（★誠實列，這是這個方案唯一的損失）
```
dispatch 迴圈在【第一個可派候選】就 return ⇒ 它後面的候選拿不到 nd
⇒ ★那些候選在 dump 上不會有 ✗ 標記
★★而 nd 的用途正是解釋「util 最高的那個為什麼沒被派」⇒ 關心的是【前段】
⇒ ★★★損失落在【本來就沒有故事價值】的那一格：
   排在已派候選之後的選項，production 根本沒考慮它們，「可不可派」對故事沒有意義。
```
★**而若 QA 真的要後段的 ✗**，那就不是「順手戳記」能給的，
  ★★需要一個【真的 pure 的 to_task 投影】（B 案）—— 那是另一個決定，不在本票。
