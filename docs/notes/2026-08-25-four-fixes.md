## §1 為什麼 #1 是急件

`fb9f4687`（2026-08-25 16:57）的 commit 訊息原文：

> `docs(test): land the [FAIL] print list as a file, **after three failed handback deliveries**`

⇒ 那天不是「implementer 沒發信」——**它發了三次，三次都沒送到**，才改成落檔。
（同日該角色寄出 **52 封**，全部 consumed；它不是不寄信的角色。）

真根在 `18:14`／`18:15` 被抓到：

```
watchdog 孤兒殭屍手術: 6 隻歷代 orphan（管道死仍持鎖）全清
★★★訂正診斷:「watchdog 掛了=否」證據不成立（殭屍也會 touch lock）
```

### 為什麼現有兩道防線都抓不到殭屍

| 機制 | 治什麼 | 對同代殭屍 |
|---|---|---|
| 搶佔式 arm | 舊代不讓位 | ❌ 殭屍 lock 格式正確、pid 存活、心跳新鮮 |
| 跨代判代（欄數 < 3） | 版本歪斜 | ❌ 同版本 |
| **session_id 綁定**（P4） | 分辨 compact vs 真重開 | ⛔ **它那條「同 session → 安靜退出」正好放過 compact 產生的殭屍** |

★ compact 後 `session_id` 不變、bash pid 還在跑 → 判「覆蓋仍在」→ 不 arm
→ **而那支的 stdout 管道可能在 compact 當下就斷了。**

### 為什麼是「刪分支」而不是「加偵測」

**能證明管道活著的只有一件事：成功寫過 stdout。** 沒有便宜的偵測法
（主動 emit 心跳＝定期喚醒 session，太貴；challenge/response 殭屍照樣答得出來，因為它的 bash 迴圈還在跑）。

⇒ **與其偵測，不如每次 arm 都換血——新起的一定活著。**

原本保留那條分支的理由是「避免 `SEEN` 空掉重吐」，
但 **`SEEN` 落地（`.inbox-seen.<role>`）已經解決重吐**。
⇒ 那條分支現在是**純負債**：省不到東西，卻正好漏掉唯一漏網的那類殭屍。
