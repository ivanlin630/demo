## §0 原始目的與診斷

**用戶三個月前建文字介面的原始目的：讓 agent 自己玩遊戲，自檢「哪些功能沒進 UI、哪裡有 bug」。**

診斷（2026-09-08 實測）：

| 層 | 現況 |
|---|---|
| 指令層 `player_command_api`／`player_command_system` | **~50 個動詞已接線**，每個自帶 `enabled / disabled_reason / label`（context 動詞架構在） |
| 讀取層 `player_api_mapper`（891 行、30+ 面板映射） | 團/派系/倉儲/據點/子隊/成員/交易/訊息/地點… 在 |
| agent 入口 `scripts/debug/agent_repl.gd`（321 行，JSON 逐行指令介面） | **存在，骨架完整**——但**最後更新 2026-06-02** |
| GUI（`scripts/ui/*` 8 個場景、text_ui_main 2018 行） | 最後實質更新 **2026-07-13** |

⇒ **agent 玩得了，但兩條路都是 6 月化石**。6 月後 merge 的機制（市場板／寄賣／薪資／camp-access／貨幣創世／belief 四源）**沒有一個進了指令表**。

**三個斷點**：
1. 入口停更——agent 連上玩的是 6 月的遊戲
2. **缺 oracle**——REPL 只回 `ok:true`，agent 能按按鈕、**不能判對錯**（掛了單，該出現在板上、該扣糧——沒有斷言）
3. **沒進工作流**——P9 交付物全是引擎產物（spec/verdict/measure），**沒有一格是「玩家碰得到」**，所以每個新機制天生漏接 GUI 與 REPL——**兩者共用同一個 api 層，一起 drift 是制度保證的**

## §2 三段修法（★順序＝先 agent 後 GUI）

### ① 復活 agent 入口到現況（一張中票）
把 6 月後的新動詞補進指令表（市場四件套為首），讀取層補市場板。**GUI 與 REPL 共用 api 層，補一次兩邊都拿到。**

### ② ★工作流義務：`player_reachable`（用戶核可：先討論後核可，本場即討論）
派工單 frontmatter 加一欄，與 `slice:`／`tier:` 並列，**立案時由 systems 定、做的人不能自己選**：
```
player_reachable: yes | no
```
`yes` ⇒ 交付物多兩項（seam gate 加一格檢查）：
- (a) 動詞／讀取進 `player_command_api`（GUI 與 agent 入口同時拿到）
- (b) **一條 agent 自檢腳本**：用 REPL 跑該動詞並**斷言結果**（掛單→板上該有這單→斷言；付薪→person.coin 該增→斷言）

⇒ (b) 才是原始目的的落點：**「功能有沒有進 UI」從人工抽查變成 agent 可跑的迴歸。** 不驗畫面品質（永遠是人的活），只驗「碰得到＋判得出」——機器驗得動。
`no` 的票零負擔（純引擎內部／量測床）。

## §3 擺放原則與版面

**三原則**：
1. **C1 五類＝右欄五分頁**：`團│據點│人│核心│事件`——前四頁狀態頁（as-of 戳＋事件尾巴），第五頁全事件流。不另發明資訊架構。
2. **動詞不另立選單**：既有 `available_actions` 架構照用，市場四件套註冊進去；`disabled_reason` 白話寫原因。
3. **市場板＝地點感知彈窗**：人在市場格 → 動詞列出現「看板」→ 彈窗顯示板上單（含 relay 異地單＋新鮮度）——**同時就是 L2 情報的玩家視窗**。

```
┌──────────────────────────────────────────────────────┐
│ 頂列：時間控制  ⏸ ▶ ▶▶ ▶▶▶ │ 跳到下一事件 │ 第N天    │ ← TurnControls 擴
├────────────────────────┬─────────────────────────────┤
│                        │ 右欄＝記憶 UI（C1 框）        │
│      世界地圖           │ ┌─────────────────────────┐ │
│   （belief 迷霧渲染，    │ │ 團│據點│人│核心│事件      │ │ ← 五分頁
│    known 才畫，舊情報    │ ├─────────────────────────┤ │
│    灰顯＋as-of）        │ │ 狀態頁：belief 快照       │ │
│                        │ │  每欄帶 (第N天·親見/幾手) │ │
```

## §4 優先序

| # | 項 | 理由 |
|---|---|---|
| **1** | 復活 agent 入口＋市場四件套（動詞＋板面板） | 經濟核心零觸及；agent 自檢的前提 |
| **2** | `player_reachable` 欄＋自檢腳本義務入工作流 | 防再漏；把自檢變迴歸 |
| 3 | 記憶框（五分頁＋事件流＋as-of＋血統） | C1 主體＝通用曝光層，之後每機制只欠「餵條目」 |
| 4 | 附身選擇＋point-buy | 開局入口 |
| 5 | 時間控制擴建／釘選 | 小 |

**存量還債**（用戶傾向）：**不盤點，隨玩隨補**——框蓋好後每筆是小錢，缺口要等真的有人（或 agent）玩才知道哪些痛。

驗收判準：C1 的 ≤2 跳歸因可達性；agent 自檢腳本綠。

## §5 誠實邊界

- 動詞表 ~50 是從 `player_command_system` 的 action 名稱數的，**沒逐一驗每個都能在現行世界跑通**（可能有 6 月後被引擎變動打壞的）——這正是①復活票要順手做的事。
- 「缺 oracle」是讀 REPL 回傳格式的判斷；若別處已有斷言框架供 agent 用，①可省一半。
- 影子 session 沒動任何 code／hook。
