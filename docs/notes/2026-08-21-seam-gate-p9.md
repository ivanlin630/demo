## §1 為什麼要有 P9

用戶問：**「這工作流更新後會確保職責與丟給下一站嗎？」**

**答：不會。** 前作那八項是「**漏了會被發現**」，不是「**不會漏**」。

三個具體的洞，八項一個都沒堵：

| 洞 | 說明 |
|---|---|
| **信的內容不看** | 偵測器只問「有沒有信」。**寫一封空信，所有警報立刻閉嘴** |
| **丟給對的下一站不驗** | `to:` 欄寫錯（該給 reviewer 卻直推 implementer）→ **零紅燈**。R②「每 slice 必過 reviewer」是純散文 |

★ 而這條法用戶 2026-08-04 就立過了（`00_roles.md:30`）：

> **通則：hook 提醒 ≠ gate，gate 裝執行點（鎖／merge）非 advisory 上游**

**前作那八項全部是 advisory 上游。一條 gate 都沒裝在執行點上。**
P9 就是那條裝在執行點（merge）的 gate。

## §2 ★先講障礙：我原本的估算低估了

我先前對用戶說「一張表 + ~100 行掛在 `constitution_gate` 上」。**實測後兩個部分都錯。**

### 2.1 不能掛 `constitution_gate.gd`（類別不符）

它是 **原始碼指紋掃描器**（174 行，掃 `scripts/simulation` 找補丁閘／god-view，
指紋 = `<relpath>::<func>::<type>`，契約 `current ⊆ baseline`）。
**跟 slice 產物完全無關。** 硬掛進去會污染一個乾淨的 code gate。

⇒ **獨立小腳本**，跟它並列在 merge 前跑。

### 2.2 ★真正的障礙：產物不帶 slice id

`00_roles.md:20` 已經有 slice id —— **branch/worktree 名 `feat/<slice>`**，而且用得很一致：
```
feat/convoy-return-conservation   feat/convoy-dispatch-tap
feat/convoy-drop-enum             feat/owner-outpost-index
feat/directive-stamp-honesty
```

**但產物不帶它。** 拿這五條 branch 去 grep 三類產物（`grep -i <slug>`）：

| slice | spec | handback | measure |
|---|---|---|---|
| convoy-return-conservation | ❌ | ✅ ×2 | ❌ |
| convoy-dispatch-tap | ❌ | ✅ | ❌ |
| convoy-drop-enum | ❌ | ✅（`convoy-drop-**enumeration**`，靠前綴僥倖命中） | ❌ |
| owner-outpost-index | ✅ | ✅ ×2 | ❌ |
| directive-stamp-honesty | ✅ | ❌ | ❌ |
| **命中率** | **2/5** | **4/5** | **0/5** |

三套命名互不相通：
- spec：`YYYY-MM-DD-<slug>-{HOW,design}.md`
- handback：`YYYY-MM-DD-<from>-to-<to>-<topic>.md`
- measure：`<主題>.measure.json`（**短 slug、無日期、跟 slice 完全脫鉤**：`orderbook-health` / `d1-pop-vs-cap`）

⇒ **substring 比對會大量假紅。不可行。**

### 2.3 ★但 0/5 的 measure 有一半不是病 —— 這推出了設計的第二個支柱

上表五條裡，`convoy-drop-enum` 是**列舉盤點票**、`convoy-dispatch-tap` 是**加 tap 票** ——
**它們本來就不欠 spec、不欠 measure**。缺不是病。

⇒ **一刀切的 seam gate 會製造大量假紅。必須分檔。**

這正是 evora `light.yaml` 的處理（該檔開頭自述）：
> **從一條規則導出：機械變更不欠的就砍。** 砍掉 ideate/converge/measure/accept，剩 seed → implement → review。
> ⛔ **`review` 不砍** —— owner 反對的從來不是繁文縟節，是 **agent 自己決定自己的監督**。
> **輕流程省的是 paperwork，不是 check。**

## §3 設計

### 3.1 三個支柱

**① slice id 落地** —— 每個產物 frontmatter 加一行：
```yaml
slice: convoy-drop-enum        # = branch 名去掉 feat/
```
★ **這是唯一的來源，不再有第二個真相**（對照 evora 的 `membership`：seed 的 front-matter 回答「這 item 屬哪條 flow」，**別無其他來源可 drift**）。
★ **只綁新寫的，舊產物不溯改**（同 R6 紀律；1293 handback + 142 spec 回填不可能也沒價值）。

**② 分兩檔，且做的人不能自己選**

| tier | 欠什麼 | 用於 |
|---|---|---|
| **`full`** | spec + **R② verdict** + handback + `.measure.json` | 產 code、要 merge 進 main 的 slice |
| **`probe`** | handback（＋若下因果結論則 `QA:<ref>`） | 列舉盤點／加 tap／診斷票／量測票 |

⛔ **`tier` 由 systems 在派工單時決定，寫進 dispatch handback 的 frontmatter。**
理由直接照抄 evora（用戶原話等價）：**能自己選輕流程的 agent，是在改自己的考卷。**
systems 不做 implementer 的活，所以由它定。

⛔ **兩檔都不砍 `review`。** probe 省的是 spec/measure 這些 paperwork，**不是 check**。

**③ gate 裝在 merge**（獨立腳本，與 `constitution_gate` 並列）
```
輸入：branch 名 → slice id
查：所有產物 frontmatter 的 slice: 欄
按 tier 逐項檢查 → 缺 = 紅
```

### 3.2 兩階段上線（★不可跳）

**階段 A — SOFT（只印不擋）**
跑一段時間，收集「哪些 slice 缺哪些產物」。**這就是 baseline。**

⛔ **不回溯武裝。** 只對「宣告了 `slice:` 欄」的 slice 生效。
（evora 血訓：`missing-seed` 回溯武裝是**結構性空洞** —— seed 是 membership 的鑰匙，沒 seed 的 item 根本不在母體、**永遠不可能被標紅**。同一族的錯要避開。）

**階段 B — HARD（擋 merge）**
baseline 穩定後轉硬。**增列 baseline = STOP，要人裁。**

### 3.3 gate 自己要能失敗（`expect_min` 精神）

⚠ **一個匹配不到任何東西的檢查，會印「0 violations」而讀起來像 PASS。**
（evora 兩次踩到：`reviewer-is-not-the-builder` 的 regex 第一版在 136 份 handback 裡命中 **0** 筆，
檢查印 `0 pairs compared`、**閘門全綠**。）

⇒ gate 必須自測：
- **母體地板**：帶 `slice:` 欄的產物總數 < N → **exit 2（紅）**，不是綠
- **已知良品**：拿一條已知四項齊全的 slice 當 fixture，解不出來 = 儀器壞
- **regex 要對真語料跑**，不是對 fixture 跑

## §4 順手撿到：`plans/` 是空的

```
docs/superpowers/plans/   live: 0    _archive: 52
```

`00_roles.md:13` 寫 systems 產物 = `spec / plan / invariants.md`；
`session-role.sh:43` 叫 implementer「照 systems 的 plan（`docs/superpowers/plans/`）逐 task 做」。

**實際：零個 live plan。** 要嘛 plan 停產、要嘛已折進 spec/handback。

★ 這是**教科書級的「declared, unenforced」**：doc 宣告了一個產物，流程早就不產它，**沒有任何東西發現**。

⇒ 對 P9 的直接影響：**seam 表必須從實測產物列，不能從 doc 抄。**
抄 doc 就會要求一個流程早已停產的產物 → 100% 假紅。
⇒ **`plan` 還欠不欠 = systems 的裁定**（要嘛恢復產出，要嘛把 doc 的宣告改掉）。這是 P9 的前置決策。

## §5 成本（修正我先前的低估）

| | 成本 |
|---|---|
| **運行** | **0 token** —— 檔案存在性檢查，bash/GDScript，不是 LLM。**不製造任何喚醒** |

一次持久 session 喚醒 ≈ 整個 context 重讀，抵得過幾百次腳本執行。**P9 製造 0 次。**

## §6 明確**不做**的

1. **不驗職責/越界。** 「這個決定該不該他做」是判斷題。機器只能驗「產物在不在」。
   硬做就變成 evora 那句：**a proxy for judgement is a prose claim wearing a schema.**
2. **不驗內容品質。** 「這份 review 夠不夠嚴謹」永遠是人的活（evora 把它列為三個「只屬於人」的判斷之一）。
3. **不抄 flow-contract 引擎。** 他們是 TS engine + 45KB YAML + `schema.ts`。
   P9 是那套的 20%：**只取「產物在 seam 上必須存在」這一條**，因為我們已經有 merge 前必跑的閘位。
4. **不做 claim event。** 角色單例，搶不起來；狀態可推導。
