# HOW spec：成功的結果句要用 handler 自己的話（67 條句子今天到不了玩家）

owner: systems ｜ 2026-09-25 ｜ **player_reachable: yes**
上游：不需要新 WHAT —— blueprint 的回饋契約②（指令佇列 spec §3-5）已經裁過
「消費點必回結果句：成功一句／拒絕一句＋原因」。本票修的是**那條原則只被套用在一半的分支上**。
發現者：implementer（2026-09-25，做打聽 v1 時撞到）。

---

## ★★★§1 前提（逐字，`sim_runner.gd:566-571`）

```gdscript
var why: String = String(res.get("message", res.get("msg", "")))
state.command_results.append({
  ...,
  "text": ("%s：完成" % PlayerCommandApi.describe(name, args)) if ok
       else ("%s：被拒絕（%s）" % [PlayerCommandApi.describe(name, args),
              why if why != "" else "沒有給原因"])})
```
```
★`why` **算出來了，而它只餵給【拒絕】那一支**。
★★而同一段的註解自己寫著：「原因取自 handler 自己回的 message ⇒ 零第二份真相」
  ⇒ **那條原則只套用在一半的分支上。**
★★★母體已量（★★訂正後）：`player_command_system.gd` 有 **67 個** `"ok": true, "msg": ...` 的回傳
  （其中 33 條帶格式化參數，例：「索貢成功（獲得 %.0f coin）」「拔擢 %s 為記名成員」）
  ⇒ **全部到不了玩家**；玩家看到的是「<動作人話>：完成」。
```

## §2 做什麼（一行）

```
成功時：`why` 非空 ⇒ "%s：%s" % [describe(name,args), why]
        `why` 為空 ⇒ 維持 "%s：完成"
★保留 `describe` 當前綴（不要只印 msg）—— 前綴是玩家分辨「哪一道指令」的那一半。
★★不新增欄位、不動 handler、不動拒絕那一支。
```

## ★★★§8 第二次訂正：那個母體【不是一個檔】，而它也【不是五個檔的加總】
（implementer 2026-09-25 執行§7 硬規時抓出；systems 裁）

```
★三個量法給三個數，而三個都有解釋（他逐行 diff 過，我核過）：
  A 單行比對（ok:true 且同行有 msg）＝65
  B 括弧配對（以 `return {` 為錐）  ＝63  ← ★漏掉】 4 處 `result = {…}` 赋值型
  C 最寬（非註解行含 "ok": true）＝67  ← 與 spec §7 一致
  ⇒ 65 ∪ {:798, :1311} ＝ 67 ＝ C；67 − 4（赋值型）＝ 63 ＝ B
★★而他又抓出一件更大的：**修的地方在 `sim_runner` 的結果句組裝**
  ⇒ 它影響【每一個走消費點的 handler】，不只 `player_command_system` 那一個檔。
  實測（我獨立數過，最寬法）：player_command_system 67／interaction_system 8／
  sim_bridge 2／game_setup 1／player_trade_system 1
★★★而【五個檔加總】也不是答案：
  ·`:423 return result2`、`:439 return result` 確實**直接轉出**別的系統的 dict
    ⇒ 那些 msg 真的會抵達消費點 ⇒ 屬於母體
  ·而 `:609 _interaction.subjugate_team(...)` 的回傳**沒有人轉出** ⇒ 不屬於母體
  ⇒ ★**單檔數少算（漏轉出），五檔加總多算（收了沒人轉出的）** —— 兩邊錯的方向相反。
```

### 裁定（三條）

```
(1)★**母體的定義是【可抵達消費點】，不是【哪些檔】** ——
   而那是一個 **call-graph** 問題，grep 回答不了。
   ⇒ P2 改成印**兩個數字＋一條邊界句**：
     ①`player_command_system` 自己的成功回傳（寬視窗，今日 67）逐條列名
     ②**轉出點**（`return <別的系統的 dict>`）逐處列名 —— 今日至少 `:423`、`:439`
     ③並印一行：「本格沒數【收了但沒人轉出】的回傳」
   ⇒ ★★邊界要印出來，因為**這份 spec 本身已經在這一點上錯過兩次**。
(2)★★P2 的掃描**不得以 `return {` 為錐** —— 4 處 `result = {…}` 赋值型
   （拒絕外交提案／拒絕勒索／婉拒收留／無人可繼承）會被漏掉，
   而它們 `ok: true` 而語意是「我選擇拒絕」⇒ 正是最需要被看到的那種句子。
(3)★★★【空的才退回「完成」】那一支：實測帶話比例 ＝ 全數
   ⇒ 它今天是一條**永遠不走的分支**。
   ⇒ 保留它（防未來新增），但兩件缺一不可：
     ⓐ註解寫明**今日 0 命中**（否則它就是「從沒 fire 過而註解替它編好理由」）
     ⓑP3 改成**注入式對照**：餵一個回傳空 msg 的假 handler ⇒ 必須印「…：完成」
     ⇒ ★因為 P3 的母體今天是 **0**，不注入的話它是一格恆綠的空母體。
```

### P2 的最終形狀（三欄＋一條邊界句）

```
①`_action_registry` 的 action 數（今日 **51**）—— `:166` 這一條邊涵蓋它們全部
②**不經 registry 而可抵達的路徑**逐處列名 —— ★不是「至少」，是**機械導出的完整候選**：
   ·`choose_heir`（registry 空時的早返）、`ignore`（inline）
   ·★★**第二條分派邊** `execute_action_with_target()` 的 4 個 case：
     `recruit_named`（走 `_recruit_named_internal`）／`set_member_salary`／`equip_member`／`unequip_member`
   ·把別的系統的 dict 轉出那幾處：`_action_confirm_trade`、`_action_submit_trade_offer`
     （★列【函式名】不要只列行號 —— 行號逐樹會飄）
   ★★★**導出方法（可複核、不靠人記得）**：`func _action_*` 的定義集合 減掉 registry 值的集合
     ⇒ 差集就是「定義了但不走 registry」的那些，**而它們必然有第二條路（否則是死碼）**。
     實測（我獨立跑過）：定義 54／registry 51／**差集 3**
     （`_action_set_member_salary`／`_action_equip_member`／`_action_unequip_member`）
③`player_command_system` 自己的成功回傳逐條列名（寬視窗，今日 **67**）
★邊界句（必印）：「本格沒數【收了但沒人轉出】的回傳」
★★而邊界非印不可的理由（implementer 補的，收下）：
  本 spec 在這一點上錯過兩次，而**兩次錯的方向相反**（少算漏轉出／多算收了沒人轉出的）
  ⇒ ★★★**一個會往兩個方向錯的量，光看數字永遠判不出它在哪一邊。**
```

### ★★裁定（三條）

```
(1)★**P2 的列名格不得用關鍵字分類：67 條全部印出來、不分類**，由讀的人判。
   ★★血證：他的關鍵字表把「Team%d 接受邀請」「Team%d 拒絕邀請」誤判成中間步驟
     —— 因為【「邀請」裡面有「請」】。而它們是標準的結果句。
   ⇒ ★★★**判準要用【詞】不是【字】**（「等待」「選擇」是詞，「請」是字）。
(2)若一定要輔助標記：用**白名單詞**，且**命中與未命中都要印** ——
   ★讓誤判在卷面上看得見（他這次就是靠【印出來】才發現那兩條是誤判的）。
(3)★**沒有字面文案的要單獨成一類**：
   `r.get("msg", "")`（轉出別的 handler 的話）與 `msg`（前幾行組出來的變數）
   ⇒ ★★不分類的話，卷面上會出現兩條【讀不出內容】的列，而那看起來像抽取壞了。
```
