# HOW：單據帶上【掛單者自己申報的價格】

> systems 立 2026-09-07｜blueprint 核可（★他補的理由：B-v0 已裁「成交＝taker 吃 maker 掛單價，
> 凍結價＝商人生計」⇒ **那條 WHAT 本來就要求板上有價格欄位** ⇒ 本案＝把 B-v0 的地基提前到 ⑩ 窗，
> **零新概念、純鋪路**）

## §0 為什麼非做不可（★不是優化，是【唯一的路】）
```
套利秤的正解(blueprint 已裁)=捕獲剩餘:
   買 = (local_value − ask) × qty      賣 = (bid − local_value) × qty
★而 implementer 逐半查可行性:
   賣邊:bid 要讀【買方內部估值】= god-view          ⇒ 不可做
   買邊:ask 只有【到場】才算得出來,而 best_arbitrage_order 是【出發前】的目標選擇 ⇒ ★★也不可做
⇒ ★★★兩半在【現行資料】下都不可行 —— 所以這不是「比較好的做法」,是【唯一的做法】
```

## §1 ★這個改動【不需要任何新函式】（★最小性是它的主要優點）
```
現行:撮合當下才算
   ask = TradeValuation.ask_price(seller, ...)          = local_value(seller) × (1 − discount)
   bid = TradeValuation.local_value(buyer, res, state)  ★沒有 bid_price 函式,bid 就是買方的 local_value
                                                          (interaction_system.gd:1137 就是這樣算的)
本案:★同一條公式,改在【掛單那一刻】算,並把結果寫進單據
⇒ ★★零新公式、零新常數、零新語意 —— 只是【算的時刻】與【誰看得到】改變
```

## §4 撮合改讀板價
```
★成交價 = 板上的 maker 價（taker 吃 maker 價；blueprint 已裁）
⇒ ★★`_market_visitor_buy` / 賣方向 / 撮合迴圈不再【當場重算】對方的價格
⇒ ★★★而這順帶修掉 §3 講的那個感知不一致
★注意:零價路徑不變 —— maker 深過剩時自報 ask 本來就是 0,
   而 ⑩ 已裁【零價可成交】⇒ 三處比較閘與五處除法照舊適用
```

## §5 驗收（★每一格都要能紅）
```
①★relayed 的單【帶得到價格】:relayed entry 中 price 欄非 null 的比例
   ⇒ ★★這格【非 1.0 就是 §2 的陷阱踩到了】—— 而它是本案最容易靜默失敗的地方
②★機制斷言:同一張單,商隊【出發前】看到的價 == 它【到場】用的價
   ⇒ ★★沒有這格,「有欄位」與「有在用」分不出來
③★正數:買邊 `local_value > 板上 ask` 而被選中的單 > 0；
        賣邊 `板上 bid > local_value` 而被選中的單 > 0
   ⇒ ★★★兩邊各一格 —— blueprint 裁「兩半各自帶自己的對照」
④fp 會變（決策看得到的資訊變了）⇒ 要 before/after 對照，★不要把 fp 變了當失敗
⑤★守恆:成交價改讀板價之後,coin 與貨的總量守恆不得改變
```

## §6 誠實限
```
★relayed 價格是否該【隨 strength 失真】(而不只是過時)——本案【不做】
   理由:`distorted` 旗標已存在,而失真是另一個機制;先做【精確但過時】,
   ★★而「過時到什麼程度就不該信」交給既有的 strength/decay 機制,不新開一把尺
★★本案不動 `ask_price` 的折扣公式,也不新增 `bid_price` —— 若日後要讓買方也人格化加價,那是另一票
```
