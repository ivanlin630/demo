# 效能 arc：切法（HOW）

`from: systems`｜**WHAT**：用戶裁定 2026-08-26（TG「然後沒變數就照原路線圖」）——
★**事件比例計算五刀，目標＝零 LOD、50+ 隊。**
★★**模擬層零 LOD：計算跟隨【事件密度】，不跟隨任何觀察者；玩家遠近不分班、不刪除、禁降真實禁凍結。**

## 五刀（blueprint 轉述用戶原案）
```
① T0 事件驅動          ② 髒旗快取          ③ 掃描剪枝（換迭代源，治 team_discovered N²）
④ 錯峰                 ⑤ 隊數收斂
```

## ★★★而第一件不是刀，是【分母】—— slice 0
★**目標寫的是「50+ 隊」，而我現在不知道【現況幾隊會爆、爆在哪一段】。**
⇒ ★★**沒有一條 scaling 曲線**：
- **每一刀的效果無法歸因**（改完變快了，是這刀還是上一刀？）
- ★**「到了沒」根本回答不了** —— **那是一個不可達驗收。**

### ★★★★而 `team_discovered` 這一格特別需要先分解
```
world_state.gd:25   team_discovered: Dictionary   # int team_id → Array[int] 已知 team_id 清單
★production 讀者：**55 處、15 個檔**（★★**可重跑的指令，別目測**）：
    `grep -rno "team_discovered" scripts/simulation/ | wc -l`  → 55
    `grep -rl  "team_discovered" scripts/simulation/ | wc -l`  → 15
  （★含 `scripts/data/world_state.gd` 的定義處則為 **60 / 16**；★**未排除任何檔**。）
```
⇒ ★★★**N² 的成本不是「它存在」，是【誰在每 tick 走它】。**
★**不做熱點分解就換迭代源 ＝ 改 55 處，而其中絕大多數毫無效果** —— **成本高、風險高、收益不明。**

## ★slice 0（★純量測，零 code 改，已派 measurer）
| 要的 | 形狀 |
|---|---|
| ★**scaling 曲線** | **config-only 隊數階梯**（`perf_scale.json` 變體，★**seed 固定**），每階段報 **per-tick 中位數** |
| ★★**熱點分解** | 既有 `SimRunner.phase_timing`（★**不必新增儀器**） |
| ★★★**每段要有分母** | **該段每 tick 被走到幾次** —— **否則「這段很慢」分不出是【單次慢】還是【被走很多次】，而那兩者的刀完全不同** |

★**判準沿用 `reference_hob_perf_protocol`：比 per-tick，★不撞絕對門檻**（機器差異會製造假 reject）。

## 五刀的依賴與序（★slice 0 回來後才定死）
| 刀 | 依賴 |
|---|---|
| ③ 掃描剪枝／換迭代源 | ★**強依賴熱點分解** —— **先知道 48 個讀者裡哪幾個在熱路徑上** |
| ① T0 事件驅動 | 依賴「哪些計算其實可以由事件觸發」＝ 分解的另一面 |
| ② 髒旗快取 | 相對獨立，但**收益大小要靠曲線判**（快取沒被打到的東西＝零收益） |
| ④ 錯峰 / ⑤ 隊數收斂 | 相對獨立；★**⑤ 會改變世界內容 ⇒ 它不是純 perf 刀，驗收要含行為面** |

### ★★★★②→③ 之間插一道【量測檢查點】（R² 給 —— ★互斥風險不靠猜，靠序列裡的門檻擋）
★**風險是真的**：②髒旗快取打的是「同樣的東西不用算兩次」；③剪枝打的是「一次少看幾樣東西」——
**理論上不互斥**，★★**但③會不會變得不必要，取決於那 55 個讀者裡哪些是「資料常不變、快取吃得到」vs「每 tick 都變、只能減少迭代量」**
—— ★★★**那是量測問題不是推理問題。**
⇒ **處置**：**②落地後【重跑同一組隊數階梯】**：
- **②鎖定的熱點成本已顯著下降**（③要打的目標多數被②吃掉）⇒ ★**③縮小範圍或跳過**
- **沒有** ⇒ **③照原計畫做**
★**同一條紀律的延伸：「有資格否決一張票的量測必須擋在動工前」——這裡「動工前」變成【刀與刀之間】。**

## ★每一刀的共同驗收
1. ★**同床同 seed 同隊數階梯重跑曲線** —— ★★**報【曲線形狀】不只單點**
   ### ★★★可執行判準（R² 給，2026-08-26 —— ★取代原本「斜率變了」那句沒有定義的話）
   | | |
   |---|---|
   | **點數** | ★**隊數階梯至少 4 個點**，涵蓋現況到目標（例：`10 / 20 / 35 / 50+`） |
   | **算法** | ★**log-log 對 `(隊數, per-tick 中位數)` 線性迴歸取斜率 `k`**（`cost ~ N^k`），★★**同一組階梯、同一台機器**，比 `k_before` vs `k_after` |
   | ★**紅線** | **`k` 沒有顯著下降（降幅 `< 0.3`），或仍停在 `k ≥ 1.5` 這種明顯超線性區間** ⇒ ★★★**只是截距降了、沒治 N²** —— **照原樣回報，不得宣稱治好** |
   ★**這樣「怎麼算斜率／幾個點／多少算過度解讀」三個都有可重跑的答案，不是各自感覺。**
2. ★**`fp` 預期要連【床】＋【機制有沒有 fire】一起寫**（本日血證；純 perf 刀應 `fp` 不變，★而「不變」要是【驗過的】不是【假設的】）
3. 對帳／headless（baseline 7）／憲法閘 PASS

## ★誠實限
- ★**命令戳記 −34.5% 已入袋，不重做**（blueprint 轉述）。
- ★**B/C 重定靶結論沿用**：真 N² 嫌 ＝ `team_discovered` 成長。★★**但「哪個讀者」仍未定 —— 那正是 slice 0 要答的。**
