## §1 常駐狀態列（blueprint 裁 2026-09-10：`current_task` 的家）

```
★裁定原文：「我是誰／在哪／現在在做什麼／現在幾時」＝玩家永遠要一眼看到的四件事，
  ★★放進任何一個分頁裡都等於【每次要翻】—— 與 C1「時間控制＝UI 第一公民」同格待遇。
最小內容（四件）：
  ①附身對象名
  ②位置（格 ＋ 據點名）
  ③current_task（＋一行 intent 摘要）
  ④世界時間 ＋ 速度檔
形態：REPL 版 ＝ `status` 動詞回這四件；GUI 版 ＝ 頂欄。
```

★**HOW 補一條**：狀態列的四件事**必須來自既有查詢面**，
★★**不得為了狀態列另開一條讀 state 的捷徑** —— 否則它會變成第二個資料來源，
★★★而兩個來源必然 drift（我們今天已經在 `TextBank` 與 `merge-gates` 各看過一次）。

## §2 文字版畫面走查（★本票的主體）

```
產物 ＝ 一份【純文字的畫面模擬】：五個分頁 ＋ 常駐狀態列，
       每頁把該頁欄位【照真實查詢面拿到的值】排出來，★不是設計稿、是真的跑出來的值。
★★為什麼是文字版而不是 GUI：GUI 會把「看不看得懂」跟「好不好看」混在一起，
   而現在要判的只有前者。
★★★而它要能【重跑】：走查腳本進 repo，用戶隨時可以再看一次
   （★一次性的貼圖不算交付——下一輪改完分頁沒有人能重看）。
```

**走查腳本的三條硬規**：

```
①★只呼叫【公開查詢動詞】——不得直接讀 state。
  ⇒ 這樣走查同時是 117 分批票的【驗收工具】：接不出來的欄位會在畫面上開天窗。
②★★天窗要【印出來】，不得靜默略過：
  「〈欄位名〉：未接出（TODO:<票路徑>）」——★★★沉默的空白會被讀成「這個世界沒有這個東西」。
③★世界要是【真的跑過的】：至少推進到有東西可看（有隊、有據點、有市場單），
  ★★而不是開局第 0 tick 的空世界——空世界的每一頁都很好看。
```

## §3 用戶要簽的是什麼（★寫清楚，免得走查變成「看過了」）

```
①分頁：這個欄位放這一頁，我找得到嗎？    ⇒ 簽了才把 119 欄的【暫定】拿掉
②看得懂：這一行字我知道它在說什麼嗎？    ⇒ 看不懂的列進【人話層清單】（本票的第二個產物）
③缺什麼：我想知道而畫面上沒有的            ⇒ ★★這一格最重要，它是【補充母體】的來源
   （★★★117 那張表的母體是引擎讀了什麼，而這一格問的是【玩家想看什麼】——
     兩者的差集只有真人能給。）
```

★**不要求用戶做的**：不要他逐欄確認 119 格（★那正是 blueprint 拒絕遙控 119 格的理由）。
**他看畫面，畫面錯了他會說。**

## §6 ★★★R² 回件（2026-09-10）：兩格補完即就緒，不再送審

### (1) 走查不能是「看過了」⇒ **種一顆陽性對照給用戶抓**

R² 指出我原本的加強（每頁列天窗清單）**與 §3③ 衝突**，我同意並否決了自己：
天窗清單會把注意力鎖在**我們已經知道缺的東西**，而 §3③ 要的正是**我們不知道缺什麼**。

**改採的形狀（R² 提）**：

```
走查跑給用戶看之前，★【故意種一顆錯】——某頁漏印一個原本該有的欄位，
或某隊的 current_task 印成一個不存在的字串。
★★若那次走查用戶沒有指出它 ⇒【那次「簽了」不算數，要重來】。
   ——★★★不是因為他簽的內容有問題，是因為【這次驗證沒有證明他真的在看】。
```

★**我加一條 R² 沒寫、但我認為必要的**：

```
★★【要告訴用戶「這一份裡種了一顆錯」，只是不說在哪】。
理由：不說有，是拿他當受試者；說了有、不說在哪，★★★鑑別力一點都沒少
  （他仍然得真的逐頁看），而它從【測試一個人】變成【一起玩一個找碴遊戲】。
⇒ 這也讓「沒抓到要重來」這件事在事前就講好，不是事後才搬出來。
```

★**這正是今天全天在用的同一招**（`failure-feedback-coverage` 的假選項要具名紅／
「把 record 那行拿掉這格必須紅」）——**只是這次的執行者是人不是腳本**。
★★而它比逼問「缺什麼」好，因為**它不要求用戶自己生成問題**，
只要求他對**已經放在眼前**的一個具體錯誤有反應 ⇒ **被動偵測，門檻低很多**。

### (2) ★★狀態列第④件事：**兩半都讀不到**（R² 查實，比我猜的更缺）

```
player_query_api.gd 全部 16 支公開動詞 ＋ player_api_mapper.gd：
  current_tick／world_time／"tick"                 ⇒ ★零命中
  speed_tier／speed_mult／sim_speed／game_speed     ⇒ ★零命中
（sim_runner 的 time_speed_mult 是【日夜週期對移速的物理乘數】，
  與「玩家選的播放速度檔」是兩個概念，★★不能借。）
```

★**而速度那一半的缺席不是意外，是票① 自己選的設計**：
「不在 `sim_runner` 加狀態，推進幾步留在呼叫端」
⇒ **目前沒有任何地方持久記著「現在的播放速度是多少」**。

**補法（R² 設計，我認領到本票）**：

```
①世界時間  ⇒ player_query_api 加一支薄 wrapper 讀 state.world.current_tick（★不涉票①的顧慮）
②速度檔    ⇒ ★記在【呼叫端／REPL 自己的 session 狀態】，★★不進 WorldState／sim_runner
             （REPL 知道自己上次收到「推進幾步」的指令）；
             player_query_api 加一支薄 getter 讀那個 session 變數 —— ★★★讀的是呼叫端的記憶，不是 state。
⇒ 兩條規矩同時守住：sim_runner 照舊什麼都不記（不多一個真相源）；狀態列也真的有東西可查。
★認領：【本票】（票① 已 merge，為兩支薄 wrapper 重開一張票不划算）。
★★而【不得默認「查詢面已經有」】——現在沒有，走查腳本第一次跑就會卡在這裡。
```

### (3) 驗收④的成對對照：R² 判**落在真行為區間**

```
我原本的疑慮（「這只證明走查腳本會處理 null」）被駁回，理由成立：
★它真正在防的是【畫面接的是快照／快取，不是即時查詢】——

  ★★畫面仍會顯示舊值 ⇒ 抓到的不是「null 沒處理好」，是【走查根本沒在跑真查詢】。
★★★與 §2③「世界要是真的跑過的」同一個精神。
```
