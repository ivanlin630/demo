## §1 缺陷

```
faction_ai_system.gd:1218
  func _evaluate_all_body(state: WorldState, _team_ids: Array) -> void:
                                              ↑ ★底線前綴＝刻意不用
  函式體 392 行｜`_team_ids` 出現 2 次，★都不是迴圈
  :1226  for fid in state.factions:     ← ★★它跑【全世界】
```

⇒ **呼叫端傳一批隊進去，而它不看** ⇒ 在散相位之下，它會**每一批都重跑整個世界**
（60 批 ⇒ 每小時 60 次，現在 1 次）⇒ ★**不是漏做，是重複執行**：正確性與效能雙壞。

## §2 修法形狀（★改接線不改數值）

```
讓 `_evaluate_all_body` **真的以傳入的 team_ids 為母體**：
  ・派系層的工作，要由【這一批隊所屬的派系】驅動，而不是 `for fid in state.factions`
  ・★同一派系在同一小時內【不得被驅動兩次】—— 那是本票的正確性核心
★★而「怎麼從一批隊得到該做的派系工作」是實作決定，spec 不指定資料結構。
★★★硬規：**簽章不得再說謊** —— 參數要嘛真的被用，要嘛拿掉並把 `SYSTEMS` 的 shape 改成 world。
```

## §3 驗收（★兩格，缺一不可）

```
①★**世界指紋逐字相同**（世代 7，expect 仍是 763e9ee91e7c91807b9a625d60362650）
  —— 本票【不改世界】：它改的是「誰驅動它」，不是「它決定什麼」。
  ★★指紋一變 ⇒ 本票的前提（純接線）就破了，那要回頭查，不是改指紋。
②★**每派系每小時恰好一次**：加一格 tap 計數（派系 id × 小時 ⇒ 驅動次數），判準＝**恆為 1**
  ★★★這一格是為【未來的散相位】準備的：今天不散相位時它也該是 1，
    而散了之後它【仍然要是 1】—— 那正是「重複執行」這個危害的直接守衛。
```

## ★★★§3b 補充（blueprint 2026-09-23）：為什麼指紋【必須】一樣，以及它的一個缺口

```
blueprint 的理由（我收）：本票只是把迴圈限到【被給的那一批】，
而今天沒有散相位 ⇒ **批次＝全部隊** ⇒ 迴圈覆蓋同一個集合
⇒ 行為零改變 ⇒ ★fp 逐字相同、**不推世代**（散相位是下一張票才推世代 8）
```

★★**而這個論證有一個缺口，systems 補：**

```
同一個【集合】不代表同一個【順序】。
舊實作：`for fid in state.factions`        ⇒ 依 Dictionary 的鍵序
新實作：由 team_ids 推出該做的派系  ⇒ ★順序可能不同
⇒ ★★若派系層有任何決策依賴【迴圈順序】（先來先拿的資源、先到先結盟…）
  ⇒ 集合一樣、順序不同 ⇒ **fp 仍然會變**
```

⇒ ★★★**硬規（本票）**：新實作必須【保住與舊實作相同的派系迭代順序】。
  ★否則 fp 那一格會紅，而它紅的原因是【良性的】—— ★★**而那種紅最危險**：
  下一個人會把它讀成「指紋本來就會變」然後把它改掉，而真正的回歸就從那一刻隱形。

## ★§3c 守衛②的陽性對照（blueprint 令）

```
注射：讓某一個派系在同一小時被驅動【兩次】
預期：那一格必須讀到 **2**（不是「有紅」，是【讀到 2】）
★理由：這一格今天是恒真的（不散相位本來就該是 1）
  ⇒ ★★沒有陽性對照，它就只是一句【看起來很安心的話】
  ⇒ ★★★有了對照，它才是【已經證明會動的儀表】
```
