# stock vs flow：同一把尺要分得出【流】和【存量】（HOW）

`from: systems` ｜ `blocked-by: means-end-brick`（形狀標記先落地，這票才有東西可接）

## 病
`DiscountedFlow.flow_utility` 假設 `gain_daily` **在整段 `h` 天都持續**（`pv()` ＝ `flow·δ(1−δ^H)/(1−δ)`，`discounted_flow.gd:48-52`）。
★**對再生資源成立；對存量資源不成立** —— `ore_iron`/`gem` **窮盡 grep 零 regen 路徑**，**採完就沒**。

**⇒ 系統性高估，且不對稱**（reviewer 自推 PV 證明）：**只會高估或打平，不會低估。**
★**誤差比值 ＝ `gain_daily × H / S`** —— **`S` 越小越糟**（★**哪個資源最糟需要真實採集率，留給量測，不推理**）。

## 修法（★改接線，不改數值 —— 零新常數）

### ★★★2026-08-26 訂正：**我原本寫的公式是【對稱】的，而對稱的那個版本【什麼都不會改變】**

**我原本寫**：`H_stock = min(H_eff, S / maxf(gain_daily, 0.001))`，**然後整條算式都用 `H_stock`**。
★**implementer 照字面實作，測試當場逮到它是 no-op**（`1.0000 < 1.0000` 兩條 FAIL）。

★**根因（而且答案就寫在我引用的那個檔的註解裡）**：`discounted_flow.gd:74-77` 白紙黑字寫著
> **「分母改用 `pv(daily_need,…)` ⇒ utility ＝『這個選項相當於幾倍餬口』，★δ/H 在分子分母相消」**

⇒ **把視野縮短，分子分母一起縮 ⇒ 比值不動。** 既有測試 `gate6 視野長短不改變倍數` 就是這條性質的守衛。
★★**我把 `H` 塞進一個【`H` 會相消】的比值裡，然後宣稱它會改變估值。**

> ★**精確一點（我核過代數，免得下一個人以為它完全惰性）**：
> `ratio = [gain·wait_mult − baseline]/need − cost/pv(need, δ, h)`
> ⇒ ★**`h` 只透過【`cost` 項】和【`h ≤ 0` 那道 gate】起作用，在 gain/need 這一項上完全相消。**
> ★★**而那更糟**：對稱版的 `H_stock` **會動到數字**（透過 cost 項），**但動的理由跟「礦會挖完」毫無關係。**

### ★修法（採用 implementer 的形狀，systems 裁定 2026-08-26）：**不對稱視野**

| | 用哪個視野 | 為什麼 |
|---|---|---|
| **分子**（這個來源拿得到的流） | ★`H_stock = min(H_eff, S / maxf(gain_daily, 0.001))` | ★**礦會挖完** |
| **分母**（我還是要吃） | `H_eff` | ★★**人不會因為礦挖完就不用吃** |

★**這不是為了通過測試而湊的形狀，它在模型上是【精確】的**：
存量 `S` 以 `gain_daily` 開採，恰好在 `S/gain_daily` 天耗盡 ⇒
**該來源的真實折現產出 ＝ `pv(gain_daily, δ, H_stock)`** —— **分子是精確值，不是保守估計。**
⇒ **既不高估（原病），也不低估。**

★★**而且不對稱在這個函式裡不是新東西**：`wait_mult` 只乘分子、`cost` 只在分子
（`discounted_flow.gd:79-81`）—— ★**分子分母本來就代表不同的東西：「這個選項給我什麼」vs「我需要什麼」。**

### ★★★這次的教訓（比公式本身重要）
我用「**與 `horizon_eff` 完全同構**」當理由。**形狀確實同構** ——
★**但我沒有檢查【被同構過去的那個位置】的代數性質**：`horizon_eff` 在它原本的位置上是承重的，
**而我搬去的那個位置，`H` 會相消。**
> ★★**「同構」要驗的不是「形狀一樣」，是【它在新位置上還起不起作用】。**
> ★★★**併我上一版已經立的那半**：**同構不該只抄公式，連護欄也要一起抄** ——
> **這次是更前面一步：★連【它在原處為什麼是承重的】都要一起抄。**

（原本的 epsilon guard 論述仍然成立，照留：）
★★**`maxf(gain_daily, 0.001)` 不是新增的謹慎，是【同構的一部分】**（R² 抓到，2026-08-25）：
**`horizon_eff` 自己的分母就有 `maxf(-post_action_net_flow, 0.001)`（`discounted_flow.gd:44`）。**
`gain_daily = 0` ⇒ `S/0.0` ＝ `inf` ⇒ `H_stock` 失去上界 ⇒ **病原封不動，只換了個入口。**

## ★★接口：**兩個入口，不是一個 default 參數**
**禁**：`flow_utility(..., source_stock: float = INF)`
★**理由**：**新呼叫端忘記傳 ⇒ 存量被當流 ⇒ 靜默高估。**
（★**對照組**：`reason: String = ""` 的 default **208/208 呼叫點沒人用過** ＝ 純負債；
**但這裡的 `INF` default 會被 4 個現有 caller 真的用到** ⇒ **收益是真的、風險也是真的** ⇒ **兩者都要，就別用 default。**）

★**改用**：
- `flow_utility(...)` —— **再生流**（現有 4 個 caller 不動）
- ★`stock_utility(...)` —— **有限存量**，**`source_stock` 必填**

> ★★★**忘記選 ＝ 沒有函式可呼叫。用【入口】區分，不用【參數值】區分** ——
> **同 `record_driver` 的 `kind`：用出處分類，不用字面分類。**

## 驗收（★集合型優先）
1. ★**`stock_utility` 的呼叫端集合 ＝ 形狀標記為 `stock` 的資源集合**（兩邊互為對方的 falsifier，**任一邊多出成員 ＝ 紅**）
   ★★★**形狀標記側【必須】＝ 靜態 grep `AcquisitionPaths.SHAPE_TABLE` 的內容，★不得改用 runtime 觀測值。**
   ★**理由（R² 要求寫死，2026-08-25）**：`SHAPE_TABLE` 是**寫死在原始碼的靜態表，現有 4 個成員**
   （`ore_iron`／`ore_gold`／`ore_silver`／`gem`）⇒ ★★**它有一個恆為 4 的【非零地板】**
   ⇒ **呼叫端若是 0（又一次「磚落地沒接線」），會立刻對不上（`4 vs 0`）⇒ 紅。**
   ★★★**若改讀 runtime 觀測**（例如接 `driver_ledger`），**一次沒觸發礦物短缺情境的跑 ⇒ 兩邊都空 ⇒「互為 falsifier」形同虛設**
   —— **那正是這輪一路在打的死水／母體塌陷覆轍。**
2. **`flow_utility` 的 4 個既有 caller 行為 byte-identical**（此票不得改再生路徑）
3. **`S / gain_daily ≥ H_eff` 時 `stock_utility ≡ flow_utility`**（★**存量夠撐滿視野就該打平** —— 這是 reviewer「只高估或打平」的直接可測推論）
   ★★**這一條【單獨】不夠**：對稱版的 no-op 公式**也會通過它**（因為它恆等）⇒ **必須與 3b 併看。**
3b. ★★★**存量不足時必須【嚴格低於】，而且【連續】**（新增 2026-08-26，補上 ③ 的另一半）：
   - `S/gain_daily < H_eff` ⇒ `stock_utility < flow_utility`（**嚴格**，不是 ≤）
   - **存量越少值越低**（1 天 < 3 天 < …）—— ★**連續，不是一刀切**
   - `gain_daily = 0` ⇒ **不得產生 `inf`/`NaN`**（epsilon guard 的陽性對照）
   ★**理由**：③ 是「不該動的時候不動」，3b 是「該動的時候真的動」——★★**只有前者的閘，恆真式一路綠。**
