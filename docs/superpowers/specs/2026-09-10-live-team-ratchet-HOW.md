## ⓪ 這張票的判斷基礎（★兩句，缺一不可）

```
①★「用 `has()` 當存活守衛」是這個 codebase 的【預設寫法】，不是三次個案（87%）。
   ⇒ ★★而一旦是預設寫法，**逐處修就是錯的處置**：改完 75 處，
     下一個人寫第 76 處仍然會寫 `has()`，因為那是最省力的路徑。
②★★★而那 75 處【不是 75 個 bug】：一個 [L] 只在【殭屍窗打開】時才咬人，
   而今天量到殭屍窗 ≒1 tick、自然世界滅團 ≒0（23 天）、真正的消失走【合併】。
   ⇒ **「這裡到處是一個【在特定條件下】才錯的習慣」，不是「這裡到處是 bug」。**
⇒ ★所以：**不專案化、不逐處修**，改【換掉預設路徑】＋【棘輪擋新增】。
```

★**blueprint 的一句話比我原本的說法好記，收錄**：**「改人不如改路。」**

## ① 修法（三件，★第一件是重點）

```
(1)★**便捷式**：`WorldState.live_team(tid) -> TeamData`（不存在【或】pending_erase ⇒ 回 null）
    呼叫端：`var t := state.live_team(tid)`
            `if t == null: continue`
    ⇒ ★★**比 `has()` ＋ `[]` 兩步【更短】** —— ★★★**寫法要贏在人體工學，不贏在紀律。**
    ★而既有的 `is_live_team(tid) -> bool` 保留（純布林那一類仍然需要它）。
(2)★★**新增行棘輪閘**：新寫的「`state.teams.has(` ＋ 後續對該隊動作」⇒ **亮警**
    ⇒ 存量 86 處進 **baseline 豁免**（沿用 site-freeze 慣例）。
    ★★★而 baseline 的形狀照既有慣例：**每一列帶 owner ＋ 到期／觸發條件**（born-with 過期紅）——
      ⇒ ★這裡的「觸發條件」＝**那一行被碰到時**（on-touch 就要轉），
        而不是一個日期（★★日期會過期而沒有人處理，觸發條件不會）。
(3)★**存量 on-touch 順手轉**，★★**永不專案化**（blueprint 明文）。
```

## ② 驗收

| # | 格 | 判準 |
|---|---|---|
| ① | **便捷式行為** | `live_team` 對【正常隊】回物件、【pending_erase】回 null、【從不存在】回 null；★三格都要（前兩格回不同答案而理由不同，只驗第三格會漏掉殭屍窗那格） |
| ② | **★棘輪會咬** | 新增一行 `state.teams.has(x)` ＋ 後續動作 ⇒ **具名亮警**；★★移除後回綠 |
| ③ | **★★不得亂咬存量** | 那 86 處（baseline）**不得**亮警；★★★而 baseline 的每一列要能對回 `teams-has-callsites.tsv` |
| ④ | **★★★不得亂咬 [G] 類** | 純存在守衛（`has()` 之後不再碰那個 team）**不亮警** —— ★而這一格是本閘最容易做錯的：判準若只看 `has(` 就會把 [G] 也咬進去 |
| ⑤ | **fp 不變** | 本票**只加介面＋加閘**，不改任何既有呼叫點 ⇒ fp 必須完全相同（★★而依界限第十八條，同時附一格行為證據：既有測試全綠） |

★**誠實限**：④ 的判準是【語意】的機械代理（「守完之後有沒有再碰」）
⇒ ★★它會有偽陽／偽陰，★★★**而偽陽的處置是【加進 baseline 並寫理由】，不是放寬判準**。

## ③ 這張票【不做】

```
①★不改那 86 處任何一處（存量 on-touch，永不專案化）
②不動 `teams_pending_erase` 的生命週期
③★★不把 `state.teams` 改成私有／改名 —— ★★★那是更大的手術，

```

## ④ ★為什麼這張票值得現在做（★序的理由）

```
今天量到：自然世界【幾乎不滅團】⇒ 殭屍窗幾乎不開 ⇒ 那 75 處【現在】幾乎不咬人。
★★而攻擊門那張會讓世界【開始有滅團】——
★★★**那一天，這 75 處會從「幾乎不開的窗」變成「常常開的窗」。**
⇒ 所以便捷式與棘輪【做在攻擊門之前比之後便宜】：
  ★之前做 ＝ 新寫的 code 一開始就走對的路；
  ★★之後做 ＝ 攻擊門期間新增的每一處都要再回頭轉一次。
```
