## §1 病：**批一①的雙胞胎**

```
goal_resolver.gd:616   const SEEK_TILE_RANGE: int = 30   # TEST VALUE — belief-reachable 上界
用點 :703 / :951       find_nearest_terrain_tile(state, team, terrain, SEEK_TILE_RANGE)
實作 :990-1004         d = _hex_dist(team.tile_pos, t.tile_pos)；`if d > max_range: continue`
```

★「這支隊願意/能夠去多遠找地形」對**所有隊**都是同一個 `30` **格**。
★★而**真值今天才長出來**（批一① 已 merge）：`tiles_per_day = TICKS_PER_DAY / _move_cost(state, team)`
⇒ 重載疲勞隊實測 **2.00 tiles/day**、滿編坐騎隊 **12.10** ⇒ **同樣 30 格＝ 15 天 vs 2.5 天**。
⇒ ★★★**同一個量在兩層各有一份**（(ii) 型），而這一次的第二層**是我們自己昨天接上的** ——
   這是 blueprint 那條「**舊 code 誰在用這個量的佔位版？**」的**第一個回頭命中**。

⇒ **現況不是「每支隊都搜尋 30 格」，是「沒有任何隊有搜尋上界」。**
⇒ ★★所以本票**不是**「把一個平版數字換成真值」，而是**第一次讓這個上界真的存在** ——
   ★★★**那是行為改變，不是接線**。

★**這是「被初始參數凍結的閘」的【反向】版本**：
「空家不返」是**門檻遠低於世界的量**（800 vs 40）⇒ 閘永遠不擋；
這一條是**門檻遠高於世界的量**（30 vs 全圖 28）⇒ ★**閘一樣永遠不擋，只是從另一邊**。
⇒ **同一族、兩個方向**，而**兩次都要先算可達區間才看得出來**（界限第八條）。

★★**因此本票需要 blueprint 的 WHAT 確認才能 dispatch**（不只是 R²）：
問題不是「要不要用真速度」，而是「**搜尋範圍到底該不該是一個限制**」。
（★我的看法：該是 —— 一支走不動的隊「看得到全圖並決定去對角線採木」正是

## §2 ★★★單位鐵則（本票最容易做錯的一格）

```
`SEEK_TILE_RANGE` 的單位是【格】,而真值 `tiles_per_day` 的單位是【格/天】
⇒ ★不能直接代 —— 直接代會把「30 格」變成「30 天的路」或反之。
★★正確形狀：先決定【願意花幾天】,再乘上那支隊的真速度：
     seek_range_tiles = int(round(SEEK_DAYS × tiles_per_day(state, team)))
   其中 `SEEK_DAYS` 是【設計選擇】(世界答不出「該找幾天」) ⇒ ★它留成具名參數,不是死常數。
★★★而 `SEEK_DAYS` 的預設【要從現況導出,不要發明】：
     中性隊實測 4.20 tiles/day（批一①卷面）⇒ 30 格 ÷ 4.20 ≈ 7.1 天
     ⇒ 預設 `SEEK_DAYS = 7.0` ⇒ ★中性隊的搜尋半徑【幾乎不動】,而快慢隊分開
     ⇒ ★★這讓本票是【差異化】不是【全域放大/縮小】—— 兩者的世界後果完全不同。
```

## §3 修法

```
①`goal_resolver` 新增 `SEEK_DAYS: float = 7.0`（★具名參數,註解寫明它是設計選擇＋7.0 的來歷）
②兩個用點（:703 / :951）改成傳【逐隊算出來的格數】
   ⇒ ★用批一① 已經抽好的 static 核心（`move_cost_pure` 那條路）,不要重算一份物理
     （★★「估算器禁手抄物理」—— 而批一① 正是為了這件事把核心抽成 static 的）
③`SEEK_TILE_RANGE` ★連常數一起刪,只留一行註解說明舊版與病。
④★★★下界保護：`maxf(seek_range, 1)` —— 一支速度被 clamp 到最低的隊【仍然要看得到隔壁格】,
   否則本票會把「慢」變成「瞎」,而那是【新的病】不是【修好的舊病】。
```

## §4 驗收

```
①【腦看得見】同世界：慢隊的 seek_range【變小】、快隊【變大】,中性隊【幾乎不動】
   ★★★可達區間【已算】（界限第八條）：tiles_per_day ∈ [2, 18] ⇒ seek_range ∈ [14, 126]（SEEK_DAYS=7）
     而全圖 hex 距離上限 ＝ 28（radius 14）
     ⇒ ★**快隊那一端（≥28）等於沒有上界 —— 它在任何窗都量不出差別**，
       ⇒ ★★所以「快隊變大」**不能當驗收格**（它結構性不可觀測）。
       ⇒ ★★★真正可觀測的只有【慢隊那一端】：`tiles_per_day < 4` 的隊 seek_range < 28
         ⇒ **它們第一次真的被限制** —— 驗收要掛在這裡，並【具名列出】是哪幾隊。
②【穿透到結果】不只是半徑變了：★慢隊【找到的目標】要與舊版不同（至少一支隊的 target 改變）
   ⇒ 沒有這格,本票可能只是改了一個沒人在用的上界。
③★★【咬不咬人】raw / eff / gate 三數（接線票必備格）：
   raw ＝算出來的 seek_range 變了幾隊（斷言掛這裡）
   eff ＝真的改變了 `find_nearest_terrain_tile` 回傳值的隊數（只印不斷言）
   gate＝因此改變了 goal/task 的隊數（只印不斷言）
   ★誠實限：短窗下 eff/gate 只能回答「沒翻轉」,不能回答「不咬人」。
④【同源】`tiles_per_day` 的計算點在該函式內【只有一次】（結構檢查，成對對照先數到 2）。
⑤★★★【不把慢變成瞎】速度最低的隊 seek_range >= 1,且床要【具名印出】那些隊,
   不要只印一個 min 值。
```

★誠實限：
1. `find_nearest_terrain_tile` 是**直線距離**（`_hex_dist`）不是路徑距離 ⇒ 本票**沒有**讓它變準，
   ★只是讓**上界**與那支隊的真速度同源。**別讓下游把它當成路徑可達性。**
2. 本票**不動** `:996` 的全 tiles 掃描（那是 perf 面，且 `gate-ok` 已標）。
