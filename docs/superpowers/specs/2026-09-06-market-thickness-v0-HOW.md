## §2 ★★★紅線推導出的**第二件事**（★六件套沒展開，而它是同一條線）
```
★用戶紅線:外地掛單者【不在場】成交 ⇒ 錢【不得】直接進其 team.coin ⇒ 待領【款】帳
★★而【到期退貨】是同一個形狀:賣家不在場,貨【也不得】直接回其 team.resources
   ⇒ ★★★否則就是【貨物瞬移】—— 同一條紅線,換一個方向
⇒ 所以 v0 要的是【兩個待領帳】:
   ①待領款(成交後,買家的錢躺在市場等賣家來領)
   ②★待領貨(到期後,escrow 的貨躺在市場等賣家來領)
⇒ ★而它們是【兩種資產型態】⇒ 照意圖帳:43「資產配念頭」⇒【各自】要配三件套
```

## §3 動作（v0 六件 ＋ §2 推導的第七件）
```
①掛單權 = 到場(非 owner-only)      —— 板 = 據點公共設施
②★押貨 escrow:掛賣單即【交貨入市場保管】—— ★★而這改變了 §1 的權威關係:
   板上【真的有貨】了 ⇒ 【權威從 active_orders 移到 tile】,而 active_orders 變成賣家自己的存根
   ⇒ ★★★這一格要寫死,否則【鏡像與實貨會分歧】,而分歧時沒有人知道該信哪個
③成交 = 事件驅動,taker 吃 maker 的【掛單價】(固定價;★禁自動改價 —— 那是 v2 的階梯掛單)
④待領【款】帳(★紅線)
⑤★待領【貨】帳(§2 推導,到期退貨用)
⑥領取念頭 ×2(款/貨各一)：照意圖帳:43 三件套
   ①腦欄位(ctx 可讀:★自己的單據【天生在手】——不需要情報系統)
   ②秤上 option(價值 = 額 × 距離/時間折現)
   ③★行為級驗收(控制床 ＋ 野外率;「機制存在」不算數)
⑦到期 = 用既有 `expire_tick` 欄
```

## §4 ★★尺寸與砍法（blueprint 給的優先序，我補一句理由）
```
★估:>1 slice。砍法優先序(blueprint):【買單押錢半邊後補】>【到期退貨簡化】>★待領帳【不可砍】
⇒ ★★而我補的理由:待領帳是【紅線本身】,砍掉它 v0 就【違憲】——
   ⇒ 那不是「功能少一點」,是【這一刀不能出】
★★★而「到期退貨簡化」若真要砍,簡化的方向是【貨留在 escrow 不動、只標到期】
   —— 而【不是】讓貨自己回家(那就是瞬移)
```

## §5 驗收
| # | 判準 |
|---|---|
| 1 | ★**紅線**：外地賣家成交後，**`team.coin` 不變**、而**待領款帳 +額**（★★逐筆對帳：買家 −額 ＝ 待領帳 +額，**零蒸發**） |
| 2 | ★★**到期**：`expire_tick` 到 ⇒ **貨不回家**，落在**待領貨帳**（★同上逐筆對帳） |
| 3 | ★★★**念頭真的會被想到**（意圖帳:43 三件套的第③）：**控制床**（構造一個有待領款的隊 ⇒ 它的 option 清單裡**出現領款**）＋ **野外率**（90 日跑：★**有多少隊真的去領了**）——★**「機制存在」不算數** |
| 4 | ★**escrow 守恆**：掛單 ⇒ 賣家 `resources` −qty ／ tile escrow +qty；成交 ⇒ escrow −qty ／ 買家 +qty（★★全程 `CoinAudit` 與物資守恆不破） |
| 5 | ★★**鑑別力**：把待領帳拿掉（錢直接進 `team.coin`）⇒ 判準 1 必須**紅**；★★★把領款 option 拿掉 ⇒ 判準 3 的**野外率必須掉到 0**（而不是「變少」） |
| 6 | ★**全量暫態可觀測性**：掛單／成交／待領餘額／領取／到期 **五個都要 tap**（★★而「待領餘額」是**存量**，要與流量分開印 —— 今天已經有人在這格上栽過） |
| 7 | determinism 三跑（★在不會被編輯的樹上）＋ 全部 merge-gate |
