```

   （emit 一次，同時進匯流排與玩家佇列）
   ⇒ ★**不准任何地方繞過 emit 直接寫玩家佇列** —— 否則變成第二本帳
   ⇒ 驗收 P3 用 grep 斷言寫入點只有一處

   ⇒ 自家隊是**唯一的具名例外**（self-knowledge；reviewer 2026-09-23 已核過這個框架）
   ⇒ ★★★過濾器的**預設是「不給」**，例外是**白名單**、逐條具名（★不是黑名單）
```

## ★★★§3 壽命夠不夠，已經有一條斷言在守 —— 擴它，不要新寫

```
★為什麼 `TICKS_PER_HOUR` 夠：`sim_bridge.gd` 每次 `tick_step()` 上界是 `STEP_TICK_BOUND`
  （＝`TICKS_PER_HOUR`），而 `_process()` 在每次 step 之後跑 ⇒ 讀者每 ≤60 tick 讀一次
⇒ ★★所以「推進一天」是 **24 次 step**，不是一次 1440 tick ⇒ 壽命一小時剛好夠
⇒ ★★★**而這是兩個常數之間的隱藏依賴，而我們【已經釘過它】**：
  command-queue 那一票的 P14b 斷言 `RESULT_TTL_TICKS >= SimBridge.STEP_TICK_BOUND`
  ⇒ **把新佇列的 TTL 加進【同一條】斷言**，不要另寫一條
  （★兩條斷言守同一個關係 ＝ 兩份真相，而其中一條遲早不會跟著改）
```

## §4 驗收（★負對照與判準寫在同一行）

```
P1 [自家隊看得到] 造出五種事件（離隊／死亡／成年／招到／挨餓）⇒ ★事件流**五種都出現**
   ｜負對照：拿掉任一種 emit ⇒ 必須紅｜★★母體地板：那一輪要真的發生過那五種（逐種斷言 ≥1）
P2 [★★★整天不漏] 按空白鍵推進**一天**（`TICKS_PER_DAY`，★用常數）
   ⇒ 事件流要含**那一天每個小時**發生的自家事件（**不是只有最後一小時**）
   ｜★陽性對照（blueprint 給的）：**把讀點搬到 step 尾** ⇒ **這一格必須紅**
   ⇒ ★★它守的是【讀者在逐 tick／逐 step 的迴圈裡讀】，不是「事件有沒有被 emit」
P3 [單一寫入點] grep 斷言：玩家佇列的寫入**只在 `WorldEvents.emit` 內**
   ｜負對照：在別處加一行直接寫 ⇒ 必須紅
P4 [過濾用同一支函式] grep 斷言：過濾呼叫的是 NPC 決定 belief 用的那一支
   ｜負對照：另寫一條「玩家專用」的可見性規則 ⇒ 必須紅
P5 [★他隊不外洩] 造一件【附身者看不到】的他隊事件 ⇒ 事件流**沒有它**
   ｜負對照：把過濾拿掉 ⇒ 必須紅｜★★母體地板：那一輪要真的有一件看不到的他隊事件
P6 [離隊帶原因] 離隊事件的人話**含原因**｜負對照：把原因欄拿掉 ⇒ 必須紅
P7 [TTL 依賴] 新佇列的 TTL 併入**既有那條** `>= STEP_TICK_BOUND` 斷言
   ｜負對照：把上界改成 `TICKS_PER_HOUR * 2` ⇒ 必須紅
P8 [fp] ★新佇列進 fp ⇒ **canon 多一行** ⇒ 基準會變，而**重設與改動要原子落地**（今天踩過一次）
P9 [電池] merge 前全電池｜★★交玩前照 merge 檢查表第 8／9 步
```
