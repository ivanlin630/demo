# HOW spec：相位樹 —— ★**在有父子關係之前，「下一個要修誰」這個問題無法回答**

owner: systems ｜ 2026-09-10 ｜ 觸發：`[FaiPhase]` 印全之後的第一份彙總（implementer 自己先擋掉了錯誤讀法）

## ① 問題（★不是「表不夠大」，是【表的形狀】不對）

```
印全之後的前三名（650 筆 spike 樣本，總計）：
   loop1.factions 404.9s ／ unified.rank 369.8s ／ loop1.assign_tasks 361.7s
   （gather.home_food 88.1s ＝ 我們剛修掉的那一筆）
★而 `assign.leader_unified`（206s）／`assign.members`（155.7s）幾乎確定是
  `loop1.assign_tasks` 的**子相位**，`gather.*` 也被更外層包著。
⇒ ★★**「總計」那一欄是巢狀的** —— 把它們加起來會超過 100%。
⇒ ★★★**用它排序＝把父親和兒子放進同一個排行榜** ⇒ 挑出來的「最大的那個」
   可能只是【某個父親】，而真正的錢在它的某一個兒子身上（或反過來）。
```

★**所以本票不優化任何東西**：它讓那張表**變得可以排序**。

## ② ★★修法（★**不碰計時熱路徑**）

```
現況：`_fai_pht(name, t0)` ＝【檢查點式】計時 —— 累加「距上一個檢查點的時間」到一個平表
     （`faction_ai_system.gd:822-831`），**沒有 enter/exit，也就沒有天然的堆疊**。
⇒ ★所以【不要】改成 enter/exit 包裹式：那會動到每一個呼點、動到熱路徑，
  ★★而我們要的資訊【是靜態的】——「哪個相位包在哪個相位裡」是**寫 code 的人知道的事實**，
    不是需要 runtime 去發現的東西。
★★★做法：**一張具名的父子表 ＋ 一支閘**
  ①`const PHASE_PARENT := { "assign.leader_unified": "loop1.assign_tasks", ... }`
    （根相位的 parent 寫 `""`）—— ★放在 `_fai_pht` **旁邊**，兩處一起看得到。
  ②輸出多一欄【淨值】：`self_us = total_us − Σ(直接子相位 total_us)`
    ⇒ ★排序改用 **self_us**；★★**total_us 仍然印**（父親的總量本身有意義）。
  ③★★★**閘**：任何出現在 `_fai_ph` 而**不在** `PHASE_PARENT` 裡的名字 ⇒ **具名紅**
    ⇒ 這就是防手抄表漂掉的機制（★沒有這一條，表會安靜地過期）。
```

## ⑥ ★★★R² 回件（2026-09-10）：**補一個第三種成因** —— 而它比我寫的那兩種更難認

### (1)(3) 過：手抄表沒有低估／序的判斷成立

```
(1)★R² 驗過 `_fai_pht`：純檢查點累加、無堆疊無進出配對
  ⇒ ★★「誰包著誰」**不是 runtime 資料裡本來就有、只是沒被讀出來的東西**，
    是純粹的【呼叫點位置關係】⇒ 自動導出要做全域呼叫圖分析
  ⇒ ★★★**這不是「懶得做」，是這個計時模型的形狀本身不支援** ⇒ 手抄＋未登記則紅是合理的次佳解。
(3)★序：今天連續四張票（前移濾網→位置對快取→bounded Dijkstra→home-granary）
   **每一版都先挑了一個看起來最大的去優化，而前三個診斷後來都被推翻**，
   只有第四版（讀既有 log 而不是猜）一次就對 ⇒ ★★**這不是抽象論證，是今天的紀錄**。
```

### (2) ★★★`self_us` 為負的**第三種成因**：**這個相位名本身代表不只一件事**

```
★`_fai_pht_s` 的註解：「DecisionContext.gather 等 **static callee** 標相位用」
  ⇒ `gather.*` 是從 `DecisionContext.gather()` **內部**累加的，
  ★★而 `gather()` **不是只被 `loop1.assign_tasks` 這一條路徑呼叫** ——
    同一個計時鍵的累加時間**可能來自好幾個不相干的外層 context**。
⇒ ★★★所以 `self_us` 為負有**三種**成因，而它們的修法**完全不同**：
   ①`PHASE_PARENT` 那一列的父親寫錯      ⇒ 改那一列
   ②相位區間真的【重疊】而不是包含        ⇒ 改計時點
   ③★**這個名字的母體不是單一父子關係**（同名代表不只一件事）⇒ **拆開這個計時鍵**（給兩個名字）
⇒ ★候選族群**點名**：所有經 `_fai_pht_s` 從 static callee 標記的 `gather.*`。
⇒ ★★而 R² 的理由要逐字留著：**「若驗收②只講父子寫錯，下一個看到紅燈的人會去改父子表，
  改半天發現改不出正確答案，因為問題根本不在那張表。」**
```

★★★**而我要補一句 R² 沒說、但同一個成因造成的更危險形狀**：

```
★負值是【看得見】的症狀。
★★而同一個成因也會造出**正的、但錯的** `self_us`：
  一個被多個外層共用的子相位，被【減進了它只屬於一部分的那個父親】
  ⇒ 那個父親的淨值被**多減**，而**沒有任何一格會紅**。
⇒ ★★★所以本票多一條硬規則：**一個名字若可能從多個外層被觸發，
  它【不得】被登記成任何一個父親的子相位** —— 登記成 `"*multi"`，
  **從 self_us 的減法裡排除**，並在輸出上**具名標示「此列不參與淨值」**。
  ⇒ 寧可少減（父親的 self_us 偏大、誠實地標出來），也不要**多減而看起來很乾淨**。
```

| ② | **★★淨值是對的** | ①已知父子（`loop1.assign_tasks` ⊃ `assign.leader_unified`）⇒ 父的 `self_us` ＝ total − 子；②★**父的 `self_us` 不得為負** ⇒ 判紅；★★而紅燈訊息**必須把三種成因並列**（父子寫錯／區間重疊／**同名代表不只一件事**）並點名 `gather.*` 是第三種的候選；③★★★被標 `"*multi"` 的列**不參與減法**且輸出**具名標示** |
