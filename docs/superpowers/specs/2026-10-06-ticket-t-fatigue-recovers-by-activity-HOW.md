
## §1 做什麼

```
①★**一支分類函式**決定「這一個 pass 這隊有沒有耗力」（單一來源，`_step6d_fatigue` 與床都呼它）：
  耗力 ＝ 這個 pass **真的移動了**（`_run_systems` 的 `moved` 陣列，`sim_runner.gd:470` 已存在）
        **或**在戰鬥中（`combat_target != -1` 或 encounter 參與方）
        **或**當下任務屬於「執行即耗力」那一組（採集／施工／搬運 —— 組名用 TeamData 既有常數列一張表，表放在分類函式旁）
  不耗力 ＝ 其餘（駐守、紮營、idle、在市集交易、夜裡沒移動）
  ⇒ 耗力 ⇒ 照現行累積算式（常數不動）；不耗力 ⇒ 照現行回復算式（`FATIGUE_RECOVERY_PER_DAY`，常數不動）
  ⇒ ★`moved` 要傳進 `_step6d_fatigue`（它今天只拿 team_ids）—— 確認 fatigue 在 move **之後**跑（registry 順序），否則讀到的是上一個 pass
②★「休息」決策選項（新，`options.gd`）：進**求生需求層**（體力那一格），util ＝ 疲勞 × 人格（慎重／求生欲）
  ⇒ to_task ＝ TASK_REST（原地，target ＝ (-1,-1)）—— ★這是 TASK_REST 的**第一個寫入者**
  ⇒ ★禁「疲勞 > X 強制休息」硬門檻（util 秤，不 override）
  ⇒ 它的意義是「主動停下來」：選了它就不移動 ⇒ 由 ① 自然進入不耗力 ⇒ 回復；`rest_mult`（崗哨）照現行
  ⇒ ~~連帶：`npc_combat_system.gd:820` 夜襲判定讀 TASK_REST —— 有了寫入者後這條第一次會活起來~~
    ★訂正（systems 自核，R² 也沒查到這一步）：`_check_night_raid` **全站零呼叫者**（`git grep "_check_night_raid("` 排除定義＝0；
      它頭上的註解是 `TODO: 接入 _try_interact`）⇒ 是**死碼**，TASK_REST 有了寫入者它也不會跑
    ⇒ ★真正第一次被啟用的讀者是 `npc_ai_system.gd:205`（`_goal_task_delta`，1 個呼叫者）：
      個人目標「逃離戰爭」者，隊伍 task＝TASK_REST 時滿足度 +0.005 ⇒ 這是本票會帶出的**附帶行為改變**
③玩家面：生存分頁一欄印疲勞（數值＋文字級距）；玩家「休息」指令（終端自驗床加一格：走法到生存分頁，疲勞欄與休息鍵都在）
```

## §2 驗收（藍圖的四格＋我加兩格）

```
P1 [每隊都會降] 30 天內 **51／51 隊**（母體印出）fatigue 至少下降一次
P2 [紅基線，只准變少] 全界在地板（mult＝0.3）的隊·tick 比例 ⇒ 本輪數當基線
P3 [反向] 移動中不得回復：任何 `moved` 的 pass，fatigue 不得下降
P4 [駐守一夜必降] 佈置一支駐守的隊過一夜 ⇒ fatigue 下降
P5 [分類窮盡] 每個 pass 每隊恰落一類（耗力／不耗力），Σ ＝ 該 pass 處理的隊數
P6 [休息被選過] 30 天內「休息」至少被某隊選中一次，且 util 隨疲勞上升（印疲勞 vs util 的對照）
   ⇒ ★若 0 次：不是加門檻，是回報（util 秤錯了 —— 判準庫：被吸收的需求不會回來敲門）
P7 fp 會變 ⇒ 量、基準與改動原子落地
P8 [★新啟用的讀者要有 tap —— 不變量「新 state 必接 tap」，R² 指出] `_goal_task_delta` 因 TASK_REST 而給出 +0.005 的次數
   （Probe.bump，30 天世界印出；★它第一次被啟用時不能在沒人看的情況下發生）
   ⇒ 夜襲那條**不用** tap（零呼叫者）；但在 spec 記一行：若日後有人把 `_check_night_raid` 接上，紮營無崗哨的風險會跟著 TASK_REST 一起活
★T 修完後，票 T 的三格（中位／撞上限比例／地形差）應該自己變綠；剩下的才是地形／隊速題
```

## §5 實作端回報後的裁定（2026-10-07，systems）

```
回報：「休息」30 天被選 0 次（可選卻輸 1159 次；自己 util 均 0.157 vs 贏家 0.80）⇒ P1 3 支「建設」隊整月卡在 1.0
  根因（實作端量）：休息掛在求生層，而求生層的急迫度只讀食物（`need_hierarchy.gd:45`）⇒ 吃飽的隊一致性係數把休息壓到 ~0.5
⇒ ★這是「感知鐵律的鏡像」那一條：決策讀不到自己的狀態（體力在 team 上，而求生層的秤看不到它）—— 不是調參問題
⇒ 裁 (a)：`raw[L_SURVIVAL] = max(食物那一項, team.fatigue)`（兩個都是 0..1；★不新增常數、不加權重；取 max＝身體最急的那一樣）
   ★已核 fatigue 的值域／欄位（`team_data.gd` 的 fatigue）；若不是 0..1，先換算到 0..1 再取 max，換算式寫在同一行旁
   ⇒ 副作用要量：疲勞高而吃飽時，其他求生層選項（覓食、買糧）的係數也跟著升，但它們自己的驅力是食物缺口 ≈ 0 ⇒ util 仍低
     ⇒ 新格 P9：疲勞 ≥ 0.8 且糧撐 > 5 天的隊·pass，贏家分佈（印出前 5 名選項與次數；休息應進前段、覓食／買糧不應暴增）
✘ 不採 (b)（換主層）與 (c)（重劃耗力組）：兩者都是 WHAT，且 (a) 是讓既有設計讀得到既有狀態，不改設計
其餘兩件：①`moved_since_fatigue` 每隊旗取代「傳 moved」—— 採（move 整點組 vs fatigue 錯開組，原文行不通）
  ②憲法閘 baseline 加 `_action_rest` 一行（同 `_action_camp`：玩家指令、PRIO_PLAYER）—— 採
驗收照舊＋P9；P1／P6 修後必綠（P6 ＞ 0、P1 全 22 隊降過）；fp 變了才換
```

## §6 (a) 之後的第二次回報與裁定（2026-10-07，systems）

```
回報：P6 綠（休息 20 次）、P9 綠；P1 仍紅 4 隊（3 整月建設、1 整月覓食）；實作端另修「休息 target (-1,-1) 被四個派工迴圈當不可派」⇒ 改腳下（採）
②【優先序】休息以 50 搶 80 的覓食被擋 130 次；同一選項在不同派工路徑拿到 50／80
  根因：`options.gd:658 priority_for_need` 對 survival-set 選項一律用**糧撐**當需求軸（吃飽 ⇒ 降成 PRIO_DISPATCH）
    ⇒ 休息的需求軸是**體力**不是糧 —— 同函式註解已寫過同一個病（「拿糧食平安去降一個逃命任務的優先序，是換一個病」，`opt == "survival"` 例外）
  ⇒ 裁（HOW）：休息的需求軸＝疲勞：`team.fatigue >= 1.0`（既有的「累垮」語意，`sim_runner.gd:955`）⇒ PRIO_SURVIVAL，否則 PRIO_DISPATCH；不新增常數
  ⇒ ★整月覓食的 Team25 若覓食持 80（＝糧撐在絕境門檻下），休息搶不下是**對的**（餓比累急）—— P1 對它不判紅，印出它的糧撐

  ⇒ 「疲勞要不要拖慢工作」＝世界物理 ＝ WHAT ⇒ 已問藍圖；在那之前 P1 不得用調秤的方式變綠（禁 crank）
```
