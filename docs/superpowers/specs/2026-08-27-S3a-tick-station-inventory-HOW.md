# S3a：每 tick 站【構造性盤點】（HOW）

`from: systems`｜`tier: probe`（★**純盤點，零 production 改動**）
**WHAT**＝`2026-08-20-time-reanchor-tier-design.md`（LOCKED）§3 ＋ **用戶原令：「列出所有頻率，一個個對」**
**blueprint 裁定 2026-08-27**：★**列舉必須是【構造性】的（掃每 tick 管線全站），不是手列。**

## ★★★為什麼先切出來：**它現在決定三件事，而它們都在等它**
```
①第三型（節律掛 tick）有幾個【真實例】—— ★目前【零實例】（propagate 那顆已被實測打掉）
②★★終量是【合併】還是【分兩次】—— blueprint 已把裁定改成【條件式】：
   真每 tick 站覆蓋率【高】⇒ 維持合併（S1c＋S3 皆齊才量）
   覆蓋率【低】          ⇒ S1c 齊即可先跑【S2 純度終量】，S3 後再一次
③S3 本身的搬家清單（原本八支 ＋ 盤點結果）
```
★**所以它是【前置決策輸入】，不是 S3 的一部分** —— **同 S1a 對 S1b 的關係。**

## ★★盤點的可執行定義（★而 propagate 那顆給了我們判準）
> ★★★**「看起來掛在每 tick」不算數** —— **`propagate` 看起來掛在每 tick 的 arrival 事件，
> 而實測呼叫次數兩根兩床完全相同（1.08/小時），因為它早就是 cadence 驅動。**
⇒ ★**所以 S3a ＝【靜態列舉】＋【實測驗證】兩步，缺一不可。**

### ①靜態列舉（構造性，從入口出發）
```
★從 tick 入口（sim_runner 的 tick 迴圈）出發，列出【每 tick 被呼叫】的所有 system 進入點
★★對每一個進入點，往下追到【第一個 cadence gate】為止
   —— ★★★有 gate ⇒ 記下 gate 的來源（哪顆常數／由誰導出）
      沒有 gate ⇒ ★【候選：真每 tick 站】
★母體要可宣告：★★「從入口能到達的進入點總數」，而不是「我找到的那幾個」
```

### ②★★★實測驗證（★這一步是 propagate 教的，不得省）
```
★對每一個【候選真每 tick 站】，量它每遊戲小時的【實際執行次數】
★★判準：次數 ≈ TICKS_PER_HOUR ⇒ ★★★真的是每 tick 站
        次數 ≪ TICKS_PER_HOUR ⇒ ★它有 gate（靜態沒追到）⇒ 回頭補靜態列舉的漏
★★★★而【後者本身是發現】：它說明靜態列舉在哪裡看漏了
```

## ★驗收
1. ★**靜態列舉有【可宣告的母體】**（★「從 tick 入口能到達的進入點總數」）—— ★★**不是「我找到 N 個」**
2. ★★**每一個候選都有【實測次數】** —— ★★★**靜態說是、實測否掉的，逐個記下來**（★那是列舉方法的缺陷紀錄）
3. ★**零 production 改動** ⇒ ★★**`fp` 兩床逐位元不變**（★**若變了就是動到了不該動的，直接回退**）
4. ★**陽性對照**：**臨時把一個【已知有 cadence gate】的站的 gate 拿掉 ⇒ 它必須出現在候選裡；還原後消失**
   ★★**沒有這一格，我們不知道列舉是【抓到了】還是【剛好沒有】**
5. 三閘 PASS（憲法／裸 tick／headless baseline 7）
