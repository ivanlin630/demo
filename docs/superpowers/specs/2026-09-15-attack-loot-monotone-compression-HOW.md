# HOW spec：攻擊的 `loot` 從【硬截】改為【單調壓縮】

- **WHAT 授權**：blueprint 2026-09-15「**先補攻擊的單調壓縮（同族修法 2026-09-04 已施行、有理由，不需新裁）→ 重量 →『該不該贏』到那時才是真問題**」
- **★而這不是新設計**：**同一個病在 `maintain_*` 那一族已經治好過** ——
  `goal_resolver.gd:125` `u = GOAL_UTIL_CAP × x / (1.0 + x)`
  **理由逐字（2026-09-04）**：「**超過上限的一律壓成同一個值 ⇒ 可比性被削掉，
  argmax 退化成註冊序偏好（實測 clamped 167/333，五個 option 同為 1.5000）**」
- **★★而攻擊是同族同症**：`terms.gd:228` `_loot = clampf(est / 3.0, 0, 1)` ⇒ **實測 72% 撞頂**

---

## ① 病（★數字，不是描述）

```
`est`（有情報的列 n=216）：**p50 3.785｜p90 17.6｜63/107 > 3.0**
⇒ `_loot = clampf(est/3.0, 0, 1)` ⇒ ★**中位 ＝ 1.000、72% 撞上限**
⇒ ★★**「肥」與「更肥」拿到同一個分數** ⇒ **那一維在 72% 的情況下是常數**
⇒ ★★★**而這正是前例那句話**：**可比性被削掉。**
```

## ② 修法（★★★而「用哪個 CAP」不准用挑的）

```
**形狀**：`_loot = CAP_L × x / (1 + x)`，其中 `x` ＝ **`est` 的某個無量綱化**
★**而三件事要在 spec 裡寫死，否則它會變成另一個死常數**：
  ①**`x` 怎麼來**（★現在是 `est/3.0` —— **而 3.0 的註解寫的是「tier0/1 的 0..3」**，
    ★★**而實測 `est` p90 是 17.6** ⇒ **那個除數與實際尺度不符**）
  ②**`CAP_L` 是多少、以及【它從哪裡來】** ——
    ★★★**implementer 說他有一個【不必挑數字】的答案 ⇒ 這一格等他，而 spec 不先填**
  ③★**壓縮的對象是哪一段**：`odds × person` **在壓縮之後還會乘**
    ⇒ **「壓縮 `loot`」與「壓縮 `0.6×loot + 0.4×need`」與「壓縮整個 `_opp`」是三種不同的修法**
    ⇒ **必須寫死是哪一種，並寫出為什麼。**
```

## ③ ★訂正 spec 裡兩個我寫過的數（implementer 抓）

```
①~~「攻擊的上限是 0.6」~~ ⇒ ★**只在 `need ≡ 0` 時成立**
  **一般式**：`0.6×loot + 0.4×need ≤ 1.0` ⇒ **上限是 1.0，而實務上因為 `need` 幾乎恆 0 而落在 0.6**
  ⇒ ★★**所以「0.6 vs 1.5」那個對比要改寫成「實務上 0.6，理論上 1.0」。**
②~~「`maintain_*` 的 payoff 是 TEST VALUE 常數」~~ ⇒ ★★★**死值** ——
  實際走 `derived_payoff()` ＝ **`(pop × 10 − stock) × 2.0`**（`goal_resolver.gd:118/194-220`）
  ⇒ **它早就是期望價值** ⇒ **本票【不碰它】。**
```

## ④ 驗收（★★沿用今天定的形狀）

```
①**撞頂比例從 72% 掉下來**（★**而不是「攻擊贏得更多」** —— 那是 crank 的形狀）
②★**分得出肥瘦**：**同一批目標裡，`est` 高的列的 `loot` 要高於 `est` 低的列**
  ⇒ **成對對照**：**肥 ⇒ 高分／窮 ⇒ 低分**，★★**兩格都要跑**
③★★★**單調性**：**`est` 變大，`loot` 不得變小**（**壓縮的定義**）—— **造一組遞增輸入驗它**
④**fp 會變**（接受）＋ **同 seed 兩跑逐字相同**
⑤★**幣別邊界具名**（blueprint 裁）：**卷上要印【哪些 option 已遷／未遷】**
  ⇒ **已遷：`maintain_*`（一直是導出的）｜未遷：攻擊**
⑥★★**禁 crank**：**不准同時調 `0.6`／`0.4`／`ATTACK_CAUTION_W`** —— **本票只動壓縮那一段。**
```

## ⑤ 不做的

```
★不碰 `payoff` 那一族（**它已經是導出值**；而 TEST VALUE 的普查另有其線）
★★不抬任何上限｜★★★不改 `need` 的定義（**92% 恆 0 是世界的事實，不是 bug**）
```

## ⑥ ★★★2026-09-15 併票與訂正（blueprint 裁 ＋ 分布量到）

### (1) 併票：**本 spec 改成【一張票做兩件】**（blueprint 裁）

```
①**攻擊對齊既有範本**：`derived_payoff` ＝ **缺口 × 單價（單位 coin）**
  ⇒ 攻擊 ＝ **belief 估戰利品 × 單價 − 風險／時間成本** ⇒ **同單位**
②**單調壓縮**（原 §②）
③★**那張死 `payoff` 表的處置（標死或刪）併進本票** ——
  ★★理由逐字（blueprint）：**「殘表會讓下一個讀的人重演今天」**
  ⇒ ★★★**而今天它已經騙過我一次**（我據它寫了「payoff 是 TEST VALUE 常數」給 blueprint）。
```

### (2) ★★★而 ①與② 的關係要先想清楚（★我不預設，這一格要 R² 看）

```
★**若攻擊改成 coin 值** ⇒ **它沒有 0–1 的天花板** ⇒ ★★**「壓縮」可能【自動不需要】**
★★**但也可能仍需要** —— 因為 `derived_payoff` 那一族**自己也有壓縮**（`CAP × x/(1+x)`）
  ⇒ **若兩邊都要進同一個 argmax，壓縮函式應該【同一支】**
⇒ ★★★**所以正確的順序是**：**先對齊幣別 ⇒ 再看壓縮要不要、以及要不要與那一族共用同一支**
  ⇒ **而不是先壓縮、再對齊**（★那會壓一個即將被換掉的量）。
```

### (3) 訂正：**「結構性不可能贏」→「極窄的角落」**（★分布量到了，n=200）

```
贏家 util 分布：**p25 0.640｜中位 0.739｜p75 1.085｜max 2.831**
★**假說成立**：贏家中位 **0.739** ≫ 攻擊的典型值 **0.27** ⇒ **2.7 倍**
★★**而「結構性不可能」過強** ⇒ **訂正**：
  **攻擊的絕對最好 ＝ `0.6 × odds(1.0) × person(1.5) ＝ 0.900` > 中位 0.739**
  ⇒ ★**不是不可能，是【極窄的角落】**：要贏中位得 **`odds × person ≥ 1.232`**
  ⇒ **而 `person` 中位 0.613 ⇒ 需要 `odds ＝ 2.01` ⇒ 不可能**
  ⇒ ★★**隊 80 正好量出那個角落有多窄**：`odds` 已滿格 1.000、`person` 0.710
    ⇒ **上限 0.426** ⇒ ★★★**它那個人格【永遠】贏不了中位。**
```

### (4) ★而 (3) 有一個【設計意涵】，我把它標出來但不裁

```
★**能贏的那個角落 ＝ `person` 要接近 1.5** ——
  而 `person ＝ clampf(0.5 + (max(好戰, 貪婪) − 0.5) − (慎重 − 0.5) × 0.8, 0, 1.5)`
⇒ ★★**也就是說：【只有好戰或貪婪拉滿、而且不慎重的領袖】才可能選擇搶劫。**
⇒ ★★★**而那【不荒謬】** —— **它其實正是「劫掠者是一種人格」的形狀**。
  ⇒ ★**所以修完幣別之後，真正要問的可能不是「搶劫夠不夠划算」，
    而是「這個世界裡有沒有那種人」** —— **而那是 blueprint 的題。**
```

## ⑦ ★★★ 2026-09-15 根因再下一層：**`est` 裡面混著兩種單位**（implementer 挖到，改寫本 spec 的核心）

```
`faction_ai_system.gd:379-384` `_belief_richness()` ★**兩條回傳路徑**：
  ①`coin_est / food_est / material_est` ⇒ **`(coin + food + material) / 100.0`**
  ②只有 `resource_scale` ⇒ **直接回那個 0..3 的【桶號】**
⇒ ★★★**tier1 的 `est = 2.0 / 3.0` 不是資產估計，它是【桶的編號】**
  （實測 tier1 p10/p50/max ＝ **2.0 / 3.0 / 3.0** —— **逐字吻合**）
⇒ ★★**而①本身也不是 coin 當量**：**coin 與 food／material 是不同單位**，
  它把三個數**直接相加**再除一個**手填的 100**。
```

### ★而它解釋了今天兩個我們追了很久的現象

```
①**72% 撞頂**：**桶號 3 被當成「價值 3」** ⇒ `clampf(3/3, 0, 1)` ⇒ **1.000**
  ⇒ ★**不是「目標很肥」，是【桶號剛好等於除數】。**
②**「知道得多挑得準」量不出來**：**tier1 的值根本不是價值** ⇒ **拿它與 tier2 比是比錢與序號**。
```

### ★★★修法的順序因此改寫（★而 CAP 那一格【正式取消】）

```
★implementer 的一句我照收：**「要填的是【單位】，不是上限」**
⇒ **第一步**：**讓 `_belief_richness` 回【同一種單位】** —— ★而那個單位已經存在：
  **`BASE_PRICE`**（`derived_payoff` 用的就是它）⇒ **coin 當量**
  ⇒ ①改成 **`Σ (資源估 × BASE_PRICE[資源])`**（★**拿掉那個手填的 100**）
⇒ **第二步**：**tier0/1 只有桶號 ⇒ 它【估不出價值】** —— ★★**而這是一個設計選擇**：
  (a)**承認估不出** ⇒ 那一層的 `loot` 項**不參與**（★而不是給一個假值）
  (b)**桶號 × 一個具名的代表值** ⇒ ★★★**而那個代表值要導出，不准手填**
  ⇒ **這一格要 R² 看，而我傀向 (a)** —— **因為 (b) 會再造一個「看起來很合理」的數字。**
⇒ **第三步**：**單位對齊之後，再看【壓縮】要不要** —— ★**而很可能不要了**：
  **coin 值沒有 0–1 天花板，而撞頂的原因是桶號不是真的很肥。**
★**所以 §② 那個「用哪個 CAP」的留白格【取消】** —— **它問錯了問題。**
```


## ⑨ ★★★一個症狀底下【兩個病】（implementer 拆開 2026-09-15）

```
**撞頂 155 列**（有 belief 的 216 列的 72%）拆開：
  ・**tier1 貢獻 92 列（撞頂的 59%）** ⇒ ★**那 92 列的 `est` 【全部都是 3.0】**
    ⇒ **桶號 3 ÷ 除數 3.0 ＝ 1.0** ⇒ ★★★**撞頂是【算術必然】，不是「那些目標很肥」**
  ・**tier2 貢獻 63 列（41%）** ⇒ `est` **3.21–24.27** ⇒ **它們才是「真的超過參考值」**
⇒ ★★**兩個病**：**單位病（tier1）要統一單位**｜**值域病（tier2）才要壓縮**
⇒ ★★★**而先壓縮會把單位病【蓋在一條漂亮的曲線下】** ——
  **因為壓縮之後，那 92 列不再都是 1.0，而它們仍然是【桶號】。**
★所以 §⑦ 那個順序（①單位對齊 ⇒ ②tier0/1 怎麼辦 ⇒ ③壓縮要不要）
  **不再是我的判斷，是【有數字支撐的】。**
```

### ★★而那 92 列的【全部都是 3.0】本身是一個簽名

```
★**「所有值都一樣」是【算術】的簽名，不是【世界】的簽名** ——
  **一個真實的世界量不會讓 92 個不同的目標拿到逐字相同的數。**
⇒ ★★**判法**：看到一群值完全相等 ⇒ **先找那個讓它們相等的【機制】**，
  **不要先解釋世界。**
```
