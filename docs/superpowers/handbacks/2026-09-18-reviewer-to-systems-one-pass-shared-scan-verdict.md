# ①「圈數相同⇒沒有提前跳出」——你的邏輯疑慮成立，而我直接查出了更硬的答案

你自己列的兩個漏洞（①break剛好沒被這批母體觸發②三段被同一個上限截斷）邏輯上都對——
「圈數在這兩次跑出來一樣」本身**推不出**「code裡沒有break」，只能推出「這兩次沒有break跳出」，
這是經驗觀察不是結構事實，你的懷疑是對的，不該把3-g(經驗式)當成這件事唯一的守衛。

我沒有停在確認你的懷疑，直接開了三支函式的完整body找答案：
```
attack_scan(faction_ai_system.gd:246-427)：全函式只有一個return，在:427(函式最尾端)，
  loop內【零】break、零提前return
_find_weakest_prey(:7386-7408)：同上，只有:7408一個return在函式最尾端
_max_belief_threat(:4620-4628)：同上，只有:4628一個return在函式最尾端
```
**三支函式的迴圈裡完全沒有break，也沒有任何提前return**——這不是「這兩次剛好沒觸發」，
是**程式碼結構上就沒有這條路可以走**。這是比「圈數相同」硬得多的證據：圈數相同是【觀察】，
這個是【讀到的事實】，前者可能因為母體特性巧合成立，後者不會。

**建議**：把3-g的角色從「本票的前提證明」降格成「回歸守衛」——**主證據換成這句靜態事實**
（三支函式逐字沒有break/提前return，file:line列在上面），3-g留著繼續守「以後有人改了其中一支
加進break會被抓到」，但它不再是撐起「等價是構造保證」這句話的那根柱子，靜態讀才是。
這個換法會讓你想要的「構造保證」真的名符其實——現在的構造保證其實是靠我剛才那次讀code，
不是靠三個數字碰巧一樣。

# ②3-d(反轉走訪順序)的陽性對照——打到真正的風險，不是空證明

這格測的不是「反過來會不會不一樣」這種顯而易見的事，是在確認**3-b這個比對機制本身有沒有
鑑別力**——它要回答的問題是「如果合併後的走訪順序真的跟原本三段任何一段的順序不一致，
3-b抓不抓得到」。反轉順序是一個乾淨、單變因的擾動(只動順序,不動集合本身、不動其他任何屬性)，
這正是今天全天在用的「陽性對照先證明會致死」同一招，用在3-b這個比對器身上。這格設計對，
不需要改。

# ③3-e/3-c守「不共用計算結果」——目前是紀律，而這條的代價比昨天那個「沒有便宜省法」高，建議往前推一步

GDScript不會阻止有人在merged loop裡把segment A算出的中間值直接讀給segment B用——
跟今天freeze-multi那票"沒有第二份算式"是同一類問題(語言層不強制)。你的3-e陽性對照
證明「如果違反,3-c會紅」，但那是**這次migration的驗收**，不是一個**之後任何人再碰這段code
時都會自動觸發**的守衛——3-c釘的是跨這次修法前後那兩棵樹的比對，migration完成之後，
未來有人改merged loop共用一個中間值，除非他剛好重跑完整的3-c跨樹比對(通常不會，因為
那是跨commit的歷史比對，不是日常回歸)，否則不會自動被抓到。

這一點我要跟你在equivalence-pruning那票判的「沒有便宜省法⇒結案」的自律格區分開——
那一格違反的代價是「多做了一次還是要過安全檢查的無謂工作」，代價低，我當時判可以接受
純自律。**這裡不一樣**：違反這條會讓merged loop少算一次，直接產出錯的數值(不是多做工，
是漏做工)，代價是**真的算錯**，跟今天已經證明過的"少呼一次會踩RNG/cadence"是同一個高
風險家族。**建議**：對merged loop的原始碼做一個內容錨——每個segment的計算區塊裡出現的
變數，不得在另一個segment的區塊裡被讀取(可以用簡單的regex：segment A宣告的區域變數名
不應該出現在segment B/C的程式碼範圍內)。這個錨比"call一個共用函式"複雜一點(不是單一
call expression)，但仍然是今天全天在用的同一種靜態文字比對工具，做得出來。非阻擋，
但鑑於代價層級,建議往這個方向補，不要只停在3-e那一格陽性對照。
