# ★③答案：(a)——量測方法低估真值，不是clamp

我的算法：`_hex_dist(prev_pos[team], cur_pos[team])`，**只在day boundary(每240tick一次)算一次淨位移**。

**低估的原因**：若一隊當天出去5格、又折返回原位（或接近原位），
淨位移＝`hex_dist(day首,day末)`可能算成0或很小，**但實際移動路徑長度是10格**。
★**day-boundary快照法只看『這一天結束時人在哪』，看不到『這一天內走了多少路』。**
⇒ **真值 ≥ 我印出來的數字**，這是(a)，不是(b)clamp/floor。

# ★★關鍵問題：這個低估的偏誤來源，before/after穩不穩定？

**我的判斷（推論,非已驗證）**：可能穩定，理由：

S2的設計前提是「cadence以小時宣告、自動跟隨tick-rate」——若這個前提成立，
**移動決策的頻率**（隊多久評估一次要不要移動、要往哪走）**應該不隨tick-rate改變**，
只是tick粒度變細（同一小時內移動被拆成更多更小的步進）。
若移動速度也是「每小時走多遠」定義、按TICKS_PER_HOUR自動換算步長（跟cadence同一個設計原則），
那麼**「一天內有沒有出去又折返」這個行為模式的統計頻率，理論上不該因為tick-rate改變**——
因為決定"要不要出門、要不要折返"的是決策cadence（小時級），不是tick粒度本身。

★**但我沒有辦法驗證這個推論**——因為(前一票已確認)「6×制」現在不存在任何可跑的版本，
我沒有東西可以拿來對照check「折返率」是不是真的statistically equivalent。

# ★★★我的建議

**這一項現在只能標「可能可用，未驗證」**，不能保證。
建議 after 那輪除了比對移動格/日的相對差，**額外驗一件事**：
「當天出去又折返(net displacement明顯小於預期路徑)的比例」在before/after是否也在誤差範圍內——
若這個比例穩定，移動那項的相對差可信；若這個比例本身跳動，移動那項的相對差就跟着不可信，
不是S2的問題，是量測方法本身失真。
