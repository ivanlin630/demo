# 判決：`issues`（小），`premise_contradiction: false`

## ★主問題——不是同一種病，判準不是自我說服

你今天拒絕 Tier2 的理由是「防一個沒發生的病」。這次不是同一個形狀，兩點差異都是結構性的，不是「因為我今天剛好想修所以合理化」：

1. **證據性質不同**：Tier2 是預防性的（尚未發生），這次是**兩支獨立床、同一天、各自真的示範過會失效**（薪資床假綠、gather 床 fp 沒鑑別力）——不是同一類事件的重複描述，是兩個不同的失效模式各自撞了一次。
2. **機制性質不同**：這條規則的核心強制力（§3b①-④）**只鎖 diff 觸及的檔**，對新增/修改的床是**真的會擋**（沒宣告 ⇒ 紅；宣告 invariant 卻沒接線 ⇒ 紅）——這是一個**硬性阻擋點**，不是「多印一行字希望大家自律」那種軟性規則。軟性規則（例如你自己點名的「印 N/371」那句）才是容易長成「清單長大不擋任何東西」的那種形狀；這次的閘體本身不是那種形狀，只有其中一句附加宣稱是。

⇒ **這不是同一個病，判準站得住。**

## ①「印 N/371」這句對沖——已經被證偽，建議拿掉這個宣稱本身（閘不用動）

`bed-arm-whitelist.txt` 表頭同一招（印出現有規模、宣稱它會單向下降）跑了一週，273→272→270——本質持平（下降主因是刪過期床，不是「印出來」這件事本身產生壓力）。**這確實證明「印數字會讓人自發修」這個因果鏈不成立**——你的懷疑是對的，不是多慮。

但要分清楚**兩件事**：「印 N/371 這行字能不能讓 371 自己降下來」（不能，已證偽）跟「§3b①-④ 這個硬性閘門能不能擋住新增/改動的床不宣告」（能，因為它是強制不是自願）。**建議只改措辭，不改機制**：把 §3b 那句「這一條抄 bed-arm-whitelist 的表頭，它那句是對的」拿掉或改寫成誠實版——「這個數字是診斷可見度，我們不宣稱它會自己下降；371 只靠 on-touch 慢慢縮小，這是刻意的止血優先設計，不是自欺」。閘的實際擋人能力不受影響，只是別再借一個已經被自己的資料反駁的類比來壯膽。

## ②`pending` 不是垃圾桶，但要加一條機械交叉驗證

`blocker:` 目前只檢查「有沒有寫」（§3b④），沒有檢查「寫的那個 token 是不是 `defers.tsv` 裡真實存在的行」——這正是它可能變垃圾桶的破口：任何人寫 `blocker: 隨便打字` 都會通過檢查，等於白名單形同虛設。

而**你自己給的 gather 範例已經示範了正確用法**：`blocker: gather-purity-bed-as-gate` 對應到 `defers.tsv:113` 那一行**真實存在的 token**（我讀過那行，格式跟其餘 token 一致，有 summary／defer_until／met_check 三欄）。既然正確用法本來就長這樣，把它變成機械檢查是**舉手之勞**：

```
§3b④ 加一句：kind=pending 的 blocker: 值必須在 docs/process/defers.tsv 的 token 欄裡找得到
   （git grep -q "^${blocker}\t" docs/process/defers.tsv，排除「已解除」註解區塊）
```
這樣 `pending` 就不是「隨便寫個理由就能拖著不修」，是**真正掛到 defer 追蹤系統上**——跟 `defers.tsv` 檔頭自己「散文裁定不受追蹤=會被遺忘」的立法精神完全一致，是同一套機制的自然延伸，不是另開一條新規則。
