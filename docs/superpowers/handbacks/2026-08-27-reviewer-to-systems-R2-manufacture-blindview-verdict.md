# 判決：`clean`

## file:line 核對——四處都對上

## ★★風險倒轉——你抓對了，而且原子性方案在這個架構下是站得住的
查了 `ResourceBank.remove`（`:9-14`）跟 `TileBank.withdraw`（`tile_bank.gd:71-74`）——**兩者語意對稱**：都是 `clampf(amt,0,現量)` 後扣、回傳實際扣到多少，沒有任何隱藏的保留量/floor 邏輯（`withdraw` 就是單純 clamp，不像 `reserve()` 那種人格化留底）。

**你問的「單執行緒同tick下夠不夠」——夠**：只要「檢查兩池夠不夠」跟「用 `remove`/`withdraw` 扣款」在**同一次函式呼叫、中間沒有 `await`/讓出執行權**（目前 `_run_recipe_group` 的迴圈就是這樣，純同步），那麼「檢查時池是 X、扣款時池變成 Y≠X」這件事在 Godot 單執行緒 tick 模型下**沒有發生的物理管道**——沒有別的程式碼會在檢查跟扣款之間插進來改動同一個 team/tile 的資源。**「兩者加總 != 應扣」這個分支在正確實作下應該是永遠不會真的觸發的防禦性斷言，不是會員際發生的競態。**

**你留的洞（已扣一半怎麼還）——不需要回滾機制，建議用「大聲失敗」取代**：既然這個分支在架構上應該不可達，投資寫一套回滾/復原邏輯是為了一個不會發生的情境增加複雜度（多寫的復原碼本身也可能有 bug，而且幾乎測不到，因為它幾乎不會被觸發）——★**建議**：「不等」那條分支不寫回滾，改成 `assert` 或 `push_error` + 詳細印出「哪個 res、預期扣多少、實際扣多少、team/tile」，把它當成「這不該發生，一旦發生代表別處有更大的 bug，要立刻被看見」，而不是優雅地兜住。這跟今天別票「不要為了防禦還沒發生的傷害過度設計」是同一條紀律。

## 另兩點——都同意

②所有權閘複用 `_team_works_tile`——**查過了，它本來就已經是整條生產流程的資格閘**（`manufacturing_system.gd:111`，卡在 `_run_recipe_group` 被呼叫【之前】）——換句話說，公庫的**寫入**（`_add_output`→`TileBank.deposit`）早就只發生在通過這個閘的 `(team,tile)` 組合上；現在投入端的**讀取/扣款**用同一個閘，是跟既有寫入端對齊，不是新引入一個較弱或較新的邊界。複用得夠。
