# ① 兩個病，第二個才是根

```
★病①【計時器的主詞會變，而計時器不會重來】
   long_running 回傳四種來源之一：beacon:<role>／godot-proc／file-activity／file-activity-wt
   舊碼：只要它非空 ⇒ run_since 一直留著；空了才歸零。
   ⇒ 來源從 A 換成 B，計時照舊 ⇒ ★★報出來的「長工作已跑 X（來源 B）」，
     那個 X 【不是 B 的時長】—— 主詞與數字來自兩件不同的事。

★★病②【其中一個來源幾乎恆真】——這才是 8h32m 的來源
   file-activity ＝ scripts/ 或 docs/measurements 十分鐘內有檔被動過。
   ⇒ ★六個角色同時在工作時，它【永遠是真的】。
   ⇒ run_since 在 watchdog 起來的第一輪就被設下，之後【永遠不重置】。
   ⇒ ★★★它量到的是【watchdog 自己活了多久】。
     8h32m 對不上任何進程，是因為它從來就不在描述任何進程。
```

★**所以你的「跨 run 累加」方向是對的，而實際更極端**：不是累加多個 run，
**是根本沒有在計任何 run。**

# ② 修法三件

```
(a) 記住【是哪個來源】（run_src），來源一換就重來 —— 治病①
(b) ★file-activity 類【不餵 MAXRUN】—— 治病②
    理由一句：**它是「有人在工作」，不是「有個長工作」**，兩件事不同名不同義。
(c) ★★beacon 本來就帶 `started=<iso>` ⇒ 用它算【真工期】，
    而不是用「我連續看到它多久」。★★★並在警報裡【標明判準來源】：
    「★真工期(beacon started=) 2h13m」vs「連續觀察到 2h13m」——
    ⇒ 讀警報的人要看得出這個數字是哪一種。
```

# ③ ★★★而我修的時候差點種下同一族的新 bug（成對對照抓到的）

```
`date -d ""` 在 GNU date 上【不報錯】，它回【今天午夜】。
⇒ 一個【沒有 started= 的 beacon】會生出一個最多 24 小時的假工期
   —— ★正是這次要修的那一族（假的長工期）。
⇒ 處置：解析抽成 beacon_started_s()，並加 --selfcheck 七格：
   ✓真格式解得出｜★沒有 started=⇒0｜started= 空⇒0｜非數字⇒0｜
   ★★被截斷的半個 ISO（`2026-09-10T`）⇒0｜荒謬日期⇒0｜檔不存在⇒0
   —— 後六格全部必須落回「連續觀察」，全綠，已註冊進 merge-gates。
★★而我要指出這一格的形狀：**它不是在測我的解析寫得對不對，
   是在測【問不出來的時候它會不會編一個】** ——
   ★★★而「編一個」正是這支 watchdog 前三次出包的共同形狀。
```

# ④ 這是 beacon 讀取系的第三次，我把三次並排（★三次都不是判斷寫錯）

```
第一次  契約改了而只有一個 reader 被遷移（bash-guard 改了心跳 mtime，watchdog 沒有）
        ⇒ beacon 那一支【從改契約那天起一次都沒 fire 過】
第二次  親子樹：殺 shell 不殺子進程 ⇒ 讀到的存活狀態是假的
★第三次（今天）計時來源：計時器的主詞會變而計時器不會重來 ＋ 一個恆真的來源
⇒ ★★共同形狀：**三次都不是「判斷寫錯」，是【讀進來的東西不是它宣稱的那個東西】。**
⇒ ★★★所以修法一律是【讓它問不出來時說「我問不出來」】，而不是讓它算得更準。
```
