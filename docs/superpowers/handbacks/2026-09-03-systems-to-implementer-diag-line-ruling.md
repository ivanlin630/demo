# ★①裁定：印【實際非空殘留】，不印清除點清單
```
★(a) 清除點清單 = 規格宣告 ⇒ 永遠一樣長 ⇒ ★★它會 rot,而且【它描述的是我們的意圖不是世界】
★(b) 實際非空殘留 = 體溫計 ⇒ ★★★它是【已處置的結果】而不是【要被解讀的狀態】——今天立過的那條
⇒ 取 (b)
```

# ★★②但 (b) 有一個【天生盲區】，而它不歸這行管
```
★runtime 行只印【它知道的那些】—— ★★有人新加一個 static 而沒註冊清除，這行【永遠不會提到它】
⇒ ★★★所以「有人新加了一個沒清的 static」由【機械檢查那張票】負責（靜態 grep production 的 `static var`
   對照清除清單），不是靠這行
⇒ 兩者分工要寫在【那行自己的註解】裡，否則下一個人會以為這行涵蓋全部
```
★**這正是「檢查管道 ≠ 失效管道」的正用法**：**動態抓「有沒有殘留」，靜態抓「有沒有漏註冊」——兩條軸，兩個工具。**

# ★★★③形狀（★母體與命中同印，缺一不可）
```
[diag] cross-run: checked=<檢查了幾個> cleared=<清之前非空的那些,含量> flags=<非預設值的旗標>
例：[diag] cross-run: checked=11 cleared=_path_cache(267) _fall_seen(117) flags=trace_infra=true
    [diag] cross-run: checked=11 cleared=none flags=none
```
★**為什麼一定要 `checked`**：★★**只印 `cleared=none` 的話，「真的乾淨」與「reset 根本沒跑」長得一模一樣。**
★★★**而 `checked` 是那條 0 的母體** —— **今天我們已經在五個地方用過這一條。**

# ④順帶
`cleared` 非空**不是紅**（第一輪本來就會有東西可清）—— ★**它是【證明清除點真的在做事】的陽性證據**，
★★**而那正好省掉一次人工陽性對照**：**若它從第一天就恆為 `none`，那才要懷疑接線。**
