# 判決：`issues`，`premise_contradiction: false`

## ①「arm行號 < setup行號」——**你猜對了會漏,而且我找到具體會漏的形狀**
這個判準的隱藏假設是【文字位置順序 ＝ 執行順序】——**這兩件事只有在「照順序往下寫的純腳本」才會相等**。GDScript 的 `SceneTree` 腳本常見寫法是 `_initialize()` 呼叫一串 helper 函式，而 **helper 函式的【定義位置】跟它們被【呼叫的順序】是兩件獨立的事**：

```gdscript
func _initialize():
    _do_setup()     # 執行順序：先
    _arm_probe()    # 執行順序：後

func _arm_probe():   # ★文字位置：定義在前（例如 line 5）
    Probe.enabled = true

func _do_setup():     # ★文字位置：定義在後（例如 line 15）
    GameSetup.setup(...)
```
這個例子裡 `arm行號(5) < setup行號(15)`——你的判準會判「正確」，但**實際執行順序是先 setup 再 arm，是一張真盲床，卻被歸進了 93 張「正確」裡**。這正是你今天已經犯過兩次的那個形狀（「從我走的管道去數，缺陷不在那條管道上」）第三次出現，只是這次換成「文字順序不等於執行順序」這個新變體。

⇒ **建議**：不用重新設計整個計數方法（那個成本太高），★**抽樣手驗**——從 93 張「正確」裡抽 8~10 張，人工讀一次它們的 `_initialize()`（或等價入口）body，確認 arm 呼叫真的在 setup 呼叫【之前執行】，不是只在文字位置上更早。若抽樣全過，殘餘風險記進誠實限（「本次數法假設文字序=執行序，未逐張驗證執行序，已抽樣N張過關」）；若抽樣抓到反例，回頭擴大排查。**這是便宜的止血，不是要你重寫方法論。**

## ②★★母體定義——**真的太窄，我查出一個平行的、完全在母體外的族群**
你把母體綁在「呼叫 `GameSetup.setup()` 的床」（136 張）——★**我查了 `scripts/debug/` 全部建構 `WorldState.new()` 的檔案，有 271 個**，扣掉那 136 個走 `GameSetup.setup()` 的，剩下 **135 個用別的路徑建世界**，而其中 **至少 96 個自己定義了 `_mk*`／`_build_world`／`_make_world`／`setup_world` 這類本地 helper**——這是一整族**用手刻、非 `GameSetup.setup()` 的世界建構方式**，完全不在你這張票的母體裡，也完全不會被腿B的閘看到。

★**我不是說這票的 scope 該擴大去修這 96+ 張**——那會把小票撐成大 refactor，跟你今天別票學到的紀律相反。★★**但「母體=GameSetup.setup()呼叫點」這句話若不加限定語，讀起來會像「這就是全部會建世界的床」，而它不是。**

⇒ **建議（小補丁）**：在 spec 明寫一句「本票母體僅涵蓋走 `GameSetup.setup()` 的床；另有 ≥96 張用本地 `_mk*`/`_build_world` 等 helper 手刻世界，是否有同型 arm-順序風險【未查】，記為已知殘餘，另票判斷值不值得查」——跟你在別票已經示範過的「已知殘量,不在本票」同一種誠實揭露，不用現在處理。

## ③白名單機制——**夠，若腿A有殘留，建議接上今天剛建的b_defer追蹤，不要另開一套**
白名單印數字這個設計本身沒問題，而且你這票的目標是【腿A做完後白名單=0】（驗收④），跟 `b_defer`（等某個未來里程碑才處理）性質不同——這裡沒有「等」，是「現在就修完」，所以不需要 `b_defer` 那種到期機制。★**唯一情況**：若驗收④走到「明確剩幾張並列出原因」那個分支（12張沒能全修完），**那些殘留條目在性質上就變成新的 `b_defer` 項目了**——建議屆時直接掛進今天才建的到期閘機制（`bare_tick_triage.gd` 那套），不要為這幾張床另建一個平行的、自己的到期追蹤系統。這條是條件觸發的建議，不影響現在能不能 CLEAN。
