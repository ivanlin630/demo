## ③ 做了什麼

**§4b X 鍵＝推進一小時**
- 不新開推進路徑：照 `KEY_SPACE` 那一支呼叫**既有的** `request_advance()`。
- 單位只引用 `WorldState.TICKS_PER_HOUR`，不寫 60。頁腳 keymap 加 `[X]推進1小時`。
- ★**實測事實**：`SimBridge.STEP_TICK_BOUND == TICKS_PER_HOUR` ⇒ **一次 `_process` 就吃完整個一小時** ⇒ X 鍵的可中斷窗口**只有一幀寬**。那不是缺陷，是那兩個常數相等的必然結果（SPACE 一天＝24 幀才有寬窗口）。已寫進 P11 的註解。

**§4c 待辦數看不懂**
- 入列時看佇列【尾端】同名且無參數 ⇒ 併進去。**不搬出佇列**（那支寫 `player_pending_targets` ＝世界狀態，搬出去會把票5 修掉的不決定性放回來）。
- 合併時回 `merged=true` 且訊息說「同一道，沒有重複排」——★**回報的字要與事實相符**（招募那張的教訓）。
- 頁腳列動作人話，文案走 `PlayerCommandApi.describe()` ＝**與入列回音同一份字串**。

**(a) 無界哨兵具名**
- `ADVANCE_UNTIL_EVENT`，**刻意不叫** `ADVANCE_UNBOUNDED`：99999 ÷ 1440 ＝ **69.4 天**，那是有限天花板。一個承諾得比它交付的多的名字會說謊，而**沒有任何一格在驗名字** ⇒ 失效是靜的。
- ★★★**套用時才發現 UI 那三處 99999 不是同一件事**：兩處是哨兵、一處是夾具（G 鍵把玩家打的數字夾到上限）⇒ **兩個名字、一個值衍生**（`ADVANCE_UNTIL_EVENT = ADVANCE_MAX_REQUEST`）。
- ★而我原以為只有兩處，是因為**先前數的是 `request_advance(` 的呼叫端，不是那個【值】的用法**。接住它的是補丁裡那句 `assert '99999' not in s`。
  ⇒ **技法**：做【替換】時，斷言要打在「**舊東西完全消失**」上，而不是「新東西出現」上（前者的母體是整份檔案，後者是我的清單）。★**反面**：做【新增】時這手法不適用 —— 「檔案裡沒有 X」對還沒加的東西是恆真。

**P19 負對照覆蓋率棘輪**
- `已於…實測紅` 的格數**只准增加**（地板 ui 14／replay 2，跑出來的）。
- ★**不硬紅**：棘輪的目的是【不准倒退】不是【強迫前進】。
- ★★**它自己也點過火**：刪掉任一行紀錄（14 → 13）⇒ 紅。**不是去改地板常數** —— 改常數是改判準，不是製造缺陷。

## ★⑦ 同一天第三次踩同一個病，我要它進帳

```
①P9 斷言「UI 沒有呼叫 runner 推進」⇒ 命中了【討論那個呼叫的註解】
②annotate 的去重拉「負對照：」⇒ 命中了【spec 抄來的要求】

```
★★★**可預測的形式**：**當一個東西的工作是【辨識某個字串】時，它的說明文字【必然】含有那個字串**
⇒ 成因是「談論 X 的文字」與「做 X 的東西」**共用同一個字串空間**，而 grep 活在字串空間裡 ⇒ **它天生分不出「提到」與「是」**。
⇒ **挑錨的判準**：挑一個**只有真實例會滿足、而描述它的文字不會剛好長成那樣**的性質 ⇒ **子字串永遠不合格；格式／行首／整行合格**。
⇒ ★而「換一個更少見的詞」**不是修法** —— 那只是把命中機率調低，沒有改變它活在字串空間這件事。
