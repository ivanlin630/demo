# 1 ★你優先打的②——核過，風險是真的，而且根因可以指到精確的那一行

## add_edge的合併規則：核對是飽和疊加，不是覆蓋也不是取大

```
relation_graph.gd:7-25 `add_edge(edges,type,target,intensity,tick)`：
  找到同(type,target)的既有邊 ⇒ `e["intensity"] = clampf(1.0-(1.0-a)*(1.0-intensity),0,1)`
  ⇒ ★這是本檔自己註解的「唯一疊加點」,逐字理由：「小怨會累積／單次大怨直接高／永不破1／順序無關」
  ⇒ 這不是你問的「覆蓋」也不是「取大」,是第三種：每次呼叫都會把新值【疊】進既有值,讓邊更接近1.0
```

## 風險：加總整季再呼form_feud,若在同一季內被呼第2次,會疊加到已經疊過的那批事件

```
spec現在的文字：「寫"tributed"時,加總同一施加者在TICKS_PER_SEASON內的tributed記憶強度
  ⇒ 以總和呼form_feud」——如果這句話的意思是【每一次新的tributed事件發生時,都重新掃一次
  這一季內該施加者全部的tributed記憶、加總、拿這個總和去呼form_feud】,那麼：
  第k次extort時,加總＝事件1+事件2+...+事件k(含前面已經被算過的那些)
  ⇒ form_feud(總和_k)算出intensity_k並呼add_edge——而邊裡已經疊著intensity_{k-1}
    (上一次呼叫,總和同樣含事件1..k-1)
  ⇒ add_edge的飽和公式是為【新事件、新貢獻】設計的(逐字理由寫「小怨會累積」,預設每次呼叫
    代表一筆【新】的怨),不是為【重複提交含舊事件的總和】設計的——事件1..k-1的強度會透過
    這次呼叫【又】被疊一次(因為它們還留在總和裡),變成同一批事件對邊的貢獻被算了兩次以上
⇒ ★這不是「邊被反覆add_edge」本身的問題(重複呼叫add_edge是既有、刻意的機制),是【重複呼叫
  時傳入的severity每次都重新含有舊事件】跟【add_edge本身也會累積】兩件事疊在一起,
  變成同一批舊事件被兩套累積機制各算一次
```

## 處置（指出衝突，不代裁HOW）

```
兩個互斥的修法,各自內部一致：
  (A)只在【視窗關閉或第一次跨過FEUD_MIN】時呼form_feud一次,季內後續的tributed寫入只累加
    記憶本身、不重複呼form_feud/add_edge——那一季只貢獻一次邊強度
  (B)★更貼近"小事堆成大事"的原意：form_feud每次只傳【這一筆新事件自己的severity】
    (不重新加總整季),讓add_edge既有的飽和疊加自己去做累積(它本來就是為這個設計的)
    ⇒ TICKS_PER_SEASON在這個版本裡的角色變成「多久之後舊怨算過期/不再疊」的視窗,不是
    「總和要呼form_feud幾次」的觸發器
⇒ 不管選哪個,現在的文字「加總⇒以總和呼form_feud」沒有說清楚是【只呼一次】還是【每次新
  事件都重新呼】——這句話的歧義正是風險的來源,補一句消歧義就能解決
```
