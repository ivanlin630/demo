# ★①要坐實什麼（★這是【推導】，不是我在報結論）
```
執行端 sim_runner.gd:164  {"name":"manufacture", "lod": LOD_BOTH, "shape":"teams"}
  ★LOD_BOTH ⇒ far 隊在 far pass 也跑（每 FAR_ZONE_INTERVAL = 600 tick ⇒ 約 2.4 次/日）
  ★★shape "teams"（非 "teams_cadence"）⇒ 呼叫時不傳 cadence ⇒ 間隔變長【不補回】
⇒ 推導：near 24 次/日 vs far 2.4 次/日 ⇒ ★同工坊遠區每日產量 ≈ 近區的 1/10
```
★★**而這是靜態讀 registry 得到的，沒有跑過。** ★★★**要你把它變成量測。**

# ★★②量法（★避開一個陷阱）
```
★做法：同一座工坊、同一組人（pop 固定）、同一份配方，
      ★★一組讓它落在 near、一組落在 far，各跑 N 個遊戲日，比【每日實際產出量】
★★★陷阱：【不要用 manufacturing 的估算函式（runs_per_day 那類）當分母或對照】
   —— 那正是被查的東西：它自述「產線在 NEAR pass」,而那句話就是我們懷疑的東西
⇒ ★要的是【真的產出了幾件】,不是「它以為它產了幾件」
```

# ★★★③兩個結局都要能分辨
```
≈1/10  ⇒ ★推導成立 ⇒ 產出中性性違規 ⇒ 修法已知（接既有 teams_cadence 補償，四系統在用，零發明）
≈1/1   ⇒ ★★我的推導錯（可能有別的補償路徑我沒看到）⇒ 病4 維持銷案
其他值 ⇒ ★★★照實報,不要往兩個預期靠 —— 第三種答案比對上其中一個更有價值
```
★**若床做不到「同工坊 near vs far」的乾淨對照，寫信說** —— ★★**不要用近似的替代品然後標成坐實。**
