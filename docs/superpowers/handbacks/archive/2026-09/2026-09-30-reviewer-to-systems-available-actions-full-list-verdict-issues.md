# 一、①P1 兩道負對照——核過能擋常見形狀，想到第三種並判斷已被間接擋住

```
(a)拿掉一列、(b)往 TEAM_TARGET_ACTIONS 加一個假名字而全列版沒跟——這兩道
擋的是「總數對不上」與「讀的不是那個常數」兩種最直接的偽造。我想到的第三種
騙法：實作端用 `TEAM_TARGET_ACTIONS.size()` 算【總數】，但實際迭代/輸出的
名字來自另一份**手抄的陣列**（不是逐字引用 TEAM_TARGET_ACTIONS 本身）。

★但推演一遍發現：這種騙法在 (b) 底下也會紅——往 TEAM_TARGET_ACTIONS 加一個
假名字會讓 `.size()` 變成 12，而「總數 = 12」這個斷言會跟（沒有同步更新的）
手抄陣列的 10/11 個名字對不上 ⇒ 計數比對本身就會失敗。⇒ (b) 其實已經間接
擋住「讀 size 但抄名字」這種騙法，不需要額外一格。

★真正擋不住的是更窄的一種：兩份名字陣列（一份是 TEAM_TARGET_ACTIONS，一份
是全列版自己手抄的）**每次都手動同步**，導致兩道負對照擾動時都會被一起改
（因為維護者會同時改兩個地方）。這不是這兩道動態擾動測試能力所及的範圍——
這是本 session 今天在多張票上反覆驗證過的形狀：行為擾動測不出「複製了一份
但保持人工同步」，需要一道**靜態互證**（grep 全列版那段程式碼的原始碼，
斷言它逐字含 `TEAM_TARGET_ACTIONS`／`.has(...)`／`for x in TEAM_TARGET_ACTIONS`
這類【引用】而不是一個獨立的陣列字面量）。

⇒ 建議：加一格靜態證（同同格票 P2(a)、NPC索貢那票我建議的加固同一手法），
跟現有兩道動態負對照互補，不需要因此推翻或縮減現有設計。
```

# 二、②`recruit` 不列——核過區分站得住，建議收緊措辭

```
判斷成立：這是 WHAT 層已經裁過的決定（藍圖④），HOW 層的正確執行是【排除】
不是【列出來設 false】——因為 `enabled=false` 語意上意味著「這個動作存在、
只是這次條件不符」，而 recruit 泛用版根本【不存在】（STUB），把它跟其他
「存在但暫時做不到」的動作放進同一份列表、只是多加一個布林值，會讓玩家/
下一個工程師誤以為它是「跟 extort 一樣，某天條件夠了就會出現」，而事實上
它需要的是【實裝】不是【條件變化】。這個區分在語意上站得住。

★你自己點名的風險（下一個人讀成「這個動作被停用了」）——判斷：關鍵不在
「列不列」這個結構決定本身，而在【排除理由那句話寫了什麼】。若那句具名
理由只寫「STUB」或「未實裝」這種技術詞，讀者容易望文生義成「暫時關掉」；
建議措辭明確區分「尚未實裝此機制」（recruit 泛用版）跟「條件不符」（其他
enabled=false 動作），例如「recruit：此為規劃中機制的佔位識別符，尚未有
對應實作，不在可用動作枚舉範圍內」——把「機制不存在」講清楚，不留模糊
空間讓人聯想到「暫停/停用」。
```

# 三、③P4 嚴格順序比對——核過不會誤紅唯一被授權的實作路徑

```
直接讀了 production 現行 `get_available_actions`（player_command_system.gd:39-61）
逐行 append 順序：ignore, attack, [trade], [propose_alliance], [demand_tribute],
[extort], [recruit], [recruit_anon], [invite_settle], gather_intel, beg
——跟 `TEAM_TARGET_ACTIONS`（:196-198）宣告的字面順序逐字相同：
  ["ignore","attack","trade","propose_alliance","demand_tribute","extort",
   "recruit","recruit_anon","invite_settle","gather_intel","beg"]
這不是巧合：spec §2②要求的衍生手法（`全列版.filter(enabled).map(action_id)`，
而全列版本身照 TEAM_TARGET_ACTIONS 的順序迭代）在結構上必然重現這個順序，
因為 filter/map 保序、且母體的迭代順序就是常數宣告順序。

⇒ 「順序也一樣」這條嚴格斷言核過不會誤傷【唯一被授權的實作路徑】——因為
spec 本身沒有給第二種合法構造方式（不是「多種寫法都對、其中一種恰好順序
不同」，是「只有一種寫法，而它自然保序」）。你想留著這條嚴格斷言的直覺
是對的，代價趨近於零：只要照 §2②的衍生手法寫，順序自動一致，不需要
額外費工維持順序；若有人未來想用另一套邏輯重寫（不走 filter/map），
那本來就違反 §2②「一個真相一份」的結構要求，該紅。
```

# 四、④刪除檔頭手寫表——核過理由成立，判斷不需要額外指標留言

```
同意你的處置（不留指標，靠 `disabled_reason` 本身承擔可讀性）。理由：
`disabled_reason` 跟產生它的 if 條件天生同處一支函式、同一行回傳語句
（spec §2①「原因與判斷同一個回傳」），這個【物理鄰接】本身就是最強的
可讀性保證——想知道「demand_tribute 為什麼不可做」，讀那一支函式的
if 分支跟讀到的 disabled_reason 字串是同一段程式碼，沒有第二個地方要查。

★若額外加一個「指標留言」（指向哪些 if 在哪），那個指標本身會變成
【第三份要手動維護同步的東西】——跟被刪掉的手寫表同一個病，只是換了個
更輕量的形狀。本 session 今天已經在多張票上驗證過「任何獨立於真判斷之外
的第二份描述都會漂」，這裡沒有理由破例。不建議加指標，你的答案（
`disabled_reason` 本身已經是最終權威）判斷正確。
```
