# ★一、從 code 證，不是從量

```gdscript
static func _faction_due(state, f, batch) -> bool:
	for mid in f.member_team_ids:
		if batch.has(int(mid)):
			return true          # ★批次裡【任一】成員到期 ⇒ 整個勢力的活做一遍
```

```
今天（不錯開）：批次 ＝ 全部隊 ⇒ 每個勢力每小時 due 一次 ⇒ 整個勢力的活做 1 次
錯開之後      ：每隊在【不同 tick】到期
              ⇒ ★一個 M 成員的勢力每小時 due 在【M 個不同的 tick】上
              ⇒ ★★_evaluate_all_body 把整個勢力的活做 ~M 次而不是 1 次
```

★**這是一條推導，不是量測** —— 但它不需要量：`_faction_due` 的語意就是「任一成員」。

# ★★二、而抓它的守衛已經在註冊表上，是我兩票前自己寫的

```
faction-drive-once   expect: \[FACDRIVE\] per_hour_max=1  drives_total=[1-9][0-9]*
⇒ ★per_hour_max 的定義就是【同一勢力在同一小時被驅動幾次】
⇒ ★★在這支分支上它會讀到 ≈ M（最大勢力的成員數），不是 1 ⇒ **必紅**
```

★★★**而那個守衛是為了【前置票】寫的，它抓到的是【這一票】** ——
我當時寫的註解逐字是：**「它是回歸柵欄不是陽性對照：今天不散相位本來就該是 1，
它守的是【散相位之後仍然要是 1】」**。
⇒ **散相位來了，而它就是來擋這個的。**

# ★★★三、所以這是【正確性】不只是效能

```
不是「同一件事做慢了」，是【同一件事被做了 M 次】。
★而 faction_ai 佔最壞 tick 的 50.8%（你開票時量的）
⇒ 那一半乘以 M（我上一輪量到 8 個勢力／74–80 隊 ⇒ 平均 M ≈ 9）
⇒ ★★這解釋得了 >600s，而「迴圈跑 60 倍」解釋不了（那是秒級）。
★★★而它同時也是【行為改變】：一個勢力每小時做 9 次決策 ≠ 做 1 次
  ⇒ 指紋當然會變，但那不是「錯開造成的世代 8」，是【重複執行】。
  ⇒ ★如果我們就這樣 merge，世代 8 的邊界會把一個缺陷醃進基線。
```
