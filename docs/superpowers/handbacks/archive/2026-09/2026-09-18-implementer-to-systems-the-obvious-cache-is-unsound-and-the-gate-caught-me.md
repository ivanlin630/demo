# 二、★★★我的修法不合格（**閘抓到我**）

形狀：`gather()` 對 `(世界, 隊, tick)` 做記憶化，只給無副作用那條路（`advance == false`）。
動機是量到的：2 天 77 隊 ⇒ gather 1495 次、**同 (隊,tick) 重複 419 次（28.0%）**、
重複那些次耗時 **5.06s／17.83s（28.4%）**、單 tick 最多 **150 次**。

結果：

```
                 fp                                  行為軌跡
修法前（乾淨）    3951597c0fd9545eeb7e909ceb6bf5df    3496867408
修法後（記憶化）  47f569ae0adc8528a3eda4db386a4ab3    4003349826
⇒ ★★兩個都變了 ⇒ 格 1-e【紅】⇒ **這個修法違反「禁降真實」**
```

# 三、根因（★量的，不是推的）

我加了一個診斷模式：**命中快取時照樣重算一份，逐欄比對**（反射列舉欄位，不手抄清單）。

```
1200 tick／69 隊：命中 44 次｜★其中與重算【不同】 29 次（65.9%）
  current_task        27 次   ← ★主凶
  need_urgency        26 次
  absorb_target_id/absorb_yield 各 3｜team_strength/self_armed_ratio/winnable/ambient_train_drive 各 2
  recon_value_est／farmable_pos／leader_values 各 1
```
⇒ ★**引擎排序完會把決策【寫進世界】，而 `to_task` 的那次 gather 是在那之後** ——
所以它看到的 `current_task` 本來就該是新的。**記憶化讓它看到舊的。**
⇒ ★★**那 28% 不是浪費，是【兩個不同時刻】** —— 我把「重複」讀成「多餘」了。

★★★**順帶一個我自己的儀器錯誤，一併報**：第一版逐欄比對用 `str()` 比，
而 `camp_target_est` 是**物件欄位** ⇒ `str()` 印的是**實例位址** ⇒ 它被報成「44／44 次都在變」。
**那 44 次一次都不是真的**（是我的比較器在動，不是世界在動）。修法＝物件欄位單獨記、不算差異。
⇒ ★**這就是為什麼我把「65.9%」這個數重跑過才寫給你** ——第一版會寫成 100%。

★**我推薦 (丙)**，理由三條：
1. **它不是快取** ⇒ 沒有失效清單問題 ⇒ **「同樣輸入同樣輸出」是構造保證，不是經驗保證**。
2. 它砍的是**整份蒐集**（`to_task` 只要 1–2 個欄位卻付了全套的錢）——★**這才是真正的浪費**，
   而 (甲) 只能省下已經被我證明**不能省**的那一小塊。
3. ★★★它**不會改變 `current_task` 那個時序** —— 那正是 (甲)(乙) 會踩到的地雷。

★★**而 (丙) 有一個我先講的風險**：`to_task` 改成直接算它要的那一兩個欄位 ⇒
**那段算式會有兩份**（gather 裡一份、to_task 一份）⇒ ★**兩份會 drift，而 drift 不會有東西紅**。
⇒ 解法是**抽成同一支小函式，兩邊都呼它**（＝你們一直在做的「單一計算點」）。
★★★**這一步是架構決定，所以我停在這裡等你裁** —— 不是停工：我同時在做 §5。
