# 徵收執行真實性（優先題）—— 比備戰更隱蔽的同型 bug

## 方法
seed42，137 次「徵收」argmax 勝出。逐筆核對 `result` 分布，再對 29 次 `committed` 逐筆追蹤該隊 `tile_pos` 與 `coin` 在後續 12 筆 entry 的軌跡（不是只看下一筆——這次我學乖了，先確認過關的真的走到目的地才算數）。

## 結果
| 層 | 數字 | 意義 |
|---|---|---|
| **argmax 贏** | 137 | 卷面 81.2% 的來源 |
| **dispatch 失敗**（`try_set_noop`） | **108（79%）** | 連任務都沒設上，跟「贏了但沒發生」是同一件事的第一層 |
| **dispatch 成功**（`committed`） | 29（21%） | |
| **committed 之後 tile_pos 凍結、從未移向 target** | **24／29（83%）** | ★★★這是本題真正的發現——**「committed」這個字本身在這裡會騙人**：任務設上了，但隊伍原地不動，`task` 欄位在 1～3 個決策週期內被靜默換成別的（`建設`／`貿易`），從頭到尾沒有出發 |
| **真的移動且抵達 target** | 5／29 | |
| **★驗證到「抵達後逐 tick 真的收到 coin」的乾淨案例** | **1（team16）** | 見下 |

## team16——唯一驗證到的完整成功鏈
```
tick70200 tile=[0,14] task=徵收（committed）
tick70800 tile=[0,13]                        ← 真的在移動
tick71400 tile=[1,12]（抵達 target）coin 62.5→81.7375
tick72000 tile=[1,12]（仍徵收）coin →96.6465625
tick72600 task 換成 迎戰                       coin →108.20
```
**抵達後每個決策週期 coin 持續增長，同格、同任務、逐次累加——這是機制設計上「應該長什麼樣」的示範。**

## 對照——典型失敗案例（team0／team1／team10 都是這個形狀）
```
team1 tick1200 tile=[2,7] task=徵收（committed）target=[1,12]
tick1200~2400 全部仍在 tile=[2,7]（★完全沒動）
tick3000 task 已換成「建設」（★徵收從未真的出發，就被下一輪決策蓋掉）
```
**⇒ 這不是「贏了但因為某個資源門檻付不起」（那是我上一票的頭條形狀），是「贏了、任務設上了、但移動從未被觸發，於是任務在下一輪就被別的候選蓋掉」——比備戰的 `finder_miss` 更隱蔽，因為字面上 `result=committed`，不看 `tile_pos` 軌跡看不出來是假的。**

## ★信心界線
- **這 30 個樣本（137 argmax／29 committed）全部逐筆讀過，file:line 我沒有查**（不確定是移動 dispatch 那一步的問題還是別的）——這次我只驗證了「現象」，沒有像上次一樣同時坐實 code 根因，是因為 seed42 抽樣範圍內找不到夠多完整案例讓我定位到哪一站——**建議請 implementer 查『徵收 committed 後 movement_system 有沒有真的收到移動指令』這一格，比我猜快。**

# 其餘三題

## ①JOIN 併成之後發生了什麼——★乾淨正面案例
**team19**：merge 前後在**同一個 tick（41400）留下前後兩筆快照**：

| | merge 前 | merge 後 |
|---|---|---|
| faction_id | -1（無政權） | **1** |
| coin | 0 | **58.33** |
| food_private | 0 | **4.08** |
| material | 0.08 | **6.9** |
| pop | 1 | **2** |
| parent_team_id | 5 | 0 |

**這隊當時 food=0/coin=0，是個瀕死的孤兒 splinter——併入之後五項數字同時跳動，是真的被救了。** 這是我讀到的一個具體例子，不是全域「50 次都這樣」的宣稱——但它證明「resolve」這個新機制在至少這一例是**真實、有意義的救援**，不是又一次幻影。

## ②共位互動新增的類型（照原樣列，不解讀）

