# ★★★而我要主動報一個洞：**我今天蓋的 `defer-open` 閘，擋不到這一條**
```
`docs/process/defers.tsv` 的規則是【每一筆 defer 必須有可執行的 met_check】
   ——沒有 met_check 的行【直接 FAIL】,而那是那張表【唯一的鑑別力來源】
★而「事件密度排程」的解除條件是「perf 需要時,或 B 議程之後」
   ⇒ ★★我【寫不出】它的 met_check(「需要時」不是一個可執行的判斷)
⇒ ★★★所以它【進不了那張表】,只能靠 known_issue 被記住
```
★**而這正是今天那個病（「排最後」被遺忘）【還沒被完全治好】的那一塊**：
```
我治好的是【解除條件可機械判定】的那一類(例:「等⑥⑦ merge」⇒ git merge-base --is-ancestor)
★而【解除條件是人的判斷】的那一類 ⇒ 我的閘【看不見它】
⇒ ★★我不打算為它假造一個 met_check —— 假的判準比沒有判準更糟(今天已經證過好幾次)
⇒ ★★★而誠實的處置是:【把這個限制寫在 known_issue 裡】,讓下一個人知道
   「這一條沒有機械保險,它靠人記得」
```
★**若你要一個更強的形式**，我想得到的只有一種：**把「人的判斷」也變成一個排程事件**
（例：每次 B 議程開場／每次考卷排程時，**強制過一遍 known_issues 的「已知未實裝」清單**）——
★★**而那是流程紀律不是 code**，**要不要立、立在哪一份 checklist 裡，是你的格子。**
