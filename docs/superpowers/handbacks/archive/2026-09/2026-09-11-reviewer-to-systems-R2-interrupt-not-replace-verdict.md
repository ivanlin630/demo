# R² 判決：`2026-09-11-interrupt-not-replace-HOW.md`

## 判決：非 CLEAN——(3) 抓到掃描閘的真實邊界，(1)(2) 方向對但各補一句

## (1) 覓食會不會真的餵飽：查了執行端，機制上是真的會加糧，而且有一個「吃到夠就停」的設計——但量化問題只有你的測法能回答

```
resource_system.gd:89-90   L0被動forage: ResourceBank.add(team,"food",draw,"l0_forage")
hunt_system.gd:24-28       主動狩獵: ResourceBank.add(team,"food",banked,"hunt")
hunt_system.gd:14          ★已達buffer → 不獵（不擲骰、不耗wild_game、不bank）
                            —— 這行comment透露有一個【飽足上限】概念,不是無限索取
```

這證實覓食**不是空轉的no-op**——它真的會把food加進團隊，而且獵殺邏輯本身有一個
「夠了就停」的buffer概念，跟你要的「插斷後有機會自然結束」方向一致，不是純粹的
一廂情願。**但這只回答了「機制存在」，回答不了「這批隊在4.6天的赤字下，這個機制
夠不夠快把food_days拉過門檻」**——那是純量化問題，讀code讀不出來（跟今天稍早
「靜態讀code的認識論界限」同一條），你寫「先量再做」是對的，也是唯一能回答的方式。
沒有找到反例讓這個前提整個垮掉，方向CLEAN。

## (2) 兩個門檻可不可達：90%相對可信；30%建議先綁一個獨立的baseline存活率量測，避免撞到結構天花板

`恢復率≥90%`主要是**修法自己的機制正確性**（release()→re-rank→重新可選 這條路走不走得通），
不太受外部因素干擾，只要`unfinished()`/`serves()`真的接對（見item3），這個數字理論上
是可控的。

`到場率≥30%`不一樣——它額外疊了一層**這批隊本身能不能活著走到目的地**的風險，
而這批隊存糧中位只有4.6天，若光是路途中的自然餓死率就已經逼近甚至超過70%，
那麼即使「插斷非取代」做得完美無缺，到場率仍然可能摸不到30%——這是**跟今天
「驗收落在世界的不可達區間」同一族的風險**，你自己點名了但沒展開。

**建議**：把「求居-selecting隊在【不受插斷/取代干擾】情況下、單純因路途死亡而
到不了目的地的比例」也一起量（可以併進§③已經要跑的那次量測，不用另開一輪）——
若baseline存活到達率本身就低於30%，門檻要往下調整成「baseline+顯著改善」而不是
絕對值30%，否則這格可能天生綠不了，而那會被誤讀成「修法沒用」而不是「門檻設太高」。

## (3) 承諾語彙引用：沒有引錯，但抓到掃描閘的真實邊界——它只逼【欄位分類】，不逼【unfinished()真的長出新分支】

讀了 `commitment_fields.gd` 全檔——你引的三處都準確（:38 `solo_task_last`分類逐字對得上，
`READS`/`NOT_COMMITMENT`結構、掃描閘的自動抽取邏輯都如你所述）。**但掃描閘的覆蓋範圍
比你想的窄一格**：它的母體是「`team_data.gd`裡宣告的頂層`var`欄位」，逼的是「每個
頂層欄位都要出現在READS或NOT_COMMITMENT裡」——**它不會逼`unfinished()`函式本身
真的新增一個辨識求居承諾的分支**。

具體風險：現有的convoy承諾（:74）不是用一個新的頂層欄位存的，是塞進**既有**
`task_extra_data`字典裡的一個key（`convoy_phase`）——`task_extra_data`本身早就是
`READS`裡的一個項目（:21），所以convoy的sub-key**從來沒有被掃描閘逼著分類過**，
它能運作純粹是因為`unfinished()`裡有人手寫了:74那段讀取邏輯。**若求居也照這個
形狀（塞進task_extra_data的一個key，不開新頂層欄位）**，掃描閘會**完全看不到它**
（因為`task_extra_data`已經在READS裡,母體不會多一列)——你原本擔心的「掃描閘會不會
擋不到我加的那個欄位」，答案是：**若你選這個形狀，閘確實擋不到，但那不是閘的漏洞，
是這個形狀本來就不歸閘管**；閘只保證「新開的頂層欄位」不會被忘記分類。

⇒ **無論選哪種形狀，真正需要的保證都不是掃描閘給的**：
```
若開新頂層欄位 ⇒ 掃描閘會逼分類（好），但仍不保證 unfinished() 真的讀它
若塞進 task_extra_data ⇒ 掃描閘完全不會提醒你（母體不變）
```
**要求**：不管選哪個形狀，驗收都要**額外加一格**（不能只靠掃描閘）：
「構造一支有求居承諾的隊 ⇒ 直接斷言 `CommitmentFields.unfinished(state,team)`
回傳 `{kind:"settle",...}`（非空）」——這格是掃描閘保證不了的，必須自己驗，
且要連 `serves("settle", <求居對應的task>)` 也一起斷言（同convoy在:97-106的形狀）。
