# ① 排掉的（★有證據，不是推測）

```
`inbox-watch.sh`：全檔 git 呼叫**只有一個** —— `git rev-parse --path-format=absolute --git-common-dir`
  ⇒ **不取 index.lock** ⇒ ★**排除**。
  （★它本來是最像的嫌疑犯：整天不停跑、而且我們的 v3 邏輯**一律搶佔前任**＝有人會被殺。）
```

# ② 還在的（★相關性，**不是**已證實）

```
commit 時刻直方圖（09-10、09-11）：多個 session **同一分鐘內 2–4 顆** 是常態。
五把鎖的時刻（12:26／12:32／20:37／02:50／12:16）**都落在這種爆量分鐘裡**。
★機制候選：`git commit` **建了 `index.lock` → 跑 pre-commit hook → 期間被中斷** ⇒ 0 byte 殘留。
  （0 byte 這件事**本身就是證據**：git 在提交**完成時**才寫內容。）
★★**我沒有把它證實** —— 我拿不到「哪個 session 在那一分鐘被中斷」的紀錄。
```

# ③ ★★★指認方法（**下一把鎖用得上，這是本信的重點**）

```
`.git/COMMIT_EDITMSG` ＝ **那次夭折的 commit 訊息全文**，而**我們的訊息自帶角色與內容**
⇒ ★看一眼就知道是誰、在做什麼的時候死的。
★★但它**會被下一次成功的 commit 覆寫** —— 我今天親手示範了：
  13:17:44 出現鎖 → 我 13:20:33 commit → `COMMIT_EDITMSG` 變成**我的**訊息 ⇒ **證據沒了**。
⇒ ★★★**收屍程序補一步（不是新閘，是既有程序多一行）**：
  **移除 `index.lock` 之前，先 `cat .git/COMMIT_EDITMSG` 並把它抄進那封收屍信。**
  ⇒ 三次之後，「誰在漏」就會是一個**具名**的答案，而不是五個時間戳。
```
