# 派工：死輸入探索床

**spec** `docs/superpowers/specs/2026-09-29-scripted-exploration-bed-HOW.md`（上游票：
`2026-09-29-blueprint-to-systems-TICKET-scripted-exploration-bed-all-verbs-four-rules.md`）
**為什麼現在**：用戶早先逐字「**先跑死輸入**」，而藍圖要它的**人可讀矛盾清單**交給用戶。
我先前把它排在同格檢查票之後（理由：否則它會在一個能隔空索貢的世界裡量數字）—— **那張已 merge**。

## ★★★一、命門：陽性對照要跑在【修法前的 sha】上

spec §2③ 指定用戶兩輪撞到的三件當陽性對照，而**今天已經修掉兩件** ⇒ 對照的做法要跟著改：

```
①招募扣錢而搬 0 人      ⇒ 修法前 sha `05befff7f` 之前
②接受變拒絕（propose_alliance 不在 match 裡）⇒ **今天修掉了**（提案字串那一票）
③「Team11 提議 alliance」原樣 id            ⇒ **今天修掉了**（#7①③）
⇒ ★所以 ②③ 的陽性對照**必須在舊 sha 上跑**（例如 `fcc77268a` 之前的某顆），
  在今天的主線上跑它們【本來就不會紅】—— 而那個綠**不是床有效的證據**。
⇒ ★★做法：陽性對照那一段用 `git worktree add <舊 sha>` 起一棵**唯讀的舊樹**跑，
  卷面上把【跑的是哪一顆 sha】印在同一份輸出裡（★不是寫在信裡）。
⇒ ★★★而若第二件在舊 sha 上**綠**：**印出實際結果句給我們讀** ——
  那表示我們對那個症狀的理解是錯的，而那比床紅更重要（spec 明寫）。
```

## 二、母體：三層，三個數，各自跟常數比（不要手抄、不要自動採用新值）

```
層1 `PlayerCommandApi.dispatch` 頂層動詞 ＝ SPEC_VERBS_L1=14
層2 `_action_registry` 鍵 ＋ `execute_action_with_target` 的 case ＝ SPEC_ACTIONS_L2=51
層3 forced_event 的 action 種類 ＝ SPEC_FORCED_L3=5（回應集用 `_forced_responses()` 動態拿）
⇒ 三個數都印、各自跟常數比；★對不上 ⇒ **床紅並印差集**（哪個多哪個少），
  ★★**不是自動採用新的數**。
★★★而上游那個「37 動詞」到現在仍然對不上任何一層 ⇒ 你**不猜它指哪一層**，
  也不拿你的數去覆蓋它；spec §1③ 已經寫著，照原樣執行。
```

## 三、四條每步都要核（spec §2②）

```
(a)守恆：用既有 CoinAudit／InvariantAudit，★不新寫一份
(b)回應↔結果一致：accept 之後結果句／事件流不得說「拒絕」
(c)必有回饋：每一次 command 都要產出一句玩家看得到的句子
(d)★玩家面字串零英文識別字，而★★白名單要印出來（Team%d 這類）
   —— 否則它會變成一個沒人看得懂的紅
```
★而 (b)(c) 今天已經有一批同族守衛落地（按鍵三態／結果句），所以它們在**今天的主線**上
應該大致是綠的 ⇒ **那不是這支床沒用**：它的價值在**母體是全部組合**，而那些守衛各自只看一條路。

## 四、產物與掛閘

