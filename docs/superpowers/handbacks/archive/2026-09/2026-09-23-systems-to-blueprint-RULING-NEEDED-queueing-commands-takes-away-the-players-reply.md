# ★★★二、要你裁的那件（玩家語意，不是技術選型）

```
現在：玩家按鍵 → 指令【立刻套用】→ 回傳 {ok, message} → 畫面印出那一句
   （例：「你把隊伍移到 (3,5)」／「那裡太遠了」）
佇列化後：玩家按鍵 → 指令【排進佇列】→ 回傳 {ok, queued, seq}
   ⇒ ★**那一刻沒有任何結果可講**，因為它還沒發生
   ⇒ ★★而 TextUI 平常是【停住】的 ⇒ 下一顆 tick 可能永遠不來
   ⇒ ★★★玩家分不出「排進去了」與「我的鍵沒被吃到」
```

**四條路，與它們各自的代價（★HOW 的代價我標出來，好讓你的選擇是知情的）**：

| | 做法 | 玩家看到 | ★代價（HOW） |
|---|---|---|---|
| 甲 | 回饋延後到消費點 | **世界停著時什麼都沒有** | 最單純、最決定性；★但它把「沒反應」變成常態 |
| 乙 | 入列時印「已排入：<動作>」 | 立刻有回音，但**不知道會不會成功** | 便宜；★「那裡太遠了」這類錯誤**全部延後或消失** |
| 丙 | 按鍵本身推進一顆 tick | 跟現在幾乎一樣 | ★★決定性仍在（指令仍綁在一顆具名的 tick 上）；★★★但**每次按鍵都會讓時間前進**＝改了遊戲節奏 |
| 丁 | 入列時做**不改狀態的合法性檢查**，立刻回「可以／不行＋原因」，真正結果仍在消費點 | 立刻知道合不合法，結果稍後 | ★★★**檢查邏輯會與套用邏輯分成兩份** ⇒ 它們會漂開 ⇒ **兩個真相**；而漂開的那天，畫面說可以而世界說不行 |

★**我的傾向（僅供參考，不是裁定）**：丙或丁。★★甲我同意 implementer 的判斷——單獨用不行。
★★★而丁那條的代價是**真的**，不是理論：我們今天才剛因為「比對器與它想描述的語意漂開」修過一支閘。
