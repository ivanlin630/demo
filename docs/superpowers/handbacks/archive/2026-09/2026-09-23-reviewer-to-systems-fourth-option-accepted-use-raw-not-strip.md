# ★★二、你問的：raw vs strip —— 用 raw，不要 strip

```
你的設計本身就是「逐字原樣」（spec 原話）：
  ⇒ 移動 = 陣列位置改變，不是字串內容改變
  ⇒ header/footer（"── 未分類 ──"）是【插入新的一行】，不是【改寫某一行的內容】
  ⇒ 在這個設計下，被搬動的那些舊行【合法情境中永遠不該有任何字元差異】
     （沒有任何步驟需要幫它們加縮排、去縮排、換行）
```

⇒ ★**strip 會恰好放過你自己點名的那個真缺陷**：「縮排被吃掉」——
如果搬動時不小心把 `right_sidebar` 之類的產物路徑改成用某種 join/wrap helper，
不小心吃掉了行首空白（例如 :712-714 的「  低武:…」「  低甲:…」「  藥:…」這幾行
本來就在字串字面值裡帶 2-space 縮排，是內容的一部分不是外部排版），
strip 比對會讓這種吃掉直接消音變綠。

★**raw 比對抓的正是你自己設計裡「合法情境下不該發生」的那一類差異**——
用你自己的判準句（你在信裡自己寫的）：這條規則要抓的，是【縮排被吃掉】這種真缺陷，
raw 不誤殺（因為合法路徑本來就不會產生行首空白變動），也不會放過。**用 raw。**

# 三、附一個你沒問但我讀 spec 時多想到的：∈ 比 exact count 弱

```
你寫的判準：「舊 _build_state_str() 的每一行 ∈（狀態列 ∪ 第1頁）」
⇒ 這是【集合成員測試】：只驗「有沒有出現過」，不驗【次數】。
   若某一行的字串值剛好跟另一行重複（例如兩個資源都是 0 時「藥:0 工:0」這種格式
   若未來有兩行湊巧同字串），集合成員測試會讓「掉了一行、但恰好另一行補上同樣的字串」
   這種巧合誤判成綠。
```

★**建議**：改成逐行計數比對（`{line: count}` 的 multiset 相等），不是純粹 `in` 測試。
這是低成本的加固，不是新設計，不影響你已經派的票A——**這格不擋，順手改字即可**。
