# 判決：`issues`，`premise_contradiction: false`

## ①二分（能精確／不能精確）——**不夠，有第三類，而且它比(b)更危險因為它不會讓fp變紅**
你的(a)/(b)分法漏了一種：★★★**數值上剛好被 `hours()/days()` 整除，但語意上根本不代表「N小時／N天」，是一個湊巧整除的獨立遊戲常數**——例如某個裸值恰好等於 10（＝現制 `TICKS_PER_HOUR`），但它原本代表的是「戰鬥冷卻10 tick」這種跟真實時間長度無關的遊戲節奏數，不是作者故意寫的「1小時冷卻」。

★**這一類的危險在哪**：把它誤判成 (a) 類、改寫成 `hours(1)` ⇒ **現制下 `10==hours(1)=10`，`fp` 完全不會變紅**（S1 驗收①測不出來）——**但等 S2 真的改根旋鈕，這顆本來該保持「10 tick 不變」的常數，會被誤牽著一起縮放，變成一個 S1 埋下、S2 才會爆炸、而且 S2 事後很難追溯回「是 S1 那次誤判」的語意 bug。**這正是「機械可判斷≠正確分類」——跟今天好幾票撞到的同型（合併路徑寬度不比對、default值範圍算窄）。

⇒ **要求**：逐顆人工判定 (a) 類時，除了「能不能被整除改寫」，★★**要多問一句「這個數字的原始意圖是不是真的隨『小時』這個真實時間單位縮放？」**，判定理由（連同(b)類清單、白名單一樣）要留在 code 裡寫成註記——不是只判「數字對不對得上」，要判「概念對不對得上」。這條不是要你重新設計，是幫①的操作型定義補一格人工檢查項。

## ②-1候選集會不會漏——**會漏，而且我查出比你想的更根本：現有 `time_const_check.gd` 目前完全沒有掃描能力**
我讀了 `scripts/debug/time_const_check.gd`（25 行）——★★**它現在只是硬編 10 個具名常數的數值比對表（`INDEP_STRATEGY_CADENCE==720` 這種），沒有任何一行在掃描原始碼、找裸字面量。** spec 寫「擴充它成規約守衛」，但要擴充成的東西（能找出「跟 `current_tick` 等符號同運算式的裸 int」）**現在完全不存在，是從零建**。

★★★**這件事本身讓你問的「候選集會不會漏（例如先存進沒有 tick 字樣的變數再比較）」變得更嚴重**：GDScript 沒有現成、輕量的 AST introspection 可以在一支 `.gd` 除錯腳本裡呼叫，這支守衛**幾乎必然是文字/正則掃描**（grep 同運算式裡的符號名稱），而**文字掃描天生看不到「值先被存進一個改名字的區域變數」這種別名情況**——這不是 S1 盤點一次性的漏洞，是★★★**這支守衛長期、永久的盲點**：只要有人先寫 `var t = current_tick` 再拿 `t` 去比裸值，S1 盤點看不到，未來的守衛也看不到，兩層都失守。

⇒ **要求**：把這條寫進「誠實限」，跟「白名單擋不住已經在白名單裡的」並列——**「守衛是文字比對，看不到把 tick 存進改名變數後的比較；這是已知盲點，不是本票能關的洞」**。誠實承認比假裝守衛完備更有用（同今天別票的紀律）。
