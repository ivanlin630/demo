# 判決：`issues`，`premise_contradiction: false`

## ①②號約束——**必要,你沒把問題想大;但輪轉公式有個你沒問到的邊界風險**
**(a) ②是不是必要**：必要，而且理由比你寫的更根本一層——★**就算①的 hash 完全打散、offset 跟 team_id 的任何既有屬性都不相關，只要 offset 是【固定終身】的，「誰抽到好位置」這件事本身會【隨時間複利成優勢】**：早想的隊先搶資源，這個優勢會滾雪球，滾到某個時間點去量測「offset 分桶 vs 結果」，你會量出【offset 導致的】系統性優勢——不是因為 team_id 本來就跟強弱相關，是因為【固定 offset 這個機制本身】會把一次性的抽籤結果變成永久特權。①防的是「起手不公平」，②防的是「起手公平但機制自己把它變不公平」，這是兩個不同的病，只做①防不住②那個。**你的直覺是對的，不是想太大。**

**(b) ②有沒有引入新問題**：
- **`cycle_index` 從哪來**——spec 沒講明。★**它必須是〈`current_tick` 的純函式〉（例如 `current_tick / CADENCE` 整除），不能是另外存的遞增計數器**——否則就真的變成你擔心的「另一個要同步的狀態」（存檔/重播/多執行緒都要跟著同步這個新變數）。這件事要求寫進 spec，不能留給 implementer 自己選，兩種選法差很多。
- ★★**我查出一個你沒問到的邊界風險**：`(hash(team_id)+cycle_index) % CADENCE` 這種【全範圍重雜湊】的輪轉，相鄰兩週期的 offset 差值可以落在 `[-(CADENCE-1), +(CADENCE-1)]` 任意值——**意味著一隊連續兩次思考的間隔，最短可以逼近 1 tick**（若這週期 offset 剛好落在週期尾、下週期 offset 落在週期頭附近）。這不只是「同隊思考間隔不均勻」（你已經預期到、能接受的那種抖動），是**可能在某個 tick 意外疊出一個新的迷你 burst**——剛好違背這票的初衷（打散尖峰,不是換位置搬尖峰）。
  ⇒ **建議**：輪轉用【有界步進】而非全範圍重雜湊，例如 `offset = (offset_prev + step(team_id)) % CADENCE`（`step` 是一個小的、per-team 固定位移，逐週期累加而非重算），這樣相鄰週期 offset 差值有界（=`step` 的量級，可以控制在遠小於 `CADENCE` 的範圍），既滿足「逐週期變化、長期不固定排前面」，又不會製造相鄰週期間隔驟縮的邊界案例。★**這條要驗**：spec 補一句「相鄰週期同隊 offset 差值上界是多少、由此推出思考間隔最短可以是幾 tick，確認那個下限不會意外造出新 burst」。

## ②全局 wall 不可用，你改的驗收會不會被「改 cadence 長度」矇混——**會，而且你自己也知道，只是還沒把它從文字變機制**
你寫「已寫死不得改 cadence 長度，但那是文字不是機制」——★**這句本身就是答案：光靠文字擋不住，今天在別的票上已經反覆驗證這件事（default 值、迭代順序、pin……凡是只寫在 spec 裡沒有機械檢查的規則，遲早被繞過或無意間違反）。**
⇒ **要求（機械化，便宜）**：驗收加一條 **`CADENCE` 常數本身的數值在這票前後必須逐位元相同**（`grep -n 'CADENCE\s*=' faction_ai_system.gd` 前後對比，或更硬：`estimator-lineage-scan.sh`／既有的常數掃描機制若能覆蓋到它，直接掛上去）。**這樣「改長度矇混過關」在改動當下就會被機械攔下，不用等驗收①②的統計數字被動察覺。**

## ③驗收3「不保證spike中位數下降」——**是誠實限，不是免責條款；但它的誠實性【依附】在②有沒有被機械關住**

★★**但它會不會變成免責條款，取決於驗收①②是不是真的硬**——若①②可以被「改 cadence 長度」繞過（見上一段），那這票就可能在【什麼都沒真的修】的情況下，靠①②的數字表面改善 + ③的「不保證」當擋箭牌，交出一張看起來合格實則空的票。**加了②的機械 guard 之後，①②變成真正卡得住的硬指標，③的誠實限才名副其實——這兩件事是配套的，不是各自獨立。**
