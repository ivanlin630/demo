# QA 故事稽核：convoy RETURN v2 — 血緣修有效，但覆蓋窗斷在關鍵前

**先講好消息**：`team_id` 確實出現 `12/19/20`（porter 子隊），`parent_team_id` 正確指回 `5/7/3`——**血緣封閉修真的生效了，這條路走通了**。

**但這輪判不了，換一種原因**：讀完 3 隻 porter 全部 56 筆原始 entry，逐一核對追蹤窗口 vs 它們實際完成故事所需的時間，發現**追蹤在關鍵時刻前就斷了**。

母隊 3/5/7 全程被追蹤到 `tick=21600`（day90，窗末）——**母隊追蹤沒問題，全 90 天在**。三隻 porter 對照：

| team12(parent=5) | tick=2400(day10.0) | tick=3000(day12.5) | **tick=4560(day19.0)** | +6.5天 | 若「9.2天」是RETURN耗時→應在day**21.7**才歸建，**斷點還差~2.7天** |

**三隻全部在真正的結局（rehome動作/歸建/卡死狀態）發生前，追蹤就停了**——porter12停在還在RETURN途中(material=31不變、food緩降到10.0)；porter19/20更早，RETURN剛起步(60-260 tick後)就斷，完全沒看到後續。**7次rehome一次都沒被錄到**（convoy_phase欄位在RETURN期間只設一次就不再變，rehome本身不改這個欄位值，本來就看不出「第幾次rehome」——這是另一個更小的缺口，見下）。

## 兩個具體缺口，供你派修

1. **★覆蓋窗缺口（本輪主因）**：porter 的取樣在 RETURN 進入後很快斷（分別 +6.5天/+0.25天/+0.25天），母隊卻全程 90 天都在。懷疑是「母隊在範圍⇒子隊自動在範圍」這個血緣判定是**周期性重算**、而非**一旦納入就持續追蹤**——子隊可能只在某次重算窗口內恰好被抓到幾筆，重算再跑一輪時子隊已經「不夠新」而掉出範圍（純猜測，實際邏輯要你/implementer 查 `SpecimenDumpHelper` 的重算時機）。**建議**：子隊一旦被血緣納入，應持續追蹤到它消亡（merge/dissolve/stranded）為止，不要重算掉隊。
2. **★欄位缺口（次要，但也擋題①②）**：全檔（含母隊、含porter）**沒有 `tile_pos`/座標欄位**——母隊「做什麼」entry 有 `target`（自己下一步要去哪）跟 `beliefs[].est.tile_pos`（對別隊的belief），但**porter 自己的當前座標整份沒有任何形式存在**。就算覆蓋窗補到位，題①「追家追到哪裡算合理」跟②「路徑像不像回家」**沒有座標也判不出來**——這兩題本質是空間問題，需要 porter（也許還要母隊）的 `tile_pos` 逐 tick 進 state dict。

## 我能給的部分讀（低信心，非結論，供你參考）

- porter_12 在我能看到的窗口內（OUTBOUND→RETURN前9天）：`material` 從64掉到31（介於OUTBOUND轉RETURN那一tick，=一次性交割賣貨，非漸進消耗——跟「送完貨才轉RETURN」的故事吻合）；`food_private` 之後穩定線性下降（17.0→10.0，約每日0.78），沒有異常跳動或停滯的訊號——**這段看起來像正常在途**，但這只是RETURN頭9天，不是它卡點/歸建那段，不能代表整趟故事。
- porter_19/20 窗口太短（各0.25天），連「正常在途」都判不出來，純粹資料不夠。

## 結論

**三題仍然判不了**——這輪原因换成「覆蓋窗斷在結局前」+「無座標欄位」，跟上輪「錄錯人」是兩個不同的洞。建議先修覆蓋窗（子隊持續追蹤到消亡）+ 補 `tile_pos`，再重產一輪。地基 KEEP，convoy slice 繼續卡在我判決前不 merge。
