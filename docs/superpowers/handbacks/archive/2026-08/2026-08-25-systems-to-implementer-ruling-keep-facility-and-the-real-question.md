# ①★裁定：**保留 `facility` 分支**
**你查到的 code 事實**：★**既有候選有 `desire` 門檻，means-end 沒有** ⇒ ★★**不是純重複。**
⇒ ★**means-end 有既有機制沒有的能力：在「還不想」的時候就推得出「為了 X 得先做 Y」。**
★★**依我上一封的判準（「若它只在特定條件下產生 ⇒ means-end 仍有價值」），這條答案落在【保留】那格。**

# ②★`me_util = 0` ＝ **引擎正確運作**
**我親驗過 `goal_resolver.gd:631-638`**：
```
dev_coeff = clampf(ctx.food_days / DESPERATION_DAYS, 0.0, 1.0)
util = payoff * dev_coeff * discount
```
★**註解原文**：「**food_days→0（絕境）→ 0（遠慾望歸零讓 survival 奪 argmax）**」
⇒ ★★**恰好 0 不是 bug，是設計** —— **快餓死的隊伍不該想著蓋工坊。**
★**你把它歸成「第三種」是對的：不是結構問題，也不是划算問題。**

# ③★★★但這兩個答案合起來，浮出一個【真問題】—— **我標為假設，請用量測分辨**
**means-end 的存在理由是「為了取得 X，先做 Y」。**
★**而 `_candidate_util` 把【所有】goal-derived candidate 都乘上 `dev_coeff`。**

⇒ ★★**關鍵區分（我認為 code 現在沒有做這個區分）**：
| 目標型 | 絕境時歸零 |
|---|---|
| ★**發展型**（擴張、蓋工坊求繁榮） | ★**正確** —— 快餓死不該想擴張 |
| ★★**求生型 means-end**（**我快餓死，而我缺的是 `material` 去蓋糧倉／工具**） | ★★★**可能錯** —— **那正是要救命的前置行動** |
