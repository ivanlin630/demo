# QA 故事稽核：failure-memory-structural-identity — 正式判決

## team8（本 slice 系列一路追蹤的案例）＝ **這輪完全沒紮根成功，訊號很清楚但因果不完全乾淨**

團隊命運跟之前 camp-access/build-eta 兩輪判若兩隊：**pop 從 6 一路掉到 2**（tick5500-9410 陸續死3人），**effective_food 絕大部分時間卡在 0-3**（跟之前成功那輪 ef=2.5-17 的區間明顯更慘）。全程 **5 次「紮營」committed**（tick11600/12000/12010/13200/16300，分別在 `[10,6]`/`[16,1]`/`[12,2]` 三個不同 tile），**但一次「建設/紮根」都沒有接上**——跟之前那輪「紮營→緊接著建設/紮根一次成功」的乾淨路徑完全不同。

**逐次候選 util 核對**：「建設」每次都真的出現在候選陣列裡（不是被排除掉），但分數持續偏低：
```
tick11600: 建設=0.2336（輸給紮營1.29/求和1.18/乞食1.14/survival1.07/遷移找糧0.94）
tick12000: 建設=0.2377（輸給紮營2.90/乞食2.73/掠奪2.50/遷移找糧2.50/survival1.22）
tick12010: 建設=0.2385（同上型態）
tick13200: 建設=0.2364（輸給紮營1.91/遷移找糧1.59）
tick16300: 建設=0.2616（輸給紮營0.75/遷移找糧0.42/maintain_food0.30）
```
**「建設」在這五次機會裡從沒贏過，分數穩定卡在 0.23-0.26 這個窄帶，即使對手（紮營自己的util）掉到很低（tick16300 只有 0.75）它還是贏不了**——這個「無論環境多寬鬆都卡在同個分數帶」的訊號，方向上支持 measurer 的懷疑（失敗記憶磚可能把「建設」壓低）。

## ★誠實邊界：無法排除「genuine 資源太緊，建設本來就該輸」

**這輪 team8 本身比之前成功那輪弱很多**——pop 只剩 2、長期 ef≈0-3（前輪成功時 pop 穩定在 6、ef 在成功那刻是 2.5 且很快回升到兩位數）。在這麼窮的狀態下，「建設」這種需要投入資源/時間的長期選項，本來就可能在 WHAT 層面**genuinely**打不過「乞食」「遷移找糧」這類立即紓困選項——**這不需要失敗記憶磚介入就能解釋 util 排序**。

**我手上這份 specimen 沒有失敗記憶磚 penalty 施加前的原始 util（`mult()` 乘之前的值）**，沒辦法把「genuine 資源緊迫讓建設该輸」跟「磚把建設額外壓低」這兩個假說分開——**兩者都能解釋我看到的現象，我不能單靠這份資料坐實哪一個**。

## 建議

1. **下輪補一個 tap：`建設`（或其他被磚 suppress 的 structural_id）在套用 `mult()` 前後的 util 對照**（`failure_memory.gd` 的 `mult()` 呼叫點加一行 Probe.bump_sample 記 raw_util vs penalized_util）——這樣才能一次區分「genuine 該輸」vs「磚壓低導致該贏卻輸」，不需要再靠這種間接推論。
2. **在那個 tap 出來前，`outpost.l0_to_l1: main1→branch0` 這條 regression 的因果仍是懸案**——我這輪只能說「訊號存在、方向支持懷疑，但不到坐實」，跟 measurer 要求的「是不是磚把原本能成功的重試壓下去了」同一句話收尾：**我也還沒查到底**。
