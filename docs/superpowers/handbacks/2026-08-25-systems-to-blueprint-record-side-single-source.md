# `blocked_total = 0` 的第二層：**記錄側只有一個事件源**

implementer 報前提型**一次都沒觸發**，判「對 A 面構造性零影響」——**那層對。**
★**我追了第二層：為什麼沒觸發？**

**窮盡**：`FailureMemory.record` 的 production 呼叫點 ★**＝ 1 個**（`order_system.gd:127` **買單**）。

## ★★★這一刀切開三件事
| 現象 | 真因 |
|---|---|
| `blocked_total = 0` | 前提型（缺料）**確實大量發生**（T1：**28 次 dispatch_fail 全是資源不足**）—— **但不經買單 ⇒ 沒進記憶** |
| ★**紮根 0 次被折價** | ★**紮根不下買單**（站在原地蓋）⇒ **它的失敗【永遠】不會進 FailureMemory** |
| 「覆蓋率 1 → 16／19」 | ★**量的是【查詢側】能認得幾種 key，不是【有多少失敗真的被記下來】** |

## ★★我要認一個用詞上的疏失
**「覆蓋率」在這張票上有兩個意思，我一直只講了一個**：
- **①查詢側覆蓋**：`mult_for_*` 認得幾種 key —— ★**我們把它從 2 提到 19**
- ★**②記錄側覆蓋**：幾種失敗**真的被記下來** —— ★**一直是 1**

⇒ ★**「記 done 必同記覆蓋率」這條是我立的，但我自己只記了一半。**

## ★★因此紮根有【兩個獨立的病】
| # | 病 | 歸屬 |
|---|---|---|
| ① | **util 尺不同**（`[0,1]×[0,1]` vs 折現真流）⇒ **結構上贏不了** | `rooting-fifth-end-same-ruler`（你已授權直接修） |
| ② | ★**失敗不進記憶**（不下買單）⇒ **輸了也學不到** | ★**新，呈你** |

★**兩個獨立**：**修 ① 讓它贏得了；修 ② 讓它輸了會學。缺一個都不完整。**
