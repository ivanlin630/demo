# QA 複判：缺口①② 有硬數據，結論明確

用 explainable jsonl 逐欄核對，不是憑印象。

## 缺口①：紅——真 bug，不是觀測缺

**鐵證**：對全 331 筆逐一核對「task 是什麼」vs「effective_food 何時上升」，結果——

**整份 trace 裡，effective_food 只在 task="覓食"（forage）時上升過 3 次（tick 18260/19930/20630）。task="貿易"／winner_opt="買糧" 從頭到尾、一次都沒有讓 food 增加過。**

死亡窗口鐵證（`active_buy_food_qty` 逐 tick 追蹤）：tick 15570→16450（880 tick，跨兩次死亡 pop 3→2→1），`active_buy_food_qty` 卡在 **恰好 9，一次沒變過**，`at_market:true` 全程成立，`coin` 中途從 0 長到 5.33，food 卡在 0 逾 200 tick。直到 tick 16600（**兩人已經死了之後**）這個數字才第一次動（9→6），但同一時間 food 仍是 0——不管這個 6 代表「還缺 6」還是別的意思，**這 880 tick 裡沒有任何一筆讓 food 真的回升的紀錄**。

結論：你要問的「fix 真修還換皮」——**換皮**。thrash（高頻抖動）這個症狀確實消滅了，但底下「買糧這個 task 選中之後，food 從未真的入帳」這個更根本的問題完全沒被碰。反而因為執行鎖讓 task 穩定不再抖動，這個「選中了但沒效果」的死法變得**更難被肉眼發現**（原本 122 次抖動至少會讓人起疑，現在看起來像「正常在跑一個任務」，實際上是空轉）。

Team20 的 2 名死亡成員，死因是「決策正確選中買糧、task 鎖住不被打斷、但買糧這個動作本身沒有任何效果」——這仍然落在你判準表 ❌ 那一類（手不聽腦），只是換了一種更隱蔽的皮：不是「被打回 idle」，是「鎖住了但鎖住的動作是空的」。

## 缺口②：綠——威脅來源真實

survival/逃跑鎖定的兩段（tick 18280起、21020起），`threat` block 全程有效：`threat_id` 在 3/5 之間切換、`threat_pos` 隨 tick 移動、`threat_react` 數值連動變化（6.26→7.34→9.74…），不是空殼。這代表有真實的外部威脅實體在附近觸發 survival 反應，target=[-1,-1] 是「原地戒備／無明確移動目標」的合理呈現，不是慢版 thrash。**同意你的判斷，此缺口解除。**

## 對你「機制保證論」的回應

你問：若①②複判都綠，「執行鎖成立→死前必已試過買糧且成交鏈完整」這條機制保證是否成立，死透 specimen 還要不要。

**前提不成立，此問題連帶不成立**。①是紅的——執行鎖只保證「task/winner_opt 不被每 tick 打斷／不抖動」，**不保證底層 action 真的產生效果**。這兩者是不同層次：鎖的是「決策穩定性」，沒鎖「執行有效性」。你的推論鏈斷在這一環，不能用「鎖住了=一定試過且成交」跳過驗證。

死透 specimen 現在也還要——但不是為了驗證你原本要的「死得連貫」，而是要換一個角度問：**團滅隊伍死前，買糧／貿易類 task 是否也一樣選中了但沒出貨？** 如果是，那「死前必已試過」這句話本身沒錯（真的試了），但「試了=有意義的掙扎」這個故事判準會被弱化——因為那個「試」是空轉。

## 判決：不建議 merge（除非縮小驗收範圍）

機制/閘（thrash 消失、determinism、憲法）綠，這部分我不擋。但「故事性」這關——不行，因為挖出的不是我這輪多問的枝節，是**這刀的核心主張本身**（recognizer 修好＝求生 task 會被正確執行）**只驗證了「不被打斷」，沒驗證「打斷後真的做到事」**。

兩條路，你/系統選：
1. **修**：查買糧訂單為何在 at_market=true+coin 足夠時仍 880 tick 不出貨（換皮的根，多半是另一個獨立的 order-fulfillment 斷鏈，非本次 recognizer 範圍），修完重跑 specimen 再讓我複判。
2. **縮小驗收範圍 merge**：若你評估「thrash 消失」本身已值得先落地、買糧不出貨算另一張已知票（開 `known_issues.md`），可以 merge，但**不能寫「故事性判官已判合格」**——只能寫「thrash 已消滅，買糧訂單不出貨為新發現獨立缺陷，另案追」。這是你的 WHAT/release 裁量，我不擋，但要求 merge log 精確反映範圍，別把①的紅算進「已驗證」。
