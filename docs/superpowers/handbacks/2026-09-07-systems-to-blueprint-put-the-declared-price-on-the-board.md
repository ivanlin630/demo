```
我原本傾向:(c) 賣邊修進 ⑩、買邊開正式票
★而 implementer 查出可行性【相反】:
   買邊 `(local_value − ask) × qty`  ⇒ ★ask 是【賣方要價】,商隊到場就讀得到(現行 _market_visitor_buy 就在算它)
   賣邊 `(bid − local_value) × qty`  ⇒ ★★bid 要讀【買方的內部估值】= god-view
                                        —— 板上的單【沒有價格欄】(欄位全列過:order_id/kind/res/

⇒ ★★★所以:【買邊進 ⑩】,賣邊要一個 WHAT 決定 —— 你的裁定形狀不變(兩半各帶對照),只是【誰先】反過來
```

# ★★★二、而我提一個結構解：**讓單據帶上【掛單者自己申報的價格】**
```
賣單 → 帶 ask(賣方掛單當下的要價)
買單 → 帶 bid(買方掛單當下的出價)
★都是【掛單者自己申報】⇒ ★★不是偷看別人的內部估值 ⇒ 零 god-view
```
## ★它一次解開三件事
```
①賣邊的式子【立刻可算】:商隊讀買單上的 bid ⇒ gain = (bid − 自己的 local_value) × qty
②★★它救活你先前裁的 (d)(「自我申報的保留價值」當領取的尺)——
   ★★★當時它不成立是因為【那個欄位不存在】,而不是因為【概念錯】
③★市場板上有價格,這件事本身就比「只有數量的板」合理 —— 沒有價格的市場板才是異常
```
## ★★而「快照會過時」不是缺點，是【正確的語意】
```
資訊網本來就帶 origin_tick／strength／relayed 的衰減 ⇒ ★單據上的價格【本來就該是舊的】
⇒ ★★「我看到的是他三天前開的價」正是殘缺情報該有的樣子
⇒ ★★★而現行模型是【撮合當下重算】—— 那反而是【資訊瞬時傳遞】,與資訊網的鐵律不一致
   （★這一點我先前沒看出來:現行做法在感知上其實比帶價格【更寬】）
```

# ★★三、而它讓世界做出你要的那件事
```
買方缺糧 ⇒ 它的 bid > 0（掛單時自報）
賣方深過剩 ⇒ local_value = 0
⇒ 商隊 gain = (bid − 0) × qty > 0 ⇒ ★★【它會把糧搬過去】
⇒ ★★★而那正是你裁 (a) 時寫的:「糧食過剩流向缺糧處;資訊全開之下還爛在產地=故事是假的」
```
