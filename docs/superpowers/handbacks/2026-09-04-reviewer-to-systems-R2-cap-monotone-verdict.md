# 判決：`issues`（小），`premise_contradiction: false`

## ①食物當計價基準——**不是特殊化，是通用量尺，同意你的反面論證**

食物確實是唯一「每個隊、每天，不管缺什麼，都必須消耗」的東西——用它當「一天生計價值」的參照，跟經濟學用「一條麵包多少錢」當跨國購買力參照（大麥克指數）是同一個手法：**不是因為麵包/大麥克特別重要，是因為它是一個【普遍存在、隨處可比】的錨**。`w` 本身已經是 `BASE_PRICE` 導出的「價值」單位（跨資源同單位，上一票已核可），拿食物的日常開銷當分母不會讓食物的【短缨】在排名上被優待——它只是決定「1 單位 x」代表多少天的生計，不影響哪個資源的 payoff 比較大。你的反面論證成立。

## ★★②x 對 pop 敏感——**不是均勻的偏誤，要分兩半看**

★**maintain_\* 家族**：`w=(target-stock)×BASE_PRICE[res]`，而 `target=pop×TARGET_PER_POP[res]` 本身就隨 pop 線性縮放——跟 `UNIT`（也隨 pop 線性縮放）同一個量級變化方向，**對「同一種相對短缺程度」（例如「完全缺X」），大隊小隊的 `x` 應該大致穩定，不會因為隊大就系統性偏低**——這一半你的疑慮基本上會自己抵銷。

★★**build_\* 家族**：蓋一座設施的原料成本是**固定的**（不隨 pop 縮放）——同一個固定成本，`UNIT`（隨 pop 變大）卻在長大，`x` 因此確實會隨 pop 系統性變小，**大隊看蓋東西真的會比小隊「不急」**。

⇒ **這個 build_\* 側的殘留效應，跟你擔心的「規模偏誤」方向一致，但它可能不是 bug**——這個 session 稍早已經記過 `project_size_matter_arc`（★用戶裁定「size 該 matter」，真根是「規模經濟」目前 absent）——**「同一筆固定成本，對大隊而言相對負擔更輕」正是規模經濟的其中一種具體展現**，不是憑空冒出來的偏誤，反而是這個 codebase 一直缺、現在意外補上一小塊的效果。

⇒ **建議**：spec 不要把②寫成單一是非題（「對」或「新偏誤」二選一），改成明寫「maintain_\* 側自我抵銷、build_\* 側有殘留但方向對齊既有『規模經濟』設計意圖」——這樣下一個人看到「大隊蓋東西比較不急」時，知道這是預期中的效果，不會誤診成新 bug 回頭亂修。

## ③跨 tick 可比性——**同意，不是需求**

argmax 只在同一 tick、同一候選池內比較，這個機制本身不需要 `u` 跨 tick 穩定。★**我額外確認**：驗收③（`tie_exact` 逐 option 下降）、驗收⑥（值分布 dump）都是**同一 tick 內的比較**或**發生次數的累計計數**，不是拿不同 tick 的 `u` 數值互相比大小——現有的量測紀律也不需要這個跨 tick 可比性，你的反面論證站得住。

## ★★★附帶查到一個真的數學精度問題——**`x` 該從哪個量算，spec 現在的寫法有歧義**

§2 寫「`x = w / UNIT`」，用的是 `w`（原始值，上一輪已知可以是負的，代表有餘）。但飽和公式 `u = CAP·x/(1+x)` **只在 x ≥ 0 時性質良好**（單調遞增、值域 [0,CAP)）——**若 `x` 是負的**：
```
x 在 (-1, 0) 之間 ⇒ u 變成負值 ⇒ 「保序、值域[0,CAP)」這兩個賣點都破了
x 趨近 -1        ⇒ 分母趨近 0 ⇒ u 發散到 ±∞ ⇒ 直接炸開
```
**上一輪已經確立 `payoff = maxf(w, 0.0)`（非負）**——這支公式的 `x` 應該讀**那個 `payoff`**，不是原始 `w`。spec 目前的字面寫法容易讓 implementer 直接拿原始（可能是負的）`w` 去除，踩進上面那個坑。

⇒ **建議**：spec §2 把 `x = w / UNIT` 改成 `x = payoff / UNIT`（`payoff` = 上一輪已確立的 `maxf(w, 0.0)`），並加一句「`x` 的輸入必須先過 `maxf(w,0)`，不得是原始 `w`，否則 `x` 可能為負，公式在 x→-1 附近會發散」——這不是新規則，是把上一輪已經定案的東西在這裡接對，避免兩票之間的介面口徑不一致。

## ⇒ 要你補的
1. ①③不用補，判斷正確。
2. ②：spec 把「對還是偏誤」改寫成「maintain_\* 自我抵銷、build_\* 有殘留但對齊既有規模經濟設計意圖」，不要當單一是非題。
3. ★：spec §2 明寫 `x = payoff/UNIT`（`payoff` 已經 ≥0），不是 `x = w/UNIT`——這條是實質要求，防止公式在負值域發散。

**premise_contradiction: false，②③(數學精度)處理過即可整票 CLEAN。**
