# 1 ★你優先打的——D2：風險真實存在,但風險的性質跟你猜的方向一致,而且這個專案已經有正確的解法擺在那裡

## 核對：現有機制是「明文宣告清單」不是「查值空不空」——這條路是對的

```
text_ui_main.gd:1487-1529 `_page_skylight_fields(idx)`：回的是一份【明文具名的清單】
  (「糧食跑道（缺趨勢）」「位置與家（查詢面無此欄）」「被聚焦的人」),不是靠檢查某個值
  現在是不是空字串/0來反推「這欄沒寫入者」——它是【宣告式】的,跟欄位目前的值完全無關
⇒ 這是對的設計,D2如果沿用這支函式的模式(加名字進清單=沒寫入者,清單外=一律印值,不管值是什麼)
  不會有你問的那個風險
```

## 風險在哪：如果implementer不沿用它,改用「印出來的字串是空的就不印」這種檢查

```
★本檔自己就有一個活生生的反例,證明「值空」不等於「沒寫入者」：
  text_ui_main.gd:1475-1478 `_build_memory_lines()`：
    「已知情報：%d個對象」% rows.size() ——0個對象時這個字串不是空的,但承載的資訊是0,
    而旁邊明文註解寫「0筆也印一行——常駐：只在非零時才出現的東西,玩家學不會它的意思,
    而『沒看到』與『沒有這個功能』在畫面上長得一樣」
  ⇒ 這正是你問題裡「有寫入者但此刻值是空」的那個情境的現成案例,而它的正確處置是【照印】
★而本檔已經寫過判準庫等級的教訓,直指同一個病的鏡像版：
  text_ui_main.gd:1515-1526「哨兵值要用它自己的欄位判(id==-1),不要用is_empty()/==null/
  長度——空的字典與表示空的字典在is_empty()下同形」——那次是「被聚焦的人」那個天窗因為用
  is_empty()判一個恆不為空的哨兵dict,從來沒出現過(反方向：該印的被藏了)
⇒ D2要防的正是同一個病的第三次：如果「沒有寫入者」的判斷依據是「這個欄印出來的字串/值是
  不是空的」,那麼一個【有寫入者、這一刻恰好回傳空字串或0】的欄會被誤判成「沒有寫入者」而被藏起來
```

## 處置

```
補一句：D2的實作要沿用`_page_skylight_fields()`的宣告式清單模式(或等價的、以「這個欄位有沒有
  被登記在產生者清單裡」為準的檢查),不得以「這一刻算出來的字串/值是否為空」作為判斷依據；
  P驗收項加一條：佈置一個有寫入者、算出來的值恰好是空字串/0的欄位(例如仿`_build_memory_lines`
  那樣的0筆情境)⇒ 它必須照印,不能被新規則一起吞掉
```
