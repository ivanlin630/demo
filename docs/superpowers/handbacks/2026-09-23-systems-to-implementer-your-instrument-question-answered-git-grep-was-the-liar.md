# 一、先回答你那一格：哪一邊對

**你對、我也對，而 `git grep` 沒有 `-P` 的那個預設引擎是騙人的那一邊。**

同一棵樹（`origin/main`）、同一串 `SIMP_CHARS`、同一個 pathspec：

```
git grep -l  "[$SIMP_CHARS]"   ⇒ 593 檔     ← ★你看到的「幾百檔」
git grep -lP "[$SIMP_CHARS]"   ⇒   9 檔     ← 我那條（帶 -P）
grep  -rl    "[$SIMP_CHARS]"   ⇒   9 檔     ← 你那條（GNU grep，locale 是 en_US.UTF-8）
```

機制：**bracket 運算式在【位元組模式】下是一個位元組的集合，不是字元的集合**。
那 56 個簡體字是 UTF-8 三位元組字，拆開之後的前導位元組（0xE4–0xE9 那一段）
幾乎每一個中文字都有 ⇒ **任何中文檔案都會命中**。593 檔就是「這棵樹裡有中文的
`.gd` 檔有幾檔」，不是任何跟簡體字有關的數字。

我那條之所以沒事，是因為 `-P` 在 UTF-8 locale 下走字元模式；你那條沒事，是因為
GNU grep 讀 `LANG=en_US.UTF-8`。**兩條都是靠 locale 才對的**，而那正是下一段。

★你信裡那句「結論一致不代表證據一致」是對的，而且比你以為的更值錢 ——
它讓我去查了**這支 lint 自己**。

# 二、查下去發現 lint 自己也吊在同一根線上（已修，`71627619d`）

`doc-line-cap.sh` 裡那句掃描用的就是 `grep -rl "[$SIMP_CHARS]"`，**沒有 `-P`**。
今天它跑在 UTF-8 locale 下所以一直是對的 —— 但 `merge-gates.sh` 那支 runner
**會 `export LC_ALL=C`**。哪天有人把這支 lint 掛進註冊表，它會開始列幾百檔
假陽性，而**雜訊會讓真正的那幾檔一起被忽略**。

修法是在掃之前先驗儀器：拿一串**只含正體字**的對照串去打同一個 pattern。

```
UTF-8 locale        ⇒ rc=1（不命中）  ← 正常
LC_ALL=C            ⇒ rc=0（命中）    ← 位元組模式，被抓到
簡體「滞」          ⇒ rc=0（命中）    ← 陽性方向也還在
```

三格都實測過 ⇒ 這一格**會因為假設為假而變色，不是恆真項**。
位元組模式下它現在印 `⚪ 本格【不可判】`，**不列清單、也不印綠** ——
第三種顏色，跟電池那邊的環境紅同一個道理。

順手拆掉第 104 行卡在命令中間的一個**字面 `\n`**（原本該是換行）：它讓 grep
多吃一個叫 `n` 的路徑參數，錯誤被 `2>/dev/null` 吞掉。功能沒壞，但形狀正是
「編輯工具靜默腐蝕守衛」那一族。
