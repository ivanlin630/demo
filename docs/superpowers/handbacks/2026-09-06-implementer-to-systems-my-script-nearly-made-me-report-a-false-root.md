# 一、發生了什麼

⑩ 的驗收①要「**只拆上臂 ⇒ fp 逐位元不變**」。我用 trap 保護的暫時 patch 跑三段。
結果：
```
[TEN-A] FAIL：★★上臂拆掉之後世界變了 ⇒ 【§2 的推導錯了】—— 這才是要停下來的時刻
163a164
> [Ambition] Team5 rung 0→1 (商業 cap=2)
...
```
★**而這個 FAIL 跟 code 無關。** 上面幾行有一段我差點略過的 traceback：
```
FileNotFoundError: '/a/GDS/demo/.worktrees/declamp/scripts/simulation/trade_valuation.gd'
```
⇒ ★★**patch 根本沒套上** ⇒ 那一趟跑的是**完整拆**（不是「只拆上臂」）⇒ 比對必然不同。

# 二、★成因是【同一個路徑字串，對兩個工具語意不同】
```
`cp` / `grep` 是 MSYS ⇒ 吃 `/a/GDS/demo/...`   ★成功
`python` 是 Windows python ⇒ ★★打不開 `/a/...`  ★★★失敗
⇒ 而它們在【同一支腳本的前後兩行】
⇒ ★所以「路徑是對的」這個判斷【在同一支腳本裡同時為真與為假】
```

# 三、★★★而真正要記的是這一句
```
★腳本【預先寫好了解讀】：「§2 的推導錯了 —— 這才是要停下來的時刻」
⇒ ★★那句話是我【設計驗收時】寫的，而它寫得很好：它把 FAIL 的意義講清楚了
⇒ ★★★而正因為它寫得好，它讓一個【由腳本 bug 產生的 FAIL】看起來像【一個深刻的發現】
```
★**預先寫好失敗語意是對的**（它讓紅燈可讀）——
★★**而它同時提高了【錯誤的紅燈】的說服力**，而我先前沒有想過這個副作用。
⇒ ★★★**配套是：紅燈的解讀可以預寫，但【實驗前提有沒有成立】必須在【印出解讀之前】被驗證。**
