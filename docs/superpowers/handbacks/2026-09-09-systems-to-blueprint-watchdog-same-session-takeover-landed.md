# ① 症狀與真因

```
TaskStop 殺 task【不殺 Windows 進程樹】⇒ 孤兒 bash 還活著、還在 poll
★★而它每 poll 都 touch lock ⇒ lock 永遠新鮮
⇒ 新實例的 claim_lock 走到「age < POLL_S+120 ⇒ return 1（同代持有,讓位待命）」
⇒ ★★★永遠上不了位 —— 你今天手動收屍兩次（pid 2562 / 33624）。
```

★**你給的兩個選項我都沒有照抄，理由**：
```
「lock 有效性改心跳非 pid 存活」⇒ ★它【已經是】心跳（mtime）—— 而心跳正是【病因】：
   孤兒的心跳是真的,它真的還在跑。⇒ 換成心跳救不了。
「換成 v3 的一律換血」⇒ ★★方向對,而【換血的觸發條件】要講精確:
   不是「前任死了」(孤兒沒死),是【同一個 session 又 arm 了一次】——
   ★★★那件事本身就是「前任已被取代」的宣告,不需要去證明前任死了。
```

# ② 修法（`claim_lock`）

```
同 SID ＋ 不同 pid ⇒ ★直接覆寫 lock 接手,不問死活,並印出【已處置的結果】：
  ♻ 同 session 換血接手：前任 pid=<n> 的 lock 已由本進程 pid=<m> 接管（不問死活）
跨 session      ⇒ 維持原本讓位語意（別人的 session 不歸我搶）
舊代（欄數 < 3）⇒ 維持「需人工」（它不讀 lock 歸屬、永不讓位）
```

★★**成對驗過（三種情形各一，不是只驗會過的那個）**：
```
同 session 孤兒持有（新鮮）⇒ rc=0 接手   ✔
別 session 持有（新鮮）    ⇒ rc=1 待命   ✔（★沒有變成「新的一律贏」——那會搶別人 session 的）
舊代 2 欄（新鮮）          ⇒ rc=2 人工   ✔
```
