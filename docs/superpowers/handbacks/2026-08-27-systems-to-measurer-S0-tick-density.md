# ★①要量的（★LOCKED spec §2 定的，我照抄不改）
```
同 seed／同 config，★現制 vs 6× 制 各跑 3 遊戲日
★★比【每遊戲日 wall time】——★★★不比 per-tick（tick 定義變了，比 per-tick 會自欺）
判準：每遊戲日 wall 增幅 < 15% ⇒ 走路 A（S1→S2→…）；≥ 15% ⇒ 先做 S4（T0×LOD）再回頭 S2
```
★**背景**：`TICKS_PER_HOUR 10→60` ⇒ **每遊戲日 tick 數 240 → 1440（6×）**。
**真實工作量不變**（cadence 以小時宣告、自動跟隨），**而每 tick 的固定開銷 ×6。**

# ★★★②而這顆有一個【明確先驗】，我先講死
```
★用你 slice 0 的 baseline median（35~143 隊，全在 16~31 us／tick）紙上估：
   多出來的 50 個 no-op tick × ~25us ≈ ★1.25 ms ／遊戲小時
★★而同一小時裡的 spike 是 ~6.8 【秒】 ⇒ ★★★約萬分之二
```
⇒ ★**預期：壓倒性通過（遠低於 15%）。**
★★**所以這是【快速確認】不是開放式調查** —— **短窗就夠，別開大窗。**
★★★**而若它跑出增幅 ≥15%，那才是【真的意外】，值得停下來看，而不是照判準表機械走路 B。**

## ⚠️★但我不拿估算當結論（★我今天才被同一件事打過）
★**「baseline median」與「no-op tick」不是同一個東西** —— **baseline 含真正在跑的系統，no-op 是被 cadence 全部跳過的 tick。**
★★**而我今天才因為「拿兩個中位數相除」被 implementer 打回一次。**
⇒ ★**所以先驗只是先驗；照實跑，照原樣報。**

# ★★③而有一件我要你【順便確認】的（★便宜，且它決定 S0 有沒有意義）
> ★**6× 制那一趟，cadence 真的有跟著小時走嗎？**

★★**若某些 cadence 是【寫死 tick 數】而不是經 `TICKS_PER_HOUR` 導出，那 6× 之後它們的【真實頻率會變 6 倍】** ——
⇒ ★★★**那樣 S0 量到的就不是「固定開銷 ×6」，而是「一堆系統跑了 6 倍多次」，兩者混在一起無法歸因。**
★**做法**：**跑 6× 那趟時，順便印【每遊戲日的決策次數／事件率】** —— **若它與現制持平 ⇒ cadence 真的跟著小時走；若漲了 ⇒ 有寫死 tick 的漏網，那本身是 S1 要修的東西，也是比 wall time 更重要的發現。**
