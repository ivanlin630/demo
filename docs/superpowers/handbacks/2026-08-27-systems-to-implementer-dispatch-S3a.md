# ★★②做法：**靜態列舉 ＋ 實測驗證，兩步缺一不可**
★**因為 propagate 那顆教過我們**：**它【看起來】掛在每 tick 的 arrival 事件，而實測兩根兩床呼叫次數完全相同。**

## ★靜態：**終止條件重用【你自己建的】規則表**
```
從 sim_runner tick 迴圈頂層直接呼叫的每個函式出發，靜態遞迴追呼叫鏈：
★撞到【bare_tick 規則表裡任一個 cadence-gate 形狀】⇒ 終止，記 `gated` ＋ file:line
★★追到葉節點都沒撞到 ⇒ 終止，記 `true_candidate`
★★★撞到【變數持有的函式參照／`.new()` 動態解析】⇒ 終止，記 `untraceable`
⇒ ★三桶對帳：gated ＋ true_candidate ＋ untraceable ＝ 分支總數
```
★**R² 的理由**：**「判斷有沒有 gate」若靠人眼，「我追了幾層」就是自由心證** ——
★★**重用規則表之後，它變成【撞到哪一條、在哪一行】，別人能重跑。**

### ⚠️★★★★第三桶不是保守，是【防虛報】
> ★**GDScript 鴨子定型 ⇒ 動態呼叫對靜態掃描【不可解析】** ⇒ ★★**那種分支的真實深度是【未知】，不是【確認沒 gate】。**
> ★★★**硬算進 `true_candidate` ＝ 虛報一個根本沒驗過的站。**
★**它要出現在【輸出裡】，不是只在 handback 裡。**

## ★★實測：**每個 `true_candidate` 量它每遊戲小時的實際執行次數**
```
★次數 ≈ TICKS_PER_HOUR ⇒ 真的是每 tick 站
★★次數 ≪ TICKS_PER_HOUR ⇒ 它有 gate 而靜態沒追到 ⇒ ★★★回頭補靜態列舉的漏
   —— 而【那本身是發現】：它說明列舉在哪裡看漏了，要逐個記
```
