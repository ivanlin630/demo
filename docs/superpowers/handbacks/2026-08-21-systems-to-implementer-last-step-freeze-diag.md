# 派工：「明明相鄰卻不走最後一步」（★診斷票，只產答案）

**同前兩張診斷票的規格：只產答案、不產修法。**

## 題目（QA 逐 tick 讀 specimen 坐實，非快照距離）
三筆 convoy `stranded` 的 porter **全部**在走到**相鄰格**後**連續多個判斷週期一步不走**，
直到 T3 逾時把它們收掉：

| porter | 凍結位置 → 目標 | 凍結時長 |
|---|---|---|
| 100 | `[17,18]` → `[16,19]` | **240 tick／4 連續樣本**（之前一路正常接近） |
| 118 | `[10,12]` → `[11,11]` | **200 tick／4 連續樣本**（之前一路正常接近） |
| 164 | `[10,15]` → `[10,14]` | **一進 RETURN 即刻凍結**（★**最乾淨的樣本，從這隻查最省**） |

## ★我已幫你排除一個假設
三筆的差值是 **`(-1,1)` / `(1,-1)` / `(0,-1)`**，**全部都在 `PathSystem.HEX_DIRS` 裡**
⇒ **是真正的六角相鄰**，**不是「Chebyshev 相鄰但六角不相鄰」的度量錯配**。
**就是最後一步不走。**

## QA 建議的可疑方向（**未驗**，別當結論）
- 移動系統的**「已到達判定」**
- convoy 的 **`move_target` 更新**與**移動判定 cadence 沒對齊**
- **相鄰格被判成「已算到達」，但 `tile_pos` 沒真的寫入最後一步**

## ★連帶一起查
`porter164` 在 **`OUTBOUND→RETURN` 那一刻 `material` 沒有從 30.00 掉下來**——
其他乾淨案例（porter 12/20/22/100/118）轉 RETURN 時 material **都會因交割掉一截**。
⇒ **懷疑這趟連貨都沒真的交割成功**。
★ 若「**到達判定沒觸發**」是共同根因，**交割不觸發就說得通** —— 這兩件很可能是同一個病。

## ★★為什麼這個缺陷今天才被發現
**T3 逾時兜底一直正確地把這些 porter 收掉、把現場清乾淨了。**
（已升 `invariants`〈兜底會遮蔽它兜住的東西〉：**兜底 fire 時要留下「它兜住了什麼」的證據**。）
