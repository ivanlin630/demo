# 一、裁定

```
玩家循環是【下令 → 推進 → 看結果】。世界平常停著，這是設計不是缺陷（game-design.md:1500）。
⇒ 按鍵不推時間（否決丙）；玩家在停著的世界下幾道令，再按推進，才看到結果。
⇒ 按鍵當下唯一能誠實講的是「我收到了、排第幾」——所以印「已排入：移動到 (3,5)」（乙）。
```

```
★★但乙單獨也不夠——玩家要的是【結果】，不是回音。所以綁三格，缺一不算交付：
①入列回音：「已排入：<動作人話>」（seq 不用給玩家看，動作人話要）。
②消費結果：下一顆 tick 開頭套用後，成功印一句、拒絕印一句＋原因（「那裡太遠了」現在在這裡印）。
   ★拒絕禁靜默——意圖帳「執行失敗反饋」那一行對玩家同樣成立：失敗是事件，必回饋。
③頁腳常駐「待執行 N 道」（snapshot_meta 那個共用頁腳）：N>0 時玩家知道世界還沒吃、按推進就會吃。
   ⇒「排進去了」與「鍵沒被吃到」在畫面上是兩個不同的狀態，不靠玩家猜。
```

   判準句：「這個拒絕的答案會不會因為世界推進一顆 tick 而改變」——會⇒等消費點；不會⇒當場。

# 四、不在本票（登待辦，別偷渡）

```
撤回已排入而未消費的指令（玩家改主意）——佇列化之後自然會有人要，先記著。
```

# 五、驗收句（給床用，母體要真有）

```
一鍵入列 ⇒ 畫面同幀出現「已排入：…」且頁腳「待執行 1 道」；推進一顆 tick ⇒ 出現結果句且頁腳歸 0。
一道必拒的令（目標格太遠）⇒ 入列時【不】印拒絕；推進後印「拒絕：那裡太遠了」。
一個不認得的鍵 ⇒ 當場印拒絕、頁腳不動。
陽性對照：把消費點的結果句拿掉，第一格必紅。
```
