# ★★★一、不要預先赦免（這一條會決定第一次跑的品質）

```
你寫：「那四格很可能第一次跑就紅，那是【預期中的紅】不是回歸 —— 我先寫在這裡，
      免得第一次看到卷面的人把它當成本票改壞了世界。」
★動機我同意（避免誤判），★★而做法有一個已知的病：
  **預寫的失敗語意，對【真紅】與【假紅】一視同仁地加持說服力** —— 寫得越好越危險。
⇒ ★★★第一次跑出來的那四個紅，會【自動】被讀成「就是他說的那個」，
  而如果其中一格其實是真的回歸，它**這輩子最好的現形機會就在第一次**，而我們剛把它赦免了。
```

**★改成可證偽的形狀（我要的）**：

```
不要寫「很可能紅、那是預期」，要寫：
  ①哪一格、斷言的是什麼數（例：食物 +30）
  ②★**預測的方向與量級**：多走一顆 tick ⇒ 食物應該少掉「一顆 tick 的消耗」，而那個量是可算的
     （★★算不出來就寫「我不知道量級」—— 那也是一個誠實的預測，而它同樣可被推翻）
  ③判準：**觀測到的落差落在預測裡 ⇒ 調容差；落在預測外 ⇒ 那是【發現】，不是預期中的紅**
⇒ ★★★差別在哪：你的版本讓第一次跑【不產生資訊】；這個版本讓第一次跑【正好是那個預測的實驗】。
```

# ★★二、那 13 處【不要交給眼球】—— 它是數得出來的

```
你寫：「(a) 13 處玩家回饋的刪除【不會紅】—— 它們只會多講一次話
      ⇒ 電池看不到，只有人看得到 ⇒ 不能靠電池驗收，要靠讀畫面。」
★前半正確（電池看不到「囉唆」）★★而後半我不接受：**「多講一次話」是可以數的。**
⇒ 加一格（P15）：**同一條指令，在畫面文字裡的回音次數 ≤ 2**
   （入列 1 次 ＋ 消費點 1 次；★第三次就是沒刪乾淨的那一處）
   ★做法：ui-flow 下一條可識別的指令 → 抓整頁文字 → 數那條指令的識別字串出現幾次
   ★★母體地板：那一輪必須真的有 ≥1 條指令走完【入列→消費】，否則 0 次也會 ≤2（恆真）
   ★★★負對照：**故意留一處沒刪** ⇒ 這一格必須紅
⇒ 而這一格順便把 (a) 從「13 個要人逐一看的地方」變成【一個會紅的東西】。
```

★**為什麼我不接受「靠讀畫面」**：用戶的眼球不是 QA（我們立過這條）；
★★而「要靠人看」的驗收在忙的那一天會變成「沒看」，★★★**而它沒看的樣子跟看過的樣子一模一樣。**

# 三、你抓的假綠那四格 —— 這是今天最好的一個發現

```
`_check("…成功", r.get("ok"))` ⇒ 佇列化後 command_player 回 {ok:true, queued:true}
⇒ ★那四句【照樣綠】，而它們從此測的是「排進去了」不是「成功了」
⇒ ★★**這比紅危險：紅會有人去看，假綠不會。** 逐字收下。
★你的修法（拆三句：①入列成功、標題寫明這不是動作成功 ②母體地板：消費點真的吃到幾條
  ③在消費點成功＝讀 command_log 的 ok）★★★三句都要 —— 尤其②，沒有它①③會在空佇列上都綠。
```

**★而這一族值得命名，因為它會再來**：

```
**改變回傳值的【語意】而不改它的【形狀】時，所有讀它的舊斷言都會【繼續綠】，而它們測的東西已經換了。**
⇒ 抓法：改回傳值語意的票，要把【讀該回傳值的斷言】逐一列出來看 —— 就是你這次做的事。
```
