# R②delta 判決：生育曲線常數（K/BASE_RATE 定案）

**判決 = CLEAN + 1 輕量確認項**（不阻塞 dispatch，回信帶一句話即可）。(b)(c) 算術親算全對。(a) 選 p90 當錨方向合理，但抓到三份 snapshot 的 p90 差距大到值得你一句話確認是有意為之。

## (b) 「量級錨定」算術：親算全對
- `TICKS_PER_DAY`(world_state.gd:4)=240、`TICKS_PER_HOUR`=10、`NEAR_CADENCE`=10 → 每日呼叫數 = 240/10 = **24**，跟你算的一致。
- `0.15 × 24 = 3.6` 次/人/日——期望成功次數公式 `E[successes]=n×p` 用對，算術對。
- `cap=maxi(1,int(pop×0.25))`：pop=6 時 `int(1.5)=1`、`max(1,1)=1`，你舉的例子對。
- 結論「通過即瞬間填滿 cap，真正 binding 是 cap 非機率」邏輯站得住（期望 3.6 次/日 vs cap 常態=1，幾小時內達標，不是「機率決定產出速度」）。**這個推翻「錨定舊期望值」的論證是對的，改成「錨定舊已實現結果」是正確的重新詮釋，不是文字遊戲**。

## (c) 「85倍盈餘只換2倍速率」sanity：確認符合飽和設計意圖，非反直覺 bug
親算：`r=12.7` 對 `K=0.148`，比值 12.7/0.148≈85.8；`f(12.7)≈0.99` 對 `f(0.148)=0.5`，比值≈1.98——你的兩個數字都對得上。**這正是 `f=r/(r+K)` 這種雙曲線飽和形狀的定義性行為**（r≫K 時 f→1 的邊際收益遞減），不是校準錯誤——這個「感覺起來反直覺」的地方剛好就是你 spec 自己說的設計目的（「避免暴富爆生」）在數字上的具體體現。**建議**：spec 或 code comment 加一句「此壓縮是飽和曲線的預期行為，非低估」，防未來有人看到這組數字覺得「怎麼差 85 倍才差 2 倍、是不是算錯了」而誤修——純文件建議，非阻塞。

## (a) K=0.15 取 p90：方向合理，但三份 snapshot 的 p90 差距值得你一句確認
選 p90（非中位數/p75）當錨的論證我認同：p75 三份全 ≈0（幾乎是 0/負分界），拿 p75 當 K 會讓 K≈0，曲線幾乎立刻飽和、失去漸進意義——p90 才是「有意義的正值」中第一個站得住的分位點，這個排除法選擇合理。

**但親讀你附的表格**，三份 snapshot 的 p90 差距很大：**peaceful d45=0.148、peaceful d200=2.695（**約 18 倍**）、warring d25=0.254**。你只取 d45 的 p90 當 K——這代表**K 錨的是「早期(day45)世界的頂尖水準」，不是「整段大考期間的頂尖水準」**。這件事有具體後果：**到 day200，peaceful 世界的 p90 已經是 2.695，遠遠超過 K=0.148**——套進 `f(2.695)=2.695/(2.695+0.148)≈0.948`，代表**day200 那些「當時世界前 10% 健康」的村，用 day45 校準的 K 去算，其實早就落在 f≈0.95 的近飽和區，曲線在這個階段對它們幾乎沒有區分力了**（f 對 r 的變化已經很平，繼續變富也差異不大）。

這不一定是問題——甚至可能是你要的效果（早期建立階段給有意義的漸進曲線、中後期站穩腳跟的村自然接近滿速，不需要再細分）——但**這是一個具體、有後果的設計選擇（早期校準 vs 全期校準），差距達 18 倍不是雜訊，值得你一句話確認是刻意的**，非只是「湊手邊第一份 snapshot 用」。

**要求（輕量、回信一句話即可，非阻塞 dispatch）**：確認「K 錨在 day45（早期）水準、非全期/後期水準」是你有意識的 pacing 選擇（早期給區分力、後期自然飽和），我沒有異議、只是要這條顯式寫進 spec 一行理由,避免日後有人拿 d200 數字回頭質疑「K 算錯了」時查不到當初為什麼選 d45。
