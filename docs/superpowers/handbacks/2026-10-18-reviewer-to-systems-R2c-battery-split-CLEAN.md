# 二、派發前請併進 spec 的文字修補（C1–C3）
- **C1 臨界區的殘骸判斷缺主人資訊**：§四1b 寫「已存在 ⇒ 等 1 秒重試…仍不成 ⇒ 看該目錄 mtime 是否 >120 秒且沒有活著的取得者 ⇒ 當殘骸刪掉」。`mkdir` 只建出空目錄，上面沒有「取得者是誰」的資訊，所以「沒有活著的取得者」無從判斷；實作端最自然的作法會是「mtime 舊就刪」，這會刪掉別人正在用的鎖（臨界區內有 PowerShell 查行程，單次可能數秒）。請寫成：取得成功後立刻在目錄內寫 `owner` 檔（`winpid=… since=…`）；殘骸判斷＝mtime > 120 秒 **且**（`owner` 檔不存在 **或** `_mb_marker_alive` 判該 owner 已死）。`owner` 檔不存在的短暫窗口（`mkdir` 與寫檔之間）由 mtime > 120 秒的條件涵蓋。selfcheck 加一格：用一個活著的背景子行程當 owner、把目錄 mtime 往前調 200 秒 ⇒ 不得被當殘骸刪；用已結束行程的 winpid ⇒ 刪。
- **C2 `since` 要是「標記出生時間」，排隊另用一個欄**：臨界區內改狀態時若同時把 `since` 重寫成當下，隊列順序（`waiting` 以 `since` 排序）與 N2 的 `StartTime ≤ since + 120` 都會被改動：前者讓先到的 excl 在改狀態後變成後到，後者讓 `since` 越寫越晚而放寬存活判斷。請標記分兩欄：`since`（標記建立時，之後不變，用於存活判斷）與 `state_since`（最近一次狀態改寫，用於同狀態內的先後）；`waiting` 隊首排序用「進入 `waiting` 的時間」（不隨其他改寫而變）。
- **C3 陽性對照小腳本要同時有「安靜時綠」這一格**：兩支小腳本在負載下必須不綠；但只有這個方向時，一支「安靜時就紅」的壞腳本（例如固定工作量預算取安靜實測 ×1.1 本身就抖動）也會通過。請加：同兩支腳本在**安靜那一跑**必須綠（跑 3 次皆綠才算腳本穩定）；安靜時不綠 ⇒ 預算改取安靜實測最大值 ×1.3 重校，不要拿它當證據。
