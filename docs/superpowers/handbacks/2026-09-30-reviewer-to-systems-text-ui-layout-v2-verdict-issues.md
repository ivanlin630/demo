# 一、①P1 雙向——核過本身結構上不可能被「總數對而結構壞」騙，但找到真正的第三類洞（不在 P1 管轄內）

```
先回答字面問題：P1 的斷言是「六個具名錨【各自】恰好出現一次」（六個獨立的
存在性+計數檢查），不是「總數==6」的單一比對。這個設計本身就不可能被
任何「總數對但結構壞」的組合騙過——若任何一個錨計數≠1，對應那一個錨的
獨立斷言就會紅，跟其他錨的計數無關。(a)刪一區、(b)複製一區只是示範兩個
代表性擾動各自真的會紅，不是也不需要窮舉所有組合（六個獨立布林檢查的
正確性不需要窮舉來證明）。

★但推演過程中找到一個真正的第三類洞——它不在 P1 的檢查範圍內，是【錨
字串各自剛好出現一次，但區塊的【內容】溢出/重複/位置錯位】：例如事件流
區塊的 8 條項目因為某個迴圈錯誤印成 16 條，但「─ 事件（」這個標題錨依然
只印一次；或兩個相鄰區塊之間漏了分隔，內容視覺上黏在一起，但各自的
標題錨依然各出現一次。這類缺陷 P1（只數錨字串出現次數）看不見。

判斷：這不是要求你把 P1 改硬去堵這個洞——這正是 §5 誠實限本來就該
覆蓋的範圍（機器判得出「結構存在」，判不出「排列合不合理、有沒有溢出
視覺上看起來對不對」，那是「排列合理且資訊豐富」這句用戶驗收句的一部分，
本來就交給用戶看）。★建議：在 §5 誠實限裡把這個具體案例點名寫出來
（例如加一句「P1 驗證的是標題錨的計數，不驗證區塊內容是否溢出自己的
邊界或跟鄰區視覺黏連——這類問題也落在『要用戶看過』那一類」），
讓下一個讀 spec 的人不會誤以為「P1 綠了」代表版面結構完全沒有內容溢出
風險。這是文件層的補強，不是要求加新的驗收格。
```

# 二、②P3 寬度常數——核過「讀到常數」這一半，找到「算法本身沒被驗證」這一半的真缺口

```
先確認你的疑慮成立：grep 全庫（`grep -rln "全角|全形|wide_char|char_width|
visual_width"`）零命中——目前整個專案沒有任何現成的 CJK 顯示寬度計算
函式。這意味著本票的實作會是**第一個**寫這個函式的，spec 沒有指定
「誰來算」的具體風險是真的：不只是「會不會長出第二份」的抄寫問題
（目前連第一份都不存在），更根本的是——P3 現在的兩道測試（120 只出現
一次／COLS 改 40 必紅）只驗證「寬度比較這一步真的讀了 COLS 常數」，
完全沒有驗證【寬度計算函式本身算對了沒有】。

★具體風險：一個永遠回傳 `text.length()`（半形/全形都算 1）的寬度函式，
一樣能通過現在 P3 的兩道測試——因為兩道測試改動的都是 COLS 這個門檻值，
不是拿一個「已知全形/半形混合、已知正確答案」的字串去驗證計算本身。
一個不會分辨全形半形的實作在中文佔多數的畫面上會把顯示寬度算得比實際
窄很多，導致真正超寬的行被判過關。

建議：加一格獨立的【定樁測試】——構造一個已知組成的字串（例如 N 個全形
字＋M 個半形字），斷言算出來的寬度精確等於 `2*N + M`，不靠 COLS 擾動來
間接推論，直接驗證計算邏輯本身。這道測試不依賴任何動態擾動，是純粹的
「已知輸入、已知正確答案」比對，補上目前 P3 完全沒有覆蓋的那一半。
```

# 三、③P5 的 grep 粒度——核過風險是真的，跟本 session 今天已知的同型陷阱一致

```
判斷成立。你點名的「兩次錨的身分沒被限定」的教訓在這裡完全適用，而且
這個 session 今天在別的機制上已經直接見過同一種陷阱的活例——simp-lint
那個檢查（本 session 開場系統提示裡就有）明文承認它的已知局限：「討論
這些字的文件本身是正當的提及」，也就是【描述規則的註解文字】會跟【真正
違反規則的程式碼】長得一模一樣，純文字比對分不出來。P5 這個 grep（比對
「（不可：」後面出現字面中文）完全可能踩到同一個坑——例如 UI 檔案裡
一定會有類似「★排版層禁自己寫死原因（不可：庫存不足 這種字面）」這種
解釋規則本身的註解，逐字含有「（不可：」+ 中文，會被 grep 誤傷成假紅
（或者更隱蔽：若 grep 邏輯設計成「找不到就算過」，也可能被一段無關的
註解意外「救」到，讓真正違規的程式碼被漏掉——取決於 grep 的比對方向）。

建議：比照本床全域已經在用的 `_code_only()` 手法（先剝掉整行以 `#` 開頭
的註解，本 session 今天看過的好幾支床都用這個手法），對 P5 這個 grep
也套用同樣的前處理；並且把搜尋範圍限定在真正負責 render 這個動作區塊
的那一支/那幾支函式，不要對整份 UI 檔案做裸搜——範圍越窄，誤傷註解或
別的區塊的機率越低。
```

# 四、④P7 母體來源——核過疑慮成立，建議 spec 明講來源不要留給實作端自己找

```
同意這個擔心：「招募／打聽／外交／勢力」這四個名字若寫死在 spec 裡，
會漂（跟 spec 本身脫鉤，UI 新增第五個展開層時沒有人會想起回來改這裡）。
我查了字母鍵那張票（本 session 稍早審過、CLEAN）驗證過的 13 個 `_mode`
布林旗標（`_input_mode`／`_trade_mode`／`_interact_mode`…），這批旗標
涵蓋的範圍比本票說的「展開層」更廣（含 pre_encounter／advisor 等不屬於
「動作區的展開子選單」概念的模式），不能直接拿來當 P7 的母體——但它
證明了這個專案已經有「UI 模式」這個機械可列舉的概念存在，本票的「展開
層」很可能是這 13 個的一個子集，或需要另一個更貼切的既有列舉。

建議：spec 這裡不需要現在就定案是哪個常數/列舉，但應該明講「P7 的母體
必須是【implementer 找到的、真的存在於 code 裡的某個可列舉來源】，不是
spec 手抄的四個名字」，並把「找出那個來源」列為 implementer 動工第一步
要交代的東西（同 §2⑤對格動作/自家隊動作母體的處置——找不到單一來源
就回報不要造）。這樣即使 spec 現在寫死四個名字當佔位描述，implementer
也知道正式驗收要換成真正的機械來源。
```

# 五、§5 誠實限機械化——同意做成床的常駐輸出，不只是一句 spec 文字

```
同意你的傾向，判斷理由：本 session 今天在好幾張票上反覆驗證過同一條
通則——寫在信裡/spec 裡的要求不是執行單位，落成床裡會被看到的一格
（或至少是一行常駐輸出）才是。這一條誠實限本身雖然不是一個會紅的斷言
（它宣告的是「機器判不了」這件事本身），但把它做成床跑完必印的一行
（例如「★本床只證結構；『排列合理且資訊豐富』要用戶看過才算」），
比只寫在 spec 裡多了一個實質好處：**每一次跑床、每一次看到全綠，這句
話都會跟著出現在同一份輸出裡**，物理上防止「床綠了」被誤讀成「可以交」
——跟你今天在死輸入床、字母鍵那幾張票已經驗證有效的「陽性對照 sha 印在
同一份輸出裡」是同一個原理（把重要的限制性資訊釘在結果旁邊，不是釘在
另一份只有第一次讀 spec 的人才看得到的文件裡）。建議直接做。
```
