# threat 已統一 + ★戰略觀察：稽核系統性 over-count「各算」

R① threat（第三次驗，第三種結局）：

## threat R① = 混合（like need 2 軸），premise 大幅 FALSE
- **threat 感知（被威脅）= 已統一**：只 `ThreatAssessment.score` 一個函式、**4 個呼叫點皆讀同源**、門檻面**只 1 個 base 常數 + 人格衍生 + 用途 margin**（preempt/flee/備戰各司其職，非 3 個獨立不一致門檻）。**稽核「8 處各算 / 3 門檻不一致」不成立**——threat 感知**本就是 oracle**。
- **`_should_attack` = 真獨立公式**：自己的 strength-ratio 評分，**攻擊發起判斷 ≠ 被威脅感知**（不同方向/軸，如 need 的 demand vs need_keep）→ **不該被 naive 合併**（合併=方向錯，like 你我在 need R² 抓的單標量混反向）。
- ∴ **Arc2 threat-oracle 幾乎無 de-patch 工**：感知已統一（skip/close）、`_should_attack` 是 legit-separate 攻擊軸（留，別併）。

## ★★戰略 meta（值得你 roadmap 層看）：稽核系統性 over-count「各算」
全庫稽核的「N 處各算」斷言**連三次被 R① 打臉**：
| arc | 稽核宣稱 | R① 實際 |
|---|---|---|
| need | 散 7 處各算 | **2 軸混**（quantity vs urgency）+ **1 項真 de-patch**（facility_deficit） |
| dispatch | 三重繞過引擎 | **4 個同引擎 filtered subset**（已統一，cosmetic） |
| threat | 8 處各算/3 門檻 | **已統一**（ThreatAssessment.score）+ 1 個 legit-separate 攻擊軸 |

**模式**：**憲法溶解 arc（序1-8）早把 threat/survival/dispatch 統一了**——稽核把「同源 filtered subset」「不同軸的 legit 分立」誤讀成「各算」。**真 de-patch 工到目前只有 Arc1 的 facility_deficit 一項**（need-quantity 那也是靠實作中發現）。

## 建議（你裁 roadmap，我地盤是 HOW 不擅自改序）
1. **threat-oracle（Arc2）= 判已達成/skip**（感知已 oracle、攻擊軸別併）——除非你要我把 `_should_attack` 做成獨立「攻擊 assessment oracle」（那是新 scope 不是「統一 threat」）。
2. **剩 roadmap 4-7（_threat_recent 閘 / 死常數人格化 / 情緒 / 政治）→ 各先 R①-verify 才假設有工**——照三次經驗，恐多是已做/不同軸/cosmetic。
3. **★重估：真剩的高值 gap 恐不是「統一」（憲法溶解已做大半），是經濟/行為**——如死法② deal-wall（Arc1 揭的成交牆，真影響玩起來）、死常數人格化（照妖鏡族真 behavior 病）、情緒接線。**建議 roadmap 重心從「統一散亂」轉「真 behavior/經濟 gap」**（統一大多是幻影，R① 一驗就散）。
