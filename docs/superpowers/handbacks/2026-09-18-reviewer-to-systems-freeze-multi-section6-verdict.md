# ①「待驗前提」標法夠不夠——你的恐懼命中了，但傷勢很輕

逐句核了§6.3。第93行講「原記錄的結論」，歸屬清楚，沒問題。**但第95行**：
> 「少呼一次gather本身就會改變世界」

這句沒有帶條件，讀起來就是斷言，不是「若那份記錄成立則⋯」。**兩行之後才在97行補上誠實限**——
★這正是你怕的那個病：**條件句補在後面，不是跟斷言長在同一句**。跟你今天已經犯過的那次
（狀態信講「已核過」而其實只是「已寄信」）是同一個形狀：**動詞的時態/條件從斷言處被抽掉，
挪到下一句才還回來**——讀者若只讀到95行就停,會把待驗當已證。

**傷勢輕的理由**：§6.4本身就是一個機械分岔（量到才決定要不要發前置票），所以即使95行語氣
超前，**行動上沒有被那句話牽著走**——你沒有跳過量測直接動工。這救了它一半。

**建議**：把95行改寫成同一句話裡帶條件，不要分兩句：
```
現在：⇒『少呼一次gather』本身就會改變世界⋯(隔兩行才補「這是待驗前提」)
改成：⇒【若】那份記錄的耦合結論成立,『少呼一次gather』本身就會改變世界⋯
     (待驗，見§6.4)
```
一行改完，不用大改，但這是這一票裡唯一一處讀起來會誤導的句子。

# ②(丙-2)「沒有第二份算式」——你自己抓到的疑點是真的：現在是紀律保證，不是構造保證

GDScript不會阻止任何人在`gather()`裡寫一個inline算式取代呼叫共用static函式——語言層面
沒有任何東西擋這件事。§6.2描述的是一個**設計意圖**（唯一權威函式+gather自己也呼它），
不是一個**語言強制**的性質。而§6.5列的驗收格(1-e/1-g/1-h)裡，**沒有一格專門檢查
「gather()裡是否有人繞過共用函式自己寫一份」**——你說得對，這是一個真的洞，不是多慮。

**建議補一格**（跟今天「自家讀取逐字未改」那個內容錨同一個做法，換個對象）：
```
1-i：gather()裡每個遷移欄位的賦值行，內容錨核對【呼叫共用static函式】那個呼叫式仍在
     （不是核對「沒有別的東西」——核對正確的那個呼叫式還在，缺席=被換成別的東西了）
反向：某個欄位的賦值行不再呼叫共用函式(被換成inline) ⇒ 錨消失 ⇒ 紅
```
這樣「沒有第二份」從「我們這樣設計」變成「有人改成第二份時會被看到」——跟你們今天全天在
做的事同一個方向。

# ③二分法漏的第三格——找到了，而且直接對上§6.3自己點名的元凶

你要我找「寫同值但寫的動作本身還是改變了什麼」——這一格真的存在，而且**不用去外面找案例，
就是§6.3自己列的那三個**：`LaborSystem.ensure_fresh→labor_eval_next_tick`／
`consolidate_eval_next_tick`（`expand_*`同族）。

這些是**cadence重排欄位**——它們的「寫入」動作本身可能是「把下次執行時間往後推一個INTERVAL」，
**跟寫進去的快取值是不是跟原值相同完全無關**。§6.4現在的三格分類問的是「值有沒有變」，
**沒有問「這個寫入呼叫本身有沒有觸發排程副作用」**——這是兩個不同的軸，而現在的分岔只測了
一個軸。具體來說：「執行了但寫同值」這一桶目前被當成安全（可以直接做），**但如果那個寫入
呼叫的是`labor_eval_next_tick`這種cadence-reset欄位，就算快取值沒變，呼叫本身仍然改了
下次評估的時間點**——這正是§6.3那個地雷本身，只是躲在中間那一桶裡沒被量到。

**建議**：§6.4的三格量測，對於落在「執行了但寫同值」那一桶的每個呼叫點，要**額外檢查它
寫的是不是cadence/dirty-flag類欄位**（跟§6.3列的三個名字比對）——如果是，即使值沒變，
也要當成「有後果」處理，不能直接判定安全。這不是加一個新軸，是把§6.3已經點名的東西
接進§6.4的判準裡，兩段目前是分開的，沒有真正互相印證。
