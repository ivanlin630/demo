# 判決：`issues`（中），`premise_contradiction: false`

## ★①第七件（待領貨帳）——確認是紅線必然推論，不是做大票

紅線管的是「不在場的一方不能瞬間拿到資產」——這條規則的主語是【不在場】跟【瞬間取得】，沒有限定資產型態是錢還是貨。到期退貨時賣家一樣不在場，貨若直接回 `team.resources` 就是同一種瞬移，只是方向相反、資產型態不同。這個推廣是**同一條紅線的邏輯閉包**，不是額外加戲——如果只做「待領款」不做「待領貨」，會出現一個站不住的不對稱：錢不能瞬移、貨可以瞬移，而使用者的紅線完全沒有給這種區分留空間。你判斷這是必然推論，我同意。

**唯一想補的一個效率建議**（不是擋票的理由）：意圖帳:43「兩種各自要配三件套」不必然代表兩套完全獨立、互不共用的實作——腦欄位（「自己的單據天生在手」）跟 option 秤重（「額×距離/時間折現」）這兩件事，錢跟貨的邏輯形狀幾乎一樣，只差 `kind: coin|goods` 這個判別欄。建議先看能不能做成一個泛型「待領資產」抽象（單一資料結構＋單一 option 生成邏輯，內部按 kind 分支），而不是寫兩套並排的重複程式碼——這樣「兩種資產各自有念頭」這個 WHAT 仍然滿足，但實作成本跟未來維護的重複面積會小很多。這不是必須照做，只是提醒別把「概念上兩種」直接翻譯成「程式碼上兩套」。

## ★★★②權威搬家會不會逼出爛形狀——讀了 `settle_orders`，抓到一個真的會撞的假設

讀 `order_system.gd:371-400`（`settle_orders`）的docstring自己講死：**「按窗內 res 淨持有變化沖 active_orders（純記帳，不碰 resources）」**——這支函式的運作方式是：**觀察 team 自己 `resources` 在交易窗前後的變化量**（`avail = pool[res] = 現在持有 − before 快照`），用這個**漸進的 delta** 反推「這張單填了多少」，然後把推出來的填量寫回 `qty_remaining`。**它完全不讀 tile 板上的任何東西**——它相信的是「我自己的 resources 動了多少，我的單就填了多少」。

**這個假設在 escrow 底下會被打破**：現況（§1 描述的舊制）下，賣家的 `resources` 是**隨著每一筆真的成交才漸進減少**——這正是 `settle_orders` 賴以推論的訊號。**但 escrow 底下，賣家的 `resources` 是【掛單當下一次扣光】**（§3②：「掛賣單即交貨入市場保管」）——**posting 那一刻，`resources` 就已經掉了整個 `qty`，之後不管賣掉多少，賣家自己的 `resources` 都不會再變**（因為貨已經在 tile escrow 裡，扣減發生在 tile 的庫存，不是賣家的 `resources`）。

⇒ **如果 escrow 賣單沒有被明確排除在 `settle_orders` 現有的 `sell` 分支之外，會出兩種錯的其中一種**：
1. **posting 瞬間就被 `settle_orders` 誤判成「整單立刻成交」**（因為它看到 `resources` 一次掉了 `qty`，跟「全部賣掉了」長得一模一樣），`qty_remaining` 提早歸零、單被移除，但貨其實還在 escrow 裡沒賣出去；或
2. **之後真正的成交完全偵測不到**（因為賣家自己的 `resources` 在成交當下根本不會再變——變的是 tile escrow 的庫存），`qty_remaining` 永遠停在 posting 後的殘值，訂單狀態跟 escrow 的真實庫存**永久分歧**。

**這正是你自己擔心的「權威搬家後鏡像與實貨分歧，沒有人知道該信哪個」——而具體撞上的地方就是 `settle_orders`，不是抽象疑慮。** 這一格**必須在 spec 裡寫死**：escrow 賣單要嘛完全不進 `settle_orders` 這個既有迴圈（例如用新的 `kind` 值如 `"sell_escrow"`，讓現有 `elif o["kind"]=="sell"` 天然不匹配、自動繞開），要嘛在 `settle_orders` 迴圈開頭明確 `continue` 跳過帶 escrow 標記的單——由 escrow 專屬的新結算路徑（讀 tile 庫存的真實變化，不是賣家 `resources` 的變化）接手這些單的 `qty_remaining` 維護。**不寫這條，這張票落地的第一天就會撞上你自己點名的那個分歧問題。**

## ★③「野外率」當驗收——同意，這是誠實揭露不是留退路

母體可能為空（90 日內沒有隊路過那個市場）時判「不可判」而非判紅，跟今天已經反覆用過的「母體太窄／母體為空不是失敗是不可判」同一種紀律（今天墓碑那張票的 `outpost_owner`／`leader_team_id` 那兩個 0，判法完全一樣：母體非 0 才代表迴圈有跑到，母體是 0 就是這個窗沒有這種情況，不是機制壞了）。**這不是替自己留退路，是誠實揭露母體規模**——區分「母體為空」跟「母體非空但比率是 0」是兩種完全不同的結論，混在一起才是真正的作弊。你要求把分母（有待領帳的隊數 × 是否曾經路過）跟野外率一起印，這正是防止「母體為空被誤讀成機制失敗」的正確做法，同意保留。

## §4/§5 其餘——沒有意見
尺寸與砍法（買單押錢後補>到期退貨簡化>待領帳不可砍）、驗收的鑑別力設計（拿掉待領帳判準1必須紅、拿掉領款option野外率必須掉到0）都是對的紀律，沒有要補的。

## ⇒ 要你補的
1. spec §3② 或 §5 補一句：escrow 賣單必須明確排除在 `settle_orders`（`order_system.gd:371`）現有的 `sell` 分支結算邏輯之外，改用讀 tile escrow 真實庫存變化的新結算路徑——附上「否則 posting 瞬間會被誤判整單成交，或後續真實成交完全偵測不到」這句具體理由。
2. （非必須）評估腦欄位/option 秤重能不能用單一「待領資產（kind:coin|goods）」抽象共用邏輯，減少兩套重複實作。
3. 其餘（①③的判斷本體）都同意，不用改。

**premise_contradiction: false；補上①即整票 CLEAN。**
