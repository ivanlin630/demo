# 重評估cadence查——可能是9-zero的真正上游根

## 背景
用戶要求撈一支代表隊的3個月完整決策時間軸，結果發現：**Team7整整90天只被重新決策過1次**（第19.5天選中覓食後，一路執行到population驟降至1，中間沒有再重新評估）。見`2026-07-13-measurer-to-blueprint-single-team-trace-result.md`。

用戶反應：這樣「選一次task鎖死執行到底」的行為，跟蟑螂反射沒兩樣，不是真正的持續認知。這重新框定了整個9-zero調查——**問題可能不在option之間的分數競爭（我們前面three輪tune的方向），是在「決策機制本身多久才重新跑一次」這個更上游的cadence問題**。如果決策90天才跑1-2次，那不管五層急迫度/係數表設計得多精細，大部分時間根本沒機會發揮作用。

## 待查（零跑，patch-gate-first：先查是不是死常數/觸發條件結構性不fire）
1. **`rank_scored_ctx`（或`_decide_unified`）的重評估觸發機制**——什麼條件下會重新呼叫決策引擎？是固定cadence（例如每N小時/天）、還是事件驅動（某個狀態變化才觸發）、還是「task執行完才換下一個」（意味著只要task還沒完成/沒失敗，就永遠不會重新評估）？
2. **這是不是刻意的「承諾」設計**——類似`COMMITMENT_BONUS`(同option加分防震盪)的精神延伸，故意讓隊伍「選了就做到底」避免每個tick亂跳？如果是，這個設計本身合不合理（承諾防震盪 vs 完全不重新思考是兩個不同強度的東西——現在看起來是後者，90天0次中途重評估，過度到蟑螂等級）。
3. **若非刻意設計，是觸發條件結構性幾乎不fire**——查具體是什麼條件（例如「task失敗才重評」但task「覓食」在這個case裡從未真正失敗只是隊伍population掉了，導致從沒觸發重評；或者「某狀態變化超過門檻才重評」但門檻設太嚴)。
4. **Team14案例對照**（population波折最大10→2→0→2，但decision_count=0，全程走ThreatResponse/survival-override路徑）——這條路徑本身是否也是「一旦進入就不會離開」，跟主決策路徑一樣有「鎖死不重評」的同型問題？

## 為何這可能是真正的上游根
若確認cadence/觸發機制本身有問題（過度鎖死，非合理的「承諾防震盪」），那之前三輪normalize/T5的努力方向雖然沒錯（層內base確實有問題），但**可能不是9-zero現象的主因**——就算把備戰/訓練的分數調到贏過覓食，如果決策機制90天只跑1次，這些option被評估到的機會本來就少得可憐，跟分數高低關係不大。

## 序
零跑出重評估cadence機制真相 → to:blueprint → 我判是否為真正上游根 → 若確認是，這是比term-scale-normalize更根本的修法對象，需要重新評估T1-T5那些努力的定位（可能仍有價值但非主因）；若否，回頭繼續之前的tune方向。
