# ★★★一、停下那條路，而理由是【我開錯了規格】
```
★我裁 A 階段時寫:「我們要的是 runtime 真的執行到【幾處】」
   ⇒ 「處」= 行粒度 ⇒ 你朝那個解析度做 ⇒ get_stack() ⇒ --debug ⇒ 卡住
★★而 blueprint 預註冊的分流判準,三條【全是床／結論粒度】:
   (a)被【意圖帳／裁決】引用過的數字
   (b)推過【用戶 TG】的結論
   (c)當過【merge-gate 判準】的【床】
⇒ ★★★沒有一條需要知道是【哪一行】—— 需要知道的是【哪一支床】
```
> ★**所以這兩輪的成本是我造成的**：**我在問「要多細」之前，沒有先問「決策需要多細」。**

# ★★二、正解（★用你【已經有】的儀器，不需要新東西）
```
逐床跑 ⇒ dump `TeamData.swallowed_writes` ⇒ ★非空 ⇒ 那支床【受污染】
⇒ ★★不需要 get_stack、不需要 --debug、不會卡住、也不動 fp 可比性
⇒ ★★★而輸出就是 blueprint 要的那份名單:【一列一支床】
```
★**而每支床只需要兩個欄位**：`床檔名` ＋ `寫到了哪幾個屬性`
—— ★★**「哪一行」留到 stage B 拆的時候自然會知道（那時你會逐站改）。**

# ★★★三、而你那個 `--debug` 發現要留著（★它是一條通則的實例）
```
`--debug` 讓 get_stack() 有值 —— ★而它【同時】把 assert() 失敗變成互動式 debugger break
⇒ ★★那一跑卡在 `Enter "help" for assistance.` 等 stdin,永遠不會結束
⇒ ★★★而 main baseline 上本來就有紅 assert ⇒ 這條路【對任何有紅 assert 的床都走不通】
```
> ★**通則：一個【為了觀測而開的旗標】不是語意中性的** ——
> ★★**它可能同時改掉一件你沒在看的事**（這裡是 assert 的失敗行為）。
> ★★★**而症狀是【卡住】，不是【報錯】—— 那正是最難歸因的那種。**

★**我已把它寫進 `detail/invariants-cases.md`**（連同 `--debug` 不是 fp-comparable 那條），
**因為下一個想用 `get_stack()` 的人會踩同一個坑。**
