# QA 角色復活 + 升級「驗收官」（寫進硬流程）

用戶裁。背景諷刺收據：`04_qa.md` 第一行早寫著「**用戶不該當 debugger**」——角色存在、原則寫著、從沒排進流程 = 「文件教訓沒變機器」最痛實例。這次把它變機器。

## 為何必要（獨立性,非人力）
R1-R6 機器抓可量化的；「這世界怪不怪」的判斷層需要一顆**非蓋房者**的腦——貿易 6 筆就是 builder 自驗放行的（R5 確認偏誤）。**maker/checker 分離** = QA session 不可被機器取代的價值。

## 成本控制（不浪費）
- **頻率**：wave 邊界 + 任何東西交用戶之前。**非每 merge**（CI 常駐回歸管 per-merge）。
- **消費現成產出**（率表/ticker/截圖/GUI），不重建 harness。
- 對比：一輪 QA ≈ 一次專注 session；一個逃逸缺陷 ≈ 抗議+回溯+補機器+返工+信任損耗。

## 角色定義（WHAT,請落 process docs——你 own）
```
驗收官（QA session）四職：
  1. 充足性稽核判決官  跑/讀全系統率表(帶分母),世界句子審計,
                      標 荒謬/稀薄/健康,出判決表
  2. 戲感觀者(③owner)  開 GUI/讀 ticker 當觀眾——「觀者看得下去嗎」
  3. release gate      交用戶前 QA 必綠 = 硬閘(無 QA 綠不得交付)
     + escaped-defect ledger 管理(每筆逃逸→回溯哪層該抓→開補機器工項)
  4. UI 落差掃描       舊 04_qa 三類(可達性/顯示/對稱)保留
邊界不變：只找不修、不裁 WHAT(藍圖)、不修 HOW(系統)、不寫 sim code。
輸出：判決表/落差清單 → handback 交藍圖裁修序、系統修。
```

## 分工釐清
- 系統：備 harness/探針/率表產出機制（機器層）。
- QA：跑+判+守門（判斷層）。
- 藍圖：收判決表裁修序（WHAT 層）。
- 用戶：只看 QA 綠後的成品,說好不好玩/要什麼（願景層）。
