## Q1：「曲線形狀」驗收怎樣才可執行、不算過度解讀
你的擔心對——「斜率變了」沒有定義幾個點/怎麼算就會變成各自解讀。★**建議**：
- **隊數階梯至少 4 個點**，涵蓋現況到目標的範圍（例如 10/20/35/50+，你的 slice 0 已經在做隊數階梯，這裡只是要求最少點數）。
- **判準**：log-log 對 (隊數, per-tick 中位數) 做線性迴歸取斜率 `k`（`cost ~ N^k`），**同一組隊數階梯**、同機器，比較刀前 `k_before` 與刀後 `k_after`。
- **紅/綠線**：`k` 沒有顯著下降（例如降幅 < 0.3，或仍 `k≥1.5` 這種明顯超線性區間不變）⇒ **只是截距降了，沒治 N²**，照原樣回報，不宣稱治好。
- 這樣「怎麼算斜率」「幾個點」「多少算過度解讀」三個都有具體、可重跑的答案，不是你或 implementer 各自感覺。

## Q2：⑤隊數收斂標成「含行為面」的判斷——**對，這條判斷正確，不要當純 perf 刀**
①②③④四刀的共同前提是「同一個世界,算得更快」——`fp` 不變（或至少行為等價）是它們的及格線。⑤直接改變**世界內容**（隊變少=故事變少），如果混進純 perf 驗收（只看 tick/s），行為退化會被效能數字掩護過去（tick/s 進步,沒人去查「為什麼變快了,是不是因為世界變無聊了」）。**⑤需要獨立的行為面驗收**（例如某種多樣性/湧現指標不能因收斂而顯著下降），跟①②③④的「純變快不變世界」分開判準,你的隔離判斷是對的。

## Q3：五刀之間會不會互斥（例如②讓③收益消失）——**風險真實，但答案不是讀 code 猜出來的，是你的 slice 0 方法論本身就能回答**
