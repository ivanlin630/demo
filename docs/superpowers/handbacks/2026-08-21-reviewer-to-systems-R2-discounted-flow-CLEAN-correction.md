# R② 判決：延遲價值折現原語（第一磚）

**判決 = CLEAN + 1 必查項**。①抓到一個具體、跟蟑螂地板同等重要的坑；②③④逐一答覆。

## ★①H_eff沿用facility_roi：方向對，但有一個camp專屬的坑，會從另一條路徑繞過蟑螂地板
親讀 `facility_roi`(marginal_economy.gd:59-73，你標:59-66差7行、同函式)確認邏輯：`net_after<0時 effective_days=min(H,food_est/-net_after)`——**這條殘存活窗用的是「當前存糧」`food_est`**。

**沿用到 camp 情境時有一個 facility 沒有的坑**：`facility_roi` 服務的是**已經有據點、正在考慮升級**的隊——這種隊通常有基本穩定的糧食底子,`food_est` 不太可能貼近零。**但 `camp` 服務的正是這整個 arc 診斷出來的那群隊：`camp_level=0`+零被動所得+瀕餓（runway 1-4天)**——**這正是 `food_est`（當前存糧)系統性偏低甚至趨近零的那群人**。

**具體機制**：若紮營後 `net_after` 仍然是負的（紮營有幫助但還沒完全解決缺口,只是沒那麼慘)，`effective_days=food_est/-net_after` 用的分子是**這群瀕餓隊自己已經很低的存糧**——H_eff 會被壓得很短,短到 `Σ_{t=1..H_eff}` 這個加總本身就快接近零,**不管 δ 有多高都救不回來**。

**這正是你自己在 §2.5 蟑螂地板要防的那個結論（"原地永遠覓食變最優"），只是這次不是從 δ 塌陷進來,是從 H_eff 塌陷進來**——**同一個病、兩條不同的數學路徑**，而你 gate 3 的證偽測試（「把人格推到最短視極端」)**抓不到這條**，因為 H_eff 塌陷不是人格驅動的,是**團隊當前存糧狀態**驅動的,跟人格極端測試完全正交。

**必查項**：這條要求你明確處理,建議二選一：
- **(a)** H_eff 的殘存活窗改用一個**不會因為「本來就窮」而自我懲罰**的量——例如改用「紮營後的 `net_after` 本身」或某個跟目前絕境無關的固定視野下限,而非直接借用 `food_est`（畢竟 camp 情境下 `food_est` 低正是問題本身,不該同時是「不准你投資」的理由)。
- **(b)** 若堅持沿用 `facility_roi` 原封不動的公式,則**蟑螂地板的證偽測試(gate3)必須額外覆蓋這個維度**——不只測「人格推到最短視」,還要測「團隊存糧推到最低（零被動所得+瀕死食物量)」,兩種極端**各自獨立**驗證「永遠覓食」仍是劣解,不能只驗其中一種就宣稱地板守住。

我沒有偏好哪個選項,但**要求 dispatch 前二選一定案**,不能讓這條沿用悄悄帶著一個沒被蟑螂地板覆蓋的塌陷路徑進場——地板的存在意義就是"任何路徑都不准讓永遠覓食贏",漏一條路徑等於地板沒有真的釘死。

## ②δ_floor 求法：這輪建議先給worst-case數值推導,不留白
你的疑慮（不確定有沒有封閉解)判斷正確——`Σδ^t` 本身是幾何級數有封閉和公式,但要反解出讓「camp贏過永遠覓食」這個不等式成立的 `δ_floor`,牽涉 H_eff／inflow_est／cost／forage_floor 這些跟情境相關的其他變數,**一般不存在跟這些變數無關的通用封閉解**——但這不代表只能留白讓 implementer 猜。

**建議做法**（跟你這輪 breed-rate 那份 spec 定 K/BASE_RATE 的方法論一致)：挑**最壞情境**（inflow_est 最低、cost 最高、H_eff 最短的合理組合，取真實量測數據的邊界值)、把不等式**數值代入求解**（二分搜尋/試算表逼近即可,不需要優雅封閉式)、**把推導過程與最終數字透明寫進 spec**——跟你們這幾輪一路的「常數留白等量測,但推導方法/worst-case 定義要先講清楚」紀律相同。**這輪建議直接做**（不是必查項,是流程建議),因為①的 H_eff 坑一旦定案,δ_floor 的 worst-case 情境定義會需要同時考慮①選的方案,兩者最好一起收斂,不要分兩輪各自定一半。

## ③人格映射（δ←耐性/慎重,w←貪婪/野心/好戰控制哪條流)：讀對了
「貪婪對賺錢型未來收益折得少」實作成調 `w_錢流`（在意哪種明天)而非調 `δ`（看多遠)——這個區分正確：**δ 控制的是「時間範圍」，w 控制的是「哪個維度重要」**，貪婪的人可以同時是「對錢很有耐性、對其他事沒耐性」，這正是「貪婪≠短視」這句用戶原話的精確數學翻譯。你沒有讀錯。

## ④scope 限建點/建設類：公式層級真的限得住，argmax結果層級的位移是預期效果非洩漏
其他 option（覓食/乞食/貿易等)的**util 公式本身完全沒被這輪改動**——它們各自的 `terms.gd` weight×eval 邏輯不讀 camp 的 baseline、不共用任何運算,親讀 `MarginalEconomy`/`facility_roi` 系列函式確認全是純函式（吃 struct 吐 float,零共享可變狀態),沒有側面洩漏管道。

**你擔心的「相對排序被動變動」——這確實會發生,但它是這刀的目的不是洩漏**：camp 的 util 分數提高後,在原本 camp 該贏但因為舊基準線誤判輸掉的那些情境下,argmax **結果**會換人贏——**這是修好的行為，不是 scope 破口**。scope 有沒有守住,要看的是「有沒有動到其他 option 的**計算公式**」（沒有),不是「argmax 選誰有沒有變」（本來就該變,那是這整個arc要修的東西)。這條你可以放心,不需要因此擴大範圍。

## 結論
**CLEAN → 可等①②收斂後 dispatch**。★必查項①（H_eff的food_est坑,二選一補蟑螂地板覆蓋或改公式)必須定案。②建議這輪一併給δ_floor的worst-case數值推導,非阻塞但建議跟①一起收斂。③④確認你讀對/沒有洩漏,不需要修改。
