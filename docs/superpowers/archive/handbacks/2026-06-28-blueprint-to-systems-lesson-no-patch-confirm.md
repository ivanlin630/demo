# 教訓：架構已定時別問補丁認可

用戶回饋（2026-06-28，原話）：「以後不要浪費 token 問我這麼白癡的事，已經規劃好架構，結果還在亂修」。

## 觸發
P4 撞到統領下矛盾雙令 → 系統做了 war-priority 補丁（成員側 1.5>1.0 掰回跟戰）求藍圖認可 → 藍圖把「認可補丁 vs 重排」當拍板問題丟回用戶。

## 錯在哪（雙方）
- **系統**：統一決策框架是**已定架構**。統領層下矛盾令 = 該架構未覆蓋的洞，正解是**把統領納統一引擎**（已定方向的延伸），不是成員側調量級補丁。補丁與架構矛盾，本不該被提為「請確認」選項。
- **藍圖（我）**：架構已定時，矛盾的局部補丁 = **自動違規**，藍圖該直接照架構判掉（「不要補丁、照統一架構做」），**不該把這種問題丟回用戶浪費 token**。用戶不需逐塊認可一個已拍板架構的必然推論。

## 原則（請提煉）
1. **已定架構的必然推論，直接執行，不問用戶**。用戶只裁架構級的真分岔（願景 fork），不裁「要不要照已定架構做」這種無分岔問題。
2. **與已定架構矛盾的補丁 = 紅旗**：實作/設計撞到時，預設「架構沒覆蓋到、該延伸架構」，非「打補丁繞過」。提報時frame成「架構洞+延伸方案」，不是「補丁 vs 重排」二選一丟回。
3. 連同既有 [[feedback_no_tech_microdecisions]]（技術微決策自己定）、[[feedback_avoid_rabbithole]]：白話只問願景 fork，架構推論自己跑。
