# Open Questions

> 之後所有玩法、系統、數值、UI 問題都寫在這裡。  
> 每條問題建議使用一個編號，方便追蹤。

使用方式：
- 新問題請往「問題清單」追加下一個編號。
- 有定案就移到「討論結論（Decision Log）」並回填對應問題編號。
- 狀態建議使用：open / in-progress / closed。

## 問題清單

### Q-001（狀態：closed）
- 主題：大地圖鏡頭型態（俯瞰與縮放）
- 背景：原先鏡頭偏斜視角，資訊閱讀密度不足。
- 目前方案：正俯瞰 + 可縮放（鍵盤與滑鼠滾輪）。
- 擔憂點：縮放範圍過大時 UI 與標記可讀性下降。
- 期望結果：在不同螢幕解析度下都能穩定閱讀地圖與勢力標記。

### Q-002（狀態：closed）
- 主題：時間制度切換（半即時制 / 回合制）
- 背景：玩家希望依情境切換操作節奏，而非單一制度。
- 目前方案：可一鍵切換制度，HUD 顯示當前制度與時間狀態。
- 擔憂點：兩種制度切換時行為一致性與可預測性。
- 期望結果：切換後規則直覺、玩家不需要重新學習操作。

### Q-003（狀態：closed）
- 主題：回合制下移動是否推進世界時間
- 背景：若移動不推進時間，會破壞世界一致性。
- 目前方案：回合制每移動一格即推進一回合世界時間。
- 擔憂點：移動成本是否過高導致體驗遲滯。
- 期望結果：保持世界一致性，同時不讓探索節奏過慢。

### Q-004（狀態：open）
- 主題：回合制移動時間成本平衡
- 背景：目前固定為每格 +1 回合，簡單但可能偏硬。
- 目前方案：先維持固定成本，收集實玩回饋。
- 擔憂點：長距離移動過慢，可能壓縮探索意願。
- 期望結果：提出「地形/道路/隊伍規模」影響移動耗時的中期方案。

### Q-005（狀態：open）
- 主題：大地圖資訊層級（標記密度與可讀性）
- 背景：六角格 + 俯瞰後，標記資訊量持續增加。
- 目前方案：保留據點與基礎勢力資訊。
- 擔憂點：中後期勢力增多時畫面擁擠。
- 期望結果：定義縮放分級顯示規則（遠景顯示摘要、近景顯示細節）。

### Q-006（狀態：open）
- 主題：訊息傳播同步規則（接觸傳播 vs 據點同步）
- 背景：目前有延遲傳播與失真，但玩家缺乏可觀察工具，也未定義「接觸同步」與「據點公眾情報同步」邊界。
- 目前方案：短期採「進據點同步公眾情報，敏感情報不自動同步」；中期再擴充角色接觸觸發傳播。
- 擔憂點：若直接做全接觸傳播，系統複雜度與效能成本過高，且難測試。
- 期望結果：
	1. 增加訊息傳播 Debug 視窗（來源、carrier、延遲、強度、失真、到達時間）。
	2. 定義 public / sensitive 情報分類與同步規則。
	3. 製作最小可玩流程：進據點 -> 同步 public pool -> UI 顯示新增資訊。

### Q-007（狀態：in-progress）
- 主題：時間尺度定義（Turn 與 Tick 的關係）
- 背景：目前回合推進與移動推進規則已存在，但「世界最小時間單位」尚未被正式定義。
- 目前方案：將 Tick 定為世界最小模擬單位；Turn 定義為玩家輸入/操作節點（可映射成 N Tick）。
- 擔憂點：若不先定義，會導致大地圖移動、遭遇戰、情報延遲、聚落演化各系統時間不一致。
- 期望結果：
	1. 在設計文件明確寫出 Turn -> Tick 換算規則。
	2. 各系統（行軍、戰鬥、情報）統一使用同一時間參考。
	3. UI 顯示可同時理解「目前 Turn」與「世界時間進度」。

### Q-008（狀態：in-progress）
- 主題：單位速度屬性如何映射移動 Tick 成本
- 背景：目前玩家移動 1 格固定推進 1 Turn；尚未把「速度差異」納入時間成本。
- 目前方案：引入 speed 屬性，將「每格移動成本」由固定值改為函數計算。
- 擔憂點：
	1. 若速度影響過大，會破壞節奏與戰術可預測性。
	2. 若只改玩家不改 NPC，系統公平性不足。
	3. 若未設上下限，可能出現極端高速或幾乎無法移動。
- 期望結果：
	1. 定義基準成本：base_move_tick_cost（例如 10 Tick/格）。
	2. 定義速度公式：move_tick_cost = clamp(round(base / speed_factor), min_cost, max_cost)。
	3. 玩家與 NPC 共用同一公式（可有不同 speed_factor 來源）。
	4. UI 能顯示當前單位「預估每格耗時」。
	5. 提供至少 3 組測試檔位（慢速/標準/高速）驗證節奏。
- 實作切分建議：
	1. Phase A：僅玩家套用速度成本，先驗證手感。
	2. Phase B：擴充至 NPC 行軍與追擊。
	3. Phase C：地形、道路、負重、疲勞作為乘數疊加。

- 目前進度：
	1. 已實作 Phase A：玩家移動改為 speed_factor -> move_tick_cost 公式。
	2. 已在 HUD 顯示玩家每格移動 Tick 成本。
	3. 已實作 Phase B：FactionData 加入 speed_factor（世界生成時隨機 0.5~3.0）與 march_tick_acc；faction_system 每 Turn 累積 Ticks，累積量 >= march_tick_cost 才觸發擴張；UI 據點面板顯示勢力行軍速度與 Tick 成本。
	4. 尚未實作 Phase C（地形乘數）。

### Q-009（狀態：in-progress）
- 主題：事件是否應從個體 NPC 模型生成
- 背景：目前事件多由勢力數值與回合條件直接驅動；你的期望是先從領主、人民、代表 NPC 的反應開始，再彙總成勢力層事件，且世界資源與消耗也應先經過人物層。
- 目前方案：先定義雙階段結算與最小個體模型，讓事件從實體角色的狀態變化產生，並把資源消耗接到人物需求。
- 擔憂點：
	1. 若個體模型太細，會過早增加效能與資料複雜度。
	2. 若只做抽象勢力數值，又會和你的世界觀不一致。
	3. 若沒有明確的事件彙總層，NPC 反應會變成零散輸出。
- 期望結果：
	1. 定義勢力內部的最小個體集合（領主、守衛、平民代表）。
	2. 將每回合結算拆成「資源/生存消耗」與「實體反應」兩階段。
	3. 由個體反應生成事件，再彙總成勢力訊息。
	4. 先做最小可玩原型，不一次展開全體 NPC。
- 實作切分建議：
	1. Phase A：建立個體角色資料與代表人物。
	2. Phase B：雙階段回合結算（含資源與消耗）。
	3. Phase C：個體反應事件彙總成勢力事件。

- 目前進度：
	1. 需求已整理為 Q-009。
	2. 尚未實作個體模型與雙階段結算。



## 討論結論（Decision Log）

### D-001
- 對應問題：Q-001
- 決策內容：大地圖鏡頭採正俯瞰，並支援縮放。
- 決策原因：提升全域判讀效率，符合策略層觀察需求。
- 影響範圍：鏡頭控制、HUD 操作提示、玩家視覺體驗。
- 後續行動：依實玩回饋微調縮放上下限與鏡頭跟隨速度。

### D-002
- 對應問題：Q-002
- 決策內容：支援半即時制與回合制切換。
- 決策原因：兼顧觀察演化與精準操作兩種節奏偏好。
- 影響範圍：主循環、輸入映射、HUD 制度顯示。
- 後續行動：評估切換瞬間是否需要過渡提示與音效回饋。

### D-003
- 對應問題：Q-003
- 決策內容：回合制下玩家每移動一格推進世界一回合。
- 決策原因：維持時間與空間尺度一致，避免時間漏洞。
- 影響範圍：探索節奏、事件觸發頻率、資源消耗速度。
- 後續行動：納入 Q-004 進行移動成本平衡測試。

### D-004（草案）
- 對應問題：Q-007
- 決策內容：
	1. Tick 定義為世界最小模擬時間單位。
	2. Turn 定義為玩家操作節點，不是最小時間單位。
	3. 回合制下「玩家移動一格 = 推進 1 Turn」，而 1 Turn 內可對應固定 N Tick（N 為配置值）。
	4. 半即時制下依秒數累積推進 Tick，達到 Turn 門檻時更新需要 Turn 粒度的系統。
- 決策原因：統一世界時間基準，避免大地圖、遭遇戰、情報延遲、聚落演化各自採樣造成不一致。
- 影響範圍：主循環時間推進、移動耗時平衡、訊息傳播延遲、UI 時間顯示。
- 後續行動：
	1. 在 docs/game-design.md 補上 Turn/Tick 正式定義與換算範例。
	2. 在 config/game_config.gd 增加 TURN_TO_TICK 或等價參數。
	3. 在 HUD 顯示「Turn + 世界時間（Tick 或換算秒數）」。
	4. 完成後將 Q-007 狀態更新為 closed。
